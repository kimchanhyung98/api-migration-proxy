# 부하 시험과 검증 증거 기록

검증 담당자는 시험이 무엇을 확인하는지, 어떤 조건에서 실행됐는지, 어떤 범위까지 결론을 내릴 수 있는지를 기록해야 한다. 한 계층의 성공을 다른 계층의 검증 완료로 확대해서 해석해서는 안 된다.

## 검증 계층

| 계층 | 확인할 수 있는 범위 | 이 계층만으로 확인할 수 없는 범위 |
| --- | --- | --- |
| 문서·정적 검사 | 필드·용어·참조·문법과 설정 schema의 일관성을 확인한다. | 실제 HTTP 전달, 지연 또는 운영 상태를 입증하지 못한다. |
| 순수 로직 테스트 | Cohort 배정, 비교 정책, 결과 분류와 계산을 확인한다. | 실제 네트워크, 취소 처리 또는 프로세스 수명을 입증하지 못한다. |
| HTTP 통합 | 제어된 v1/v2 환경에서 전달·timeout·상한과 양쪽 실행을 확인한다. | 실제 서비스의 권한·데이터·운영 부하를 입증하지 못한다. |
| 실제 API 계약 | 대상 서비스의 입력·출력·권한과 예상 오류 계약을 확인한다. | 모든 피크 부하, 장애 상황 또는 장기 운영 결과를 입증하지 못한다. |
| 부하·장애 시험 | 시험에 포함한 도착률·크기·실패 조건에서 자원과 가용성을 확인한다. | 시험에 포함하지 않은 workload까지 보장하지 못한다. |
| 제한된 운영 | 관측한 사용자·데이터·업무 주기에서의 영향을 확인한다. | 관측하지 않은 구간이나 제외된 경로까지 보장하지 못한다. |

각 결과에는 source revision, 설정·비교 정책 revision, 실제 backend 배포 버전과 실행 환경을 기록해야 한다. 입력은 fixture 또는 비민감 표본 설명으로 식별해야 한다. 요청 분포와 관측 시간도 기록해야 한다. 성공·실패·누락의 증거를 해당 요구사항과 gate에 연결해야 한다.

## 실행 계약 검증

시험을 시작하기 전에 대상 route, 적용 설정, 입력과 기대 결과를 정해야 한다. 검증 담당자는 선택한 시나리오에 해당하는 항목만 아래 순서로 확인하십시오. 이 순서는 검증의 순서이며, serving과 shadow 실행을 직렬화하라는 뜻이 아니다.

1. 시나리오의 시작 설정을 확인하십시오.
2. HTTP 전달 시나리오이면 요청을 보내십시오.
3. 호출자가 받은 상태 코드·필수 헤더·body를 v1/v2 실행 결과와 대조하십시오.
4. 정상·예상 거절·실행 오류와 시험에 주입한 장애 조건을 구분하십시오.
5. Shadow·비교·수집 실패가 사용자 응답에 미친 영향을 기록하십시오.
6. 필수 비교 문맥이 미확인이면 비교 결과가 일치로 처리되지 않았는지 확인하십시오.
7. 설정 변경 또는 v1 복귀 시나리오이면 변경 요청 결과와 실제 적용 revision을 확인하십시오.
8. 설정 변경 또는 v1 복귀 시나리오이면 신규 요청의 배정 분포를 확인하십시오.
9. 저장·종료 시나리오이면 보존 기한이 남은 저장 확인 이벤트가 재시작·실행 단위 재생성 후에도 유지되는지 확인하십시오.
10. 저장·종료 시나리오이면 정해진 시간·자원 상한 안의 작업 배출 결과와 종료 기록을 확인하십시오.
11. 남은 작업·확정 유실·ACK 미확인을 구분하여 기록하십시오.
12. 관측 증거를 기대 결과와 대조하십시오.
13. 아래 상태 기준에 따라 결과를 기록하십시오.

시작 설정과 적용 결과의 판정 기준은 다음과 같다.

| 시나리오 | 확인 조건 |
| --- | --- |
| 요청 수락을 전제로 하는 시험 | 유효한 설정의 검증·적용과 실제 요청 수락이 확인돼야 한다. |
| 잘못된 설정을 거부하는 시험 | 적용이 거부되고 기존 유효 설정이 유지돼야 한다. |
| 설정 변경·복귀 시험 | 변경 전에 진행 중이던 요청과 변경 이후 요청을 구분해야 한다. |
| 모든 시험 | 확인하지 못한 계약이 있으면 전체 시나리오가 통과했다고 기록해서는 안 된다. |

외부 호출자가 받은 응답과 내부 비교 이벤트의 저장 증거는 서로 다르다. HTTP 응답을 받았다는 사실만으로 shadow 실행, 비교 판정 또는 저장이 완료됐다고 판단해서는 안 된다.

## 부하 시험 설계

부하 시험에는 method, route, 요청·응답 크기, 정상·예상 거절·오류의 비중과 요청 도착률을 정의해야 한다. 합성 입력을 사용하면 실제 workload의 어떤 분포를 재현했는지와 재현하지 못한 범위를 구분해야 한다. 동시 사용자 수만으로 부하를 설명해서는 안 되며, 실제 QPS·inflight·완료율을 함께 측정해야 한다.

| 비교 실험 | 확인할 목적 | 두 조건 사이에서 유지하거나 기록할 항목 |
| --- | --- | --- |
| v1 직접 호출과 프록시 v1 통과 | 프록시의 추가 hop·전달 비용을 확인한다. | 입력 분포, backend 배포와 cache 조건을 같게 유지해야 한다. |
| Shadow 0·일부·전체 | 반대편 실행과 수집의 추가 비용을 확인한다. | Serving을 v1으로 고정해야 한다. |
| v1 serving과 v2 serving | 실제 사용자 응답 경로의 성능 차이를 확인한다. | Shadow 조건과 관측 정책을 맞추고, serving/shadow 역할을 구분해야 한다. |
| 상세 표본 비율 0과 허용 표본 수집 | 상세 저장·마스킹의 비용을 확인한다. | Shadow 실행량과 입력 분포를 같게 유지해야 한다. |
| Warm 상태와 cold start·재시작 | 기동·복귀 때의 품질 변화를 확인한다. | Warm-up 과정, 노드와 cache 상태를 기록해야 한다. |
| 저장소 정상·지연·중단 | 관측 장애가 사용자 경로에 격리되는지 확인한다. | Queue·유실·사용자 지표를 같은 구간에서 확인해야 한다. |

검증 담당자는 각 부하 실험에 다음 절차를 적용하십시오.

1. 확인할 요구사항과 비교 실험을 선택하십시오.
2. [품질 기준](quality-and-acceptance.md)에 따라 route별 지연·오류·용량·자원·비용 목표를 정하십시오.
3. 입력 분포, 목표 도착률, 관측 기간과 비교할 환경 조건을 기록하십시오.
4. 부하를 시작하십시오.
5. 부하가 진행되는 동안 목표 도착률, 실제 전송량, 실제 도착률, 완료율과 미발행 요청을 기록하십시오.
6. 관측 구간이 끝나고 미발행 요청이 있으면 생성기 자원 부족과 응답 대기에 따른 발행 지연을 구분하십시오.
7. 성공·timeout·취소·미완료 요청의 수와 상태를 포함하여 지연·오류·자원 결과를 해석하십시오.
8. 실제 도달한 부하와 완료율을 목표에 대조하십시오.
9. 관측 조건·누락·검증 범위와 결과 상태를 기록하십시오.

실험 상태별 판정 기준은 다음과 같다.

| 상태 | 판정 기준 |
| --- | --- |
| 목표 미정 | 측정 결과는 기록할 수 있으나 요구사항 충족을 판정해서는 안 된다. |
| 비교 조건 불일치 | 같은 조건을 유지하지 못한 항목을 결과의 해석 한계로 기록해야 한다. |
| 미발행 원인 미확인 | 생성기 CPU·네트워크·동시 실행 부족과 응답 대기를 조사해야 한다. 원인을 확인하지 못하면 미확인으로 기록해야 한다. |
| 완료 표본 편향 | 빠르게 완료된 표본만으로 전체 성능을 요약해서는 안 된다. |
| 목표 부하 미도달 | 해당 구간을 목표 용량의 통과 증거로 사용해서는 안 된다. |
| 일부 부하만 검증 | 실제 검증한 부하 범위를 명시해야 한다. |

전체 적격 요청에 대한 full shadow를 검증하는 경우에는 `shadow_sample_ratio=1`이라는 설정값과 실제 선택·시작·종료·오류 비율을 함께 확인해야 한다. 자원 보호 상한, 취소 또는 드롭으로 실제 실행량이 줄어든 구간을 full-load 통과 근거로 사용해서는 안 된다.

k6를 선택하는 경우에는 [dropped_iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/)와 실제 HTTP 요청 수를 함께 기록해야 한다. 한 iteration에 포함되는 요청 수는 시나리오에 따라 다르므로 iteration 수를 그대로 요청 수로 바꿔 해석해서는 안 된다. 이 예시는 부하 도구의 채택을 확정하는 것이 아니다.

## 검증 결과 기록 양식

```text
test_id / requirement_ids / relevant_gates:
source_revision / config_revision / comparison_policy_revision:
environment / backend_versions / dependency_state:
input_distribution / request_count / duration / actual_qps:
expected_behavior:
actual_behavior / metrics / event_sample:
status: pass | fail | not_run | inconclusive
limitations / missing_evidence:
owner / next_action:
```

양식의 `status`는 다음 기준으로 기록해야 한다.

| 상태 | 판정 조건 | 기록해야 할 근거 |
| --- | --- | --- |
| `pass` | 정한 실행 조건에서 해당 시나리오의 기대 결과를 모두 확인했다. | 실제 동작과 이를 확인한 지표·이벤트·응답 증거, 검증한 범위를 기록한다. |
| `fail` | 기대 결과를 위반한 동작을 확인했다. | 위반한 계약, 입력·조건과 실제 동작을 기록한다. |
| `not_run` | 해당 시나리오를 실행하지 않았다. | 미실행 항목과 다음 조치를 기록한다. |
| `inconclusive` | 실행했지만 목표·표본·관측 또는 증거가 부족하여 충족 여부를 판단할 수 없다. | 부족한 증거와 판단할 수 없는 범위를 기록한다. |

`not_run`과 `inconclusive`는 gate 통과에 필요한 증거가 없는 상태다. 테스트 결과의 상태와 gate의 `pass`·`fail`·`unknown`은 별도로 기록해야 하며, 미실행·판정 불가 결과를 gate의 `pass`로 바꿔서는 안 된다. Comparator 단위 검증, HTTP 200 또는 프로세스 readiness만으로 전환 완료를 판정해서는 안 된다.
