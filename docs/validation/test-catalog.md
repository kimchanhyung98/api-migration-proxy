# 요구사항별 검증 시나리오

이 문서는 공개 동작, serving·shadow의 실행과 관측, 실패가 사용자에게 미치는 영향을 검증하는 기준이다. 아래 절차의 존재는 해당 검증을 실제로 실행했거나 통과했다는 뜻이 아니다. 각 기능의 계약과 FR 수용 조건은 해당 시나리오에 연결한 도메인 문서를 기준으로 한다. NFR의 의미와 서비스별로 정해야 하는 수치는 [공통 품질 요구사항](quality-and-acceptance.md)에서 확인한다.

## 적용과 판정

절차 수행자는 검증자다. 각 항목의 조건을 충족하는 입력과 환경을 준비하십시오. 그다음 각 사례 안에서 번호 순서에 따라 절차를 수행하십시오. 서로 다른 입력·설정·장애 사례의 실행 순서는 제한하지 않는다. 결과는 사례별로 구분하십시오.

serving과 shadow가 병렬로 실행되는 동작을 절차의 번호 때문에 직렬 실행으로 바꾸지 마십시오.

통과하려면 해당 사례의 판정 조건을 모두 충족하고 이를 뒷받침하는 관측 증거를 확보해야 한다. 내부 함수의 호출 횟수만으로 공개 동작의 성공을 판정하지 마십시오. 필요한 정책·목표 수치가 미정이거나 결과를 관측하지 못했다면 통과로 처리하지 마십시오. 실제 결과와 미실행·판정 불가 상태는 [검증 결과 기록 양식](load-and-evidence.md)에 따라 기록하십시오.

각 시나리오의 증거에는 입력과 정책·설정·환경을 식별할 수 있는 정보를 남기십시오. 본문·헤더·예외를 대조할 때는 합성 입력 또는 허용된 비민감 증거를 사용하십시오. 실제 금지 값을 결과 기록에 복사하지 마십시오.

serving·shadow·cohort·revision·epoch는 [공통 용어](../_rules/glossary.md)를 따른다. E/S/D/T/C/M/X/W는 [비교 커버리지의 분모 정의](../observability/coverage-and-analysis.md)를 따른다. backend 실행 종료와 사용자 응답 전송 종료는 서로 다른 시점이며, 시간 측정은 [지연의 측정 경계](../observability/metrics.md)를 따른다.

## T-01. 잘못된 route·backend 설정의 활성화 거부

요구사항: [FR-01](../routing/route-registration.md), [FR-06](../routing/configuration.md), [FR-29](../routing/configuration.md)

**대상 조건:** 기존 유효 설정을 적용한 상태에서 중복 route, 우선순위가 모호한 route, 허용되지 않은 backend를 각각 포함한 설정을 준비하십시오. 각 설정에는 한 종류의 오류만 넣으십시오. 설정별 거부 원인을 구분하기 위한 조건이다.

1. 오류가 있는 설정을 각각 검증·적용 경로에 제출하십시오.
2. 각 제출 뒤 실제 적용 revision과 요청 목적지를 확인하십시오.

**판정:** 각 설정은 활성화 전에 거부되어야 한다. 거부 이후에도 기존 유효 설정의 revision과 목적지가 유지되어야 한다.

**증거:** 제출한 설정의 오류 종류, 검증 실패 사유, 제출 전후 적용 revision, 기존 경로로 처리된 요청 결과를 남기십시오.

## T-02. v1 통과의 성공·예상 거절 응답 보존

요구사항: [FR-02](../routing/serving-and-cohorts.md), [FR-07](../routing/http-forwarding.md), [FR-17](../comparison/context-and-outcomes.md)

**대상 조건:** v2 serving 비율과 shadow 표본율을 모두 0으로 설정하십시오. 등록 API 계약에 해당하는 성공 응답과 예상 거절 응답을 각각 준비하십시오.

1. 각 입력을 프록시로 호출하십시오.
2. 양쪽 backend의 실제 실행 기록과 호출자가 받은 status·필수 헤더·body를 대조하십시오.

**판정:** 논리 요청마다 v1만 한 번 실행되어야 하며, v2는 실행되어서는 안 된다. 호출자는 v1의 성공·예상 거절 계약에 해당하는 응답을 보존한 상태로 받아야 한다.

**증거:** 입력별 양쪽 실행 기록, v1 원응답, 호출자가 받은 응답을 남기십시오. 예상 거절 여부를 판단한 API 계약도 연결하십시오.

## T-03. 미등록 HTTP와 미지원 프로토콜의 기존 경로 유지

요구사항: [FR-08](../routing/route-registration.md)

**대상 조건:** 등록되지 않았으나 v1 통과가 검증된 일반 HTTP 경로와 지원이 검증되지 않은 프로토콜의 경로를 구분하십시오. 각 경로의 기존 진입점과 처리 정책을 확인하십시오.

1. 미등록 일반 HTTP와 미지원 프로토콜 요청을 각각 해당 유형에 정해진 진입 경로로 보내십시오.
2. 각 요청의 실제 목적지와 호출 결과를 확인하십시오.

**판정:** 검증된 일반 HTTP 요청에는 문서화된 v1 통과 정책이 적용되어야 한다. 미지원 프로토콜은 기존 진입점 정책을 유지해야 한다. 기존 경로의 처리 결과를 프록시의 해당 프로토콜 지원 증거로 해석하지 마십시오.

**증거:** 경로별 지원 범위, 적용 정책, 실제 요청 경로와 호출 결과를 남기십시오.

## T-04. shadow가 먼저 완료되어도 serving 선택 유지

요구사항: [FR-03](../routing/serving-and-cohorts.md), [FR-12](../shadow/parallel-execution.md)

**대상 조건:** serving과 shadow의 응답을 서로 구분할 수 있도록 준비하십시오. shadow가 먼저 끝나고 serving이 나중에 끝나는 지연 조건을 사용하십시오.

1. 요청을 보내십시오.
2. 요청 시작 시 선택된 serving backend를 확인하십시오.
3. 동일 요청의 양쪽 실행 완료 순서와 사용자 응답 출처를 확인하십시오.

**판정:** shadow가 먼저 끝나도 serving 선택은 바뀌어서는 안 된다. 사용자에게는 처음 선택한 serving의 응답만 전달되어야 한다.

**증거:** 요청별 최초 배정, 양쪽 실행 완료 시각, 호출자가 받은 응답과 그 출처를 남기십시오.

## T-05. v2 serving 비율의 경계와 bucket 배정

요구사항: [FR-04](../routing/serving-and-cohorts.md)

**대상 조건:** 전환이 활성화되고 필요한 배정 키가 있는 route를 사용하십시오. 같은 bucket 정책 아래 v2 serving 비율 0, 1, 0과 1 사이의 값을 각각 검증하십시오.

1. 검증할 비율을 적용하십시오.
2. 검증 입력의 bucket과 serving 배정을 확인하십시오.
3. 중간 비율에서는 각 입력의 bucket을 적용된 비율과 대조하십시오.

**판정:** 비율 0에서는 v1, 비율 1에서는 v2가 serving으로 선택되어야 한다. 중간 비율에서는 `bucket < v2_serve_ratio`일 때만 v2가 선택되어야 한다. cohort 배정 비율을 실제 요청량의 동일 비율로 요구하지 마십시오.

**증거:** 입력의 비민감 식별, 적용 revision·비율·bucket 정책, 입력별 기대 배정과 실제 배정을 남기십시오.

## T-06. cohort 재현성과 비율 증가 시 기존 v2 집단 유지

요구사항: [FR-05](../routing/serving-and-cohorts.md), NFR-10

**대상 조건:** 동일한 키·그룹·salt·해시·직렬화 규칙을 사용하는 입력 집합을 준비하십시오. 인스턴스 변경과 프로세스 재시작을 검증할 수 있는 범위를 명시하십시오.

1. 각 인스턴스와 재시작 전후에서 동일 입력의 bucket을 확인하십시오.
2. 배정 기준이 같은 상태에서 v2 serving 비율만 증가시키십시오.
3. 비율 증가 전후의 v2 배정 집합을 대조하십시오.

**판정:** 동일 입력의 bucket은 인스턴스와 재시작에 관계없이 재현되어야 한다. 비율을 증가시키면 기존 v2 cohort의 모든 구성원은 v2 배정을 유지해야 한다.

**증거:** 배정 정책 식별 정보, 검증한 인스턴스·재시작 경계, 입력별 bucket, 비율 변경 전후 배정 집합을 남기십시오.

## T-07. 연관 route의 그룹 일관성과 필수 키 누락

요구사항: [FR-05](../routing/serving-and-cohorts.md), [FR-29](../routing/configuration.md)

**대상 조건:** 같은 cohort group에 속한 연관 route를 준비하십시오. 유효한 그룹 설정, 그룹 내 정책이 하나씩 다른 설정, 필수 배정 키가 없는 요청을 별도 사례로 구성하십시오. 불일치 검증 대상은 전환 활성 상태·키 출처·배정 단위·salt·해시·직렬화·비율이다.

1. 유효 설정 사례에서는 같은 키로 연관 route를 호출하십시오.
2. 유효한 동일 revision의 route별 배정을 대조하십시오.
3. 정책 불일치 사례에서는 불일치 설정을 각각 제출하십시오.
4. 각 불일치 설정의 활성화 전 거부 여부를 확인하십시오.
5. 필수 키 누락 사례에서는 키를 제외한 요청을 보내십시오.
6. 키가 누락된 요청의 배정과 사유를 확인하십시오.

**판정:** 유효한 동일 revision의 연관 route 배정은 일치해야 한다. 그룹 정책이 다른 설정은 활성화 전에 거부되어야 한다. 필수 키가 없으면 v1을 선택하고 `missing_cohort_key` 사유를 기록해야 한다.

**증거:** 그룹별 정책, 요청별 revision·배정, 불일치 설정의 거부 사유, 필수 키 누락 요청의 배정 사유를 남기십시오.

## T-08. 처리 중 설정 변경과 요청별 스냅샷 보존

요구사항: [FR-06](../routing/configuration.md)

**대상 조건:** 목적지 또는 비교 정책이 다른 두 유효 revision을 준비하십시오. 설정 변경 시 기존 요청이 진행 중인 지연 조건을 사용하십시오. 설정 적용에는 검증 환경이 제공하는 절차를 사용하십시오. 동적 설정 제어가 연결되어 있다고 가정하지 마십시오.

1. 첫 revision으로 요청을 시작하십시오.
2. 기존 요청이 진행 중인 상태에서 다음 revision을 신규 요청에 적용하십시오.
3. 변경 후 요청을 시작하십시오.
4. 각 요청이 사용한 목적지·배정·비교 정책을 확인하십시오.

**판정:** 기존 요청은 시작 시 확보한 스냅샷을 끝까지 사용해야 한다. 한 요청 안에서 이전 revision과 다음 revision의 목적지·배정·비교 정책이 섞여서는 안 된다.

**증거:** 두 revision의 차이, 적용 시점, 요청별 시작 시점과 실제 사용 정책을 남기십시오.

## T-09. 요청 body·경로·query·헤더의 양쪽 전달

요구사항: [FR-07](../routing/http-forwarding.md), [FR-11](../shadow/parallel-execution.md)

**대상 조건:** shadow 실행이 허용된 요청에 body, 인코딩된 경로, 중복 query 키와 전달 대상 헤더를 포함하십시오. 양쪽 backend가 받은 요청을 확인할 수 있어야 한다.

1. 요청을 프록시로 보내십시오.
2. 각 backend가 받은 body·경로·query·헤더를 원요청 및 전달 계약과 대조하십시오.

**판정:** 각 backend는 독립적으로 동일한 body 바이트를 소비해야 한다. 한쪽 reader의 소비로 다른 쪽 body가 비거나 변형되어서는 안 된다. raw path 인코딩, 중복 query 키의 의미와 전달 대상 헤더가 보존되어야 한다.

**증거:** 원요청과 양쪽 수신 요청의 바이트·필드 비교 결과를 남기십시오. 전달 계약상 제거하는 hop-by-hop 헤더와 보존 대상 헤더를 구분하십시오.

## T-10. 특수 HTTP 응답과 목적지 authority 계약

요구사항: [FR-07](../routing/http-forwarding.md), [FR-18](../comparison/normalization.md)

**대상 조건:** 복수 `Set-Cookie`, 압축 응답, redirect, HEAD·204·304 응답을 각각 준비하십시오. 업로드가 끝나기 전에 backend가 413 등의 최종 응답을 반환하고 호출자는 남은 입력 대신 응답을 기다리는 사례도 준비하십시오. 응답 headers를 먼저 보낸 뒤 나머지 요청 body를 계속 받는 사례를 별도로 준비하십시오. mirror 경로가 authority를 바꾸는 구성에서는 가상 호스트와 요청 서명 계약도 검증 대상에 포함하십시오.

1. 각 응답 사례를 호출하십시오.
2. backend 원응답과 사용자 수신 응답을 대조하십시오.
3. authority 변경이 있는 경로에서는 backend가 받은 Host·authority와 인증·서명 처리 결과를 확인하십시오.

**판정:** body 유무와 status·필수 헤더의 계약을 보존해야 한다. 복수 `Set-Cookie`를 임의로 결합해서는 안 되며, 압축 표현과 헤더가 일치해야 한다. 조기 최종 응답은 남은 업로드 완료를 기다리지 않고 원래 status·body 바이트·전달 대상 헤더를 유지해야 하며, 업로드 대기로 인해 502·504로 바뀌어서는 안 된다. 응답 headers만 받은 경우에는 나머지 요청 body 전달을 계속해야 한다. 자동 redirect follow나 불필요한 JSON 파싱으로 응답 의미를 바꾸어서는 안 된다. authority 변경은 가상 호스트·인증·서명 계약을 만족해야 한다.

**증거:** 사례별 원응답·전달 응답, 압축 표현과 헤더의 일치 여부, 업로드·조기 응답 시각과 종료 후 잔여 작업, redirect 후속 호출 여부, authority·서명 검증 결과를 남기십시오.

## T-11. 부적격 route의 shadow 실행 방지

요구사항: [FR-09](../shadow/eligibility-and-sampling.md)

**대상 조건:** 부작용을 확인하지 않은 route와 복제가 허용되지 않은 route를 각각 준비하십시오. route 등록 여부와 shadow 적격성은 별도로 설정하십시오.

1. 각 route에 요청을 보내십시오.

**판정:** 두 종류의 route 모두 shadow를 실행해서는 안 된다. 미실행 이유는 적격성 판단의 사유로 계측되어야 하며, route 등록만으로 복제가 허용되어서는 안 된다.

**증거:** route별 적격성 근거, 양쪽 실행 기록, 선택 결과와 사유를 남기십시오.

## T-12. shadow 표본율과 역할 전환·중복 복제 방지

요구사항: [FR-10](../shadow/eligibility-and-sampling.md), [FR-15](../shadow/parallel-execution.md)

**대상 조건:** 전환이 활성화된 지원 route에서 복제 적격성과 필수 cohort 키 조건을 충족하는 요청을 사용하십시오. shadow 중지 상태가 아닌 설정으로 표본율 0과 1을 각각 검증하십시오. 비율 1의 실행 횟수 검증에서는 슬롯 부족·입력 상한 초과·취소가 없는 조건을 사용하십시오. v1 serving과 v2 serving을 모두 포함하십시오.

1. 진입 gateway와 프록시의 복제 설정을 확인하십시오.
2. 각 serving 역할과 표본율 조합으로 요청을 보내십시오.
3. 논리 요청별 실제 backend 실행 횟수와 역할을 확인하십시오.

**판정:** 표본율 0에서는 serving만 실행되어야 한다. 표본율 1의 조건 충족 요청에서는 v1과 v2가 각각 한 번 실행되어야 하며, v2 serving일 때 v1이 shadow여야 한다. gateway와 프록시가 같은 요청을 중복 mirror해서는 안 된다.

**증거:** 진입 경로의 복제 설정, 요청별 serving·shadow 역할, 각 backend 실행 기록을 남기십시오.

## T-13. 사용자 응답 완료 후 느린 shadow의 수명

요구사항: [FR-12](../shadow/parallel-execution.md), [FR-14](../shadow/lifecycle-and-limits.md)

**대상 조건:** serving 응답은 먼저 완료되고 shadow는 자신의 deadline 이내에 늦게 완료되는 요청을 준비하십시오.

1. 요청을 보내십시오.
2. 사용자 응답 전송 종료 시점을 확인하십시오.
3. 이미 시작된 shadow의 종료 결과를 확인하십시오.

**판정:** 사용자 응답은 shadow 완료를 기다리지 않고 종료되어야 한다. 정상적인 사용자 응답 종료를 이유로 shadow를 취소해서는 안 되며, shadow는 자신의 deadline 안에서 결과를 수집해야 한다.

**증거:** serving backend 종료 시각, 사용자 응답 전송 종료 시각, shadow 종료 시각·결과와 적용 deadline을 남기십시오.

## T-14. 전송 중 client 종료·shadow timeout·정상 완료 뒤 disconnect 구분

요구사항: [FR-13](../shadow/lifecycle-and-limits.md), [FR-14](../shadow/lifecycle-and-limits.md), [FR-28](../observability/coverage-and-analysis.md)

**대상 조건:** 아래 세 가지 독립 사례를 준비하십시오.

- 응답 전송 중 client 연결 종료
- serving 실행 종료보다 이른 shadow timeout
- 정상 응답 완료 뒤 ASGI `http.disconnect`

1. 각 사례를 실행하십시오.
2. backend 실행 상태와 사용자 전송 상태의 변화를 관측하십시오.
3. 취소 시도와 serving 지속 여부를 확인하십시오.
4. T 증가 시점과 최종 비교 이벤트 제출 시점을 확인하십시오.

**판정:** 전송 중 client 연결 종료에서는 upstream과 실행 중 shadow의 취소를 시도하고 사유를 기록해야 한다. 정상 응답 완료 뒤 disconnect는 shadow 취소 근거로 사용해서는 안 된다. shadow timeout 뒤에도 serving은 지속되어야 한다. serving backend가 종료되기 전에 T를 증가시켜서는 안 되며, 사용자 전송 종료 결과를 얻기 전에 최종 비교 이벤트를 제출해서는 안 된다.

**증거:** 사례별 상태 변화 시각, disconnect 발생 시점, 취소 사유, 양쪽 종료 결과, T와 이벤트 제출 기록을 남기십시오.

**판정:** headers 전송 전 실패에는 정의된 gateway 오류 계약이 적용되어야 한다. 응답 전송이 시작된 뒤에는 다른 정상 응답으로 대체해서는 안 되며, 불완전 전송을 기록해야 한다. 실패를 이유로 반대편 응답을 자동 fallback하거나 요청을 중복 재실행해서는 안 된다.

**증거:** 실패 시점, 이미 전송된 응답 범위, 사용자 관측 결과, 양쪽 실행 기록과 오류 사유를 남기십시오.

**판정:** 대기 작업과 메모리가 무한히 증가해서는 안 된다. 큐 포화·만료와 비교 지연을 원인별로 계측해야 하며, 수집 작업의 장애 때문에 serving이 저장 완료를 동기적으로 기다려서는 안 된다.

**증거:** 적용 예산, 시간에 따른 큐·메모리·대기 상태, 감지된 드롭 사유, 사용자 응답 결과를 남기십시오.

## T-24. 저장 실패·ACK 미확인·재시도의 구분

요구사항: [FR-21](../collection/event-model.md), [FR-22](../collection/async-storage.md), [FR-28](../observability/coverage-and-analysis.md), NFR-04

**대상 조건:** 저장소 중단과 복구, 배치 일부 성공, 저장 성공 뒤 ACK 유실, 같은 event ID의 중복 재시도를 각각 준비하십시오. ACK는 저장 완료 확인 응답을 뜻한다.

검증에 사용하는 저장소와 실제 연결한 어댑터를 명시하십시오. 사설 PostgreSQL은 선택 구성이다. 이를 선택한 경우 해당 어댑터와 DB에서 아래 시나리오를 별도로 검증하십시오. SQLite의 결과를 PostgreSQL의 검증 완료로 표시하지 마십시오.

1. 검증할 저장 장애를 발생시키십시오.
2. 장애가 지속되는 동안 serving 요청을 보내십시오.
3. 수집기의 재시도 또는 저장 재확인 결과를 관측하십시오.
4. 저장 행과 W, 확정 실패·ACK 미확인 상태를 대조하십시오.

**판정:** serving은 저장 장애와 분리되어 지속되어야 한다. 같은 event ID로 복수 행을 만들거나 W를 중복 증가시켜서는 안 된다. ACK가 없다는 사실만으로 저장 실패를 확정해서는 안 되며, 재시도 종료 뒤에도 저장 여부가 불명이면 그 상태를 유지해야 한다.

**증거:** 저장소·어댑터·버전, event ID별 시도·ACK·저장 행, 배치 일부 성공 내역, W 변화, 재시도 예산과 사용자 응답 결과를 남기십시오.

## T-25. 상세 표본율·크기 제한과 요약 비교의 독립성

요구사항: [FR-23](../collection/detail-sampling.md)

**대상 조건:** 동일한 실행·비교 입력을 유지하면서 상세 표본율 0, 일부 표본을 선택하는 비율, 상세 크기 상한에 도달하는 사례를 각각 준비하십시오.

1. 각 상세 정책으로 비교 요청을 처리하십시오.
2. 비교 결과·요약·메트릭을 확인하십시오.
3. 실제 저장된 상세를 확인하십시오.

**판정:** 상세 표본율 0에서도 비교·요약·메트릭은 유지되어야 한다. 상세 선택은 backend 실행이나 비교 여부를 바꾸어서는 안 된다. 저장된 상세는 허용 필드와 크기 상한을 만족해야 하며, 선택됐다는 사실을 저장 완료로 간주해서는 안 된다.

**증거:** 상세 정책, 동일 입력의 비교 결과·요약, 상세 선택·저장 상태와 크기를 남기십시오.

## T-26. 민감 값의 저장·로그·trace·exporter 유출 방지

요구사항: [FR-24](../collection/detail-sampling.md), NFR-07

**대상 조건:** 토큰·cookie·민감 본문·예외·diff에 식별 가능한 합성 금지 값을 넣으십시오. 상세 수집이 비활성인 상태도 포함하십시오. 실제 사용하는 자동 HTTP 계측과 exporter가 있다면 그 출력도 검증 범위에 포함하십시오.

SQLite를 사용하는 경우 새 파일·데이터 디렉터리와 기존 경로를 각각 준비하십시오. 실제 사용하는 저널·WAL·SHM 등의 부속 파일과 백업 파일도 권한 확인 범위에 포함하십시오.

1. 합성 금지 값을 포함한 요청과 오류·불일치 사례를 실행하십시오.
2. 저장 결과, 조회 결과, 서버 로그·표준 출력·표준 오류, trace와 실제 exporter 전송 데이터의 URL·query·헤더·예외를 확인하십시오.
3. SQLite를 사용한다면 실행 계정과 허용되지 않은 계정의 파일 접근 범위를 확인하십시오.

**판정:** 금지 값은 어느 검증 대상 출력에도 노출되어서는 안 된다. 상세 표본율 0만으로 자동 HTTP 계측의 안전성을 판정하지 마십시오. 도입하지 않았거나 출력에 접근하지 못한 경로는 검증한 것으로 기록하지 마십시오.

프록시가 새로 만드는 SQLite 파일은 `0600`, 새 데이터 디렉터리는 `0700`이어야 한다. 기존 경로와 부속·백업 파일의 위치와 접근 권한은 정한 보호 범위를 충족해야 한다. 파일 권한 확인을 저장 암호화나 백업 삭제의 증거로 사용하지 마십시오.

**증거:** 합성 값의 위치, 적용된 허용·마스킹 정책, 검사한 출력 경로와 검사 결과를 남기십시오. SQLite를 사용한 경우 파일·디렉터리의 소유자와 권한, 실제 접근 검사 결과를 함께 남기십시오. 증거 자체에도 실제 비밀값을 포함하지 마십시오.

## T-27. 목적별 보존 만료와 삭제 실패

요구사항: [FR-24](../collection/detail-sampling.md), NFR-07, NFR-09

**대상 조건:** 요약·상세·전환 이력의 보존 기준을 확인하십시오. 만료 시각이 기준 시각과 같은 기록, 이미 지난 기록과 아직 지나지 않은 기록을 준비하십시오. 배치 상한보다 많은 만료 기록, 삭제 실패와 정리 중 종료를 별도 사례로 포함하십시오.

1. 정리 실행 주체·주기·배치 상한을 확인하십시오.
2. 기본 CLI의 내부 주기 작업과 수동 `purge-events`를 각각 실행하십시오.
3. 목적별 삭제 결과와 미만료 기록의 보존 여부를 확인하십시오.
4. 삭제 실패 사례에서는 만료 정리 실패를 발생시키십시오.
5. 삭제 실패와 적체 관측 결과를 확인하십시오.
6. 정리 중 종료 사례에서는 대기 종료 시점과 실제 DB 작업의 종료 결과를 구분하십시오.

**판정:** 각 목적의 기한에 따라 만료 시각이 기준 시각과 같거나 앞선 대상만 정리해야 한다. 기본 CLI의 자동 정리는 외부 스케줄러 없이 수행되어야 하며, 이전 정리가 진행 중이면 중복 작업을 시작해서는 안 된다. 수동 실행 성공만으로 자동 정리의 연결을 확인했다고 표시하지 마십시오.

한 배치의 성공과 해당 기준 시각까지의 전체 만료 기록 정리 완료를 구분하십시오. 삭제 실패와 남은 만료 기록을 관측할 수 있어야 하며, 실패한 삭제를 완료로 기록해서는 안 된다. 종료 중 대기 취소를 실제 DB 삭제 완료로 처리하지 마십시오.

**증거:** 실행 주체·주기·배치 상한, 기록별 생성·만료 기준, 실제 삭제 수와 잔여 만료 수, 정리 전후 존재 여부, 삭제 실패와 종료 시 미확인 상태를 남기십시오.

## T-28. 권한·범위 안의 비교 이벤트 조회

요구사항: [FR-25](../collection/query-and-retention.md)

**대상 조건:** route·기간·result·revision이 다른 이벤트와 서로 다른 조회 권한을 준비하십시오. 허용 기간·행 수·상세 조회 범위를 확인하십시오. 만료 정리를 실행하기 전의 요약 만료·상세만 만료된 기록도 포함하십시오.

1. 각 권한으로 조건을 지정한 이벤트 조회를 수행하십시오.
2. 조회 범위 제한과 반환된 이벤트의 양쪽 backend 연결 정보를 확인하십시오.

**판정:** 조회 결과는 허용된 권한과 범위 안에 있어야 한다. 한 이벤트에서 serving 선택, 양쪽 backend 결과, 비교 정책과 revision을 연계할 수 있어야 한다. 상세 권한이 없는 조회에 상세 내용을 반환해서는 안 된다.

요약 만료 시각이 조회 시각과 같거나 앞서면 해당 행을 반환해서는 안 된다. 상세만 만료됐으면 유효한 요약만 반환해야 한다. 정리 실행 전에도 이 조건을 적용해야 하며, 조회 제외를 물리 삭제 완료로 해석하지 마십시오.

**증거:** 조회 권한·필터·범위 제한, 반환된 event ID와 양쪽 결과의 연결, 허용되지 않은 조회의 처리 결과를 남기십시오. 만료 사례에서는 조회 기준 시각, 반환 결과와 실제 저장 행의 잔존 여부를 구분해 남기십시오.

## T-29. 고정 요청 집단의 분모와 종료·저장 시각

요구사항: [FR-21](../collection/event-model.md), [FR-27](../observability/metrics.md), [FR-28](../observability/coverage-and-analysis.md)

**대상 조건:** 요청 시작 구간으로 식별할 수 있는 고정 집단을 준비하십시오. 실제 실행·실패·선택 후 미실행·비교·저장을 포함하십시오. 느린 client·구간 경계 뒤 완료·계측 재시작을 별도 사례로 넣으십시오.

1. 집계 시작 전에 이미 진행 중인 작업과 대상 요청 집단을 구분하십시오.
2. backend 실행 종료와 사용자 응답 전송 종료를 각각 관측하십시오.
3. 구간 뒤에 남은 실행·비교·저장 작업의 결과를 원래 요청 집단에 귀속시키십시오.
4. 집단별 E/S/D/T/C/M/X/W를 대조하십시오.

**판정:** backend 실행 종료에는 해당 실행의 연결 정리 종료가 포함된다. backend 실행 종료를 사용자 전송 종료와 같다고 해석하지 마십시오. 최종 요약은 사용자 전송 종료 결과를 얻은 뒤 제출해야 한다. 관측 유실 없이 완료된 동일 집단은 아래 관계를 모두 만족해야 한다.

- `E ≥ S ≥ D ≥ T ≥ C`
- `C = M + X`
- `0 ≤ W ≤ S`

처리 시각 counter를 동일한 요청 시작 집단으로 해석하지 마십시오. 유실된 S를 저장 행만으로 복원하지 마십시오.

**증거:** 집단의 시작 범위, 각 종료·비교·저장 시각, 잔여 작업, counter 수집·재시작 경계, 이벤트와 분모 대조 결과를 남기십시오. 집단이나 계측을 복원할 수 없는 구간은 완전성 미확인으로 표시하십시오.

## T-30. 증거 부족과 계획된 비교 종료의 구분

요구사항: [FR-28](../observability/coverage-and-analysis.md), [FR-30](../rollout/stages-and-gates.md)

**대상 조건:** 비교 실행 구간의 분모 0, 표본 부족, 모니터링 누락을 각각 준비하십시오. 별도로 S5·S6의 계획된 비교 종료 상태를 준비하십시오. S5의 E 검증에는 전환 활성·지원 route·복제 적격·필수 cohort 키 충족 조건을 모두 만족하는 요청을 사용하십시오.

1. 비교 실행 사례에서는 구간별 분모 상태와 gate 증거를 확인하십시오.
2. S5 사례에서는 신규 shadow 선택을 중지하십시오.
3. 중지 이후 E와 S의 집계를 확인하십시오.
4. S5·S6의 비교 적용 제외 사유와 과거·현재 증거를 확인하십시오.

**판정:** 분모 0은 데이터 없음, 관측 누락은 미확인으로 구분해야 한다. 비교 실행 중 증거가 부족하면 gate는 `unknown`이다. 증거가 부족한 gate를 통과로 처리하지 마십시오. S5에서는 신규 S=0이어도 조건을 만족하는 E를 계속 집계해야 한다. 계획된 종료에는 적용 제외 사유·과거 비교 증거·현재 serving 검증이 모두 필요하다. 계획된 종료를 신규 비교 통과로 표시하지 마십시오.

**증거:** 구간별 분모와 누락 원인, stage·적용 revision, S5의 E·S 변화, 적용 제외 사유와 증거 참조, gate 판단을 남기십시오.

## T-32. shadow 중지·serving 복귀·동시 적용의 영향

요구사항: [FR-16](../rollout/rollback-and-bypass.md)

**대상 조건:** v2 serving이 활성화된 상태에서 shadow만 중지, serving만 v1으로 복귀, 두 조작을 함께 적용하는 세 사례를 각각 준비하십시오. 변경 시점의 진행 중 요청도 식별하십시오.

1. 각 사례의 설정 변경을 적용하십시오.
2. 변경 후 신규 요청의 serving 배정과 shadow 실행량을 확인하십시오.
3. 변경 전 시작한 요청의 종료 결과를 확인하십시오.

**판정:** shadow만 중지하면 신규 반대편 실행은 멈추되 v2 serving 배정은 유지되어야 한다. serving만 v1으로 복귀한 경우 유지된 shadow 정책에 따른 v2 shadow 실행 여부를 확인하십시오. 두 조작을 적용하면 신규 serving은 v1이고 신규 shadow는 없어야 한다. 진행 중 요청에는 기존 수명·취소 정책을 적용해야 한다.

**증거:** 조작별 적용 revision·시점, 신규 요청의 배정·실행 분포, 진행 중 요청의 종료 결과를 남기십시오.

## T-33. 준비된 v1으로의 serving 복귀 시간

요구사항: [FR-16](../rollout/rollback-and-bypass.md), [FR-30](../rollout/stages-and-gates.md), NFR-02

**대상 조건:** v1 데이터·스키마·권한·공개 계약·용량·경로가 복귀 조건을 충족하는지 확인하십시오. 검증할 복귀 목표 시간과 측정 시작·종료 경계를 먼저 확인하십시오.

1. v2 serving 상태에서 v1 serving 복귀를 적용하십시오.
2. 실제 신규 요청 분포가 v1으로 돌아오는 시점까지 측정하십시오.
3. 변경 당시 진행 중인 요청의 실행 기록을 대조하십시오.

**판정:** 실제 분포의 복귀 시간은 정한 목표 안에 있어야 한다. 설정 변경 요청의 성공만으로 복귀 완료를 판정하지 마십시오. 진행 중 요청을 중복 재실행하지 마십시오. 목표 시간이나 측정 증거가 없으면 충족 여부를 확정하지 마십시오.

**증거:** v1 준비 근거, 목표 시간·측정 경계, 실제 분포·소요 시간, 진행 요청의 실행 기록을 남기십시오.

## T-34. v1 복귀 조건 미충족 시 준비 상태 판정

요구사항: [FR-30](../rollout/stages-and-gates.md)

**대상 조건:** v1 데이터 최신성, 스키마 호환성, 용량 중 하나 이상이 복귀 조건을 충족하지 않는 사례를 준비하십시오. 해당 서비스에 정해진 데이터·서비스 복구 경로를 확인하십시오.

1. 조건별 준비 근거를 복귀 가능성 판단에 제출하십시오.
2. 판정 결과와 선택한 복구 경로를 확인하십시오.

**판정:** 필수 조건이 미충족인 v1의 준비 상태는 `pass`가 되어서는 안 된다. 단순 라우팅 복귀와 별도로 필요한 데이터·서비스 복구 경로를 선택하십시오. 복구 경로 자체가 정해지지 않았으면 미정 상태를 기록하십시오.

**증거:** 미충족 조건과 근거, 준비 상태 판정, 선택한 복구 경로 또는 미정 항목을 남기십시오.

## T-35. 프록시 장애 시 직접 v1 경로 복구

요구사항: [FR-31](../rollout/rollback-and-bypass.md), NFR-02

**대상 조건:** 프록시 자체가 요청을 처리하지 못하는 상태와 프록시 제어 경로에 의존하지 않는 기존 v1 직접 경로를 준비하십시오. 복구 목표 시간과 측정 경계를 확인하십시오.

1. 프록시 장애를 발생시키십시오.
2. 준비된 진입 경로에서 직접 v1 우회를 적용하십시오.
3. 실제 client 요청 경로와 응답 회복 시점을 확인하십시오.

**판정:** 실제 client 요청이 직접 v1 경로로 전환되고 정한 복구 목표를 충족해야 한다. DNS나 로드밸런서 설정 변경만으로 완료를 판정하지 마십시오. 기존 연결이 남은 범위도 확인하십시오.

**증거:** 장애 상태, 우회 조작·시각, client의 실제 요청 경로, 연결 잔존 여부와 복구 소요 시간을 남기십시오.

## T-36. HTTP 연결 배출과 내부 작업 배출·강제 종료

요구사항: [FR-14](../shadow/lifecycle-and-limits.md), [FR-22](../collection/async-storage.md), NFR-04

**대상 조건:** serving 완료 뒤 느린 shadow와 비교·저장 큐 작업이 남은 상태를 준비하십시오. 응답 전송 중인 요청도 별도 사례로 포함하십시오. 로드밸런서 등록 해제, 종료 신호, 종료 유예 만료와 재시작의 순서를 검증 환경의 종료 절차에 맞춰 기록하십시오.

1. 신규 요청 수락 중단 절차를 적용하십시오.
2. 종료 신호 이후 진행 HTTP 응답과 내부 shadow·비교·저장 작업의 종료를 각각 관측하십시오.
3. 유예 만료와 재시작 경계에서 남은 작업·이벤트·계측 상태를 확인하십시오.

**판정:** HTTP 연결 배출과 내부 작업 배출을 구분하십시오. 종료 처리는 내부 작업을 무한히 기다려서는 안 된다. 조기 종료된 응답과 유실 가능 구간을 보고하십시오. 강제 종료 전 수집하지 못한 counter나 마지막 이벤트를 확인할 수 없으면 완전한 계측으로 표시하지 마십시오.

**증거:** 종료 절차와 시각, 진행 응답·내부 작업 수, 유예 만료 상태, 저장 확인 결과, 재시작 경계의 유실·미확인 범위를 남기십시오.

## T-37. 대표·피크·큰 응답·cold start의 실제 부하

요구사항: [FR-30](../rollout/stages-and-gates.md), NFR-01, NFR-03, NFR-05, NFR-09

**대상 조건:** 대상 API의 대표·피크 도착률, 응답 크기 분포, cold start 조건과 사용자 오류·지연·자원·비용 기준을 확인하십시오. 전체 shadow 설정에서 실행 상한이 발동하는 사례도 포함하십시오.

1. 각 부하 조건을 실행하십시오.
2. 목표 도착률과 실제 프록시 도착률을 함께 측정하십시오.
3. 생성기 미발행 요청과 대상의 timeout·취소·미완료 요청을 구분하십시오.
4. 실제 실행량·완료율과 사용자·자원·비용 지표를 기준에 대조하십시오.

**판정:** 요청한 부하가 실제 도달한 범위에서만 용량을 판정하십시오. 표본율 1이어도 제한·취소·드롭으로 목표 실행량이나 완료율이 부족하면 full-load 검증 통과로 표시하지 마십시오. 정하지 않은 성능·비용 기준을 임의 수치로 대신하지 마십시오.

**증거:** 입력 분포, 목표·실제 도착률, 미발행 원인, 실제 시작·종료·오류 수, 사용자 지표·자원 사용량·비용 근거를 남기십시오.

1. worker·replica 수를 변경할 때 전체 shadow 예산이 어떻게 달라지는지 합산하십시오.

## T-39. 종료 시 잔존 v1 의존·직접 v2 계약·보존 기록

요구사항: [FR-32](../rollout/retirement.md), [FR-24](../collection/detail-sampling.md), NFR-08

**대상 조건:** 전환 대상의 전체 v2 serving이 주요 업무 주기와 피크의 품질·용량 기준을 충족하는지 확인하십시오. 등록 route 외에 미등록 API·배치·관리자 도구·내부 client·세션의 v1 의존을 조사하십시오. 직접 v2 경로와 보존 기한이 남은 관측 기록을 준비하십시오. v1 cold 상태의 복귀 목표, 복귀 가능 기간과 종료 후 서비스·데이터 복구 수단을 확인하십시오.

프록시 종료 뒤 남은 기록의 보존·만료 정리를 담당할 주체와 실행 방법을 확인하십시오.

1. 종료 범위 안에 남은 v1 호출자와 경로를 확인하십시오.
2. 신규 shadow 선택 중지와 기존 shadow 작업의 종료를 확인하십시오.
3. Shadow 종료 전후의 부하·cache·지연과 v2 단독 사용자 지표를 정한 기준에 대조하십시오.
4. v1 cold 상태에서 재가동·warm-up을 포함한 복귀 시간을 측정하십시오.
5. 직접 v2 호출의 인증·헤더·연결·오류 처리 계약과 관측 수단을 검증하십시오.
6. 복귀 가능 기간과 종료 후 서비스·데이터 복구 수단을 확인하십시오.
7. 목적별 보존 기한에 따라 관측 기록의 유지·정리 결과를 확인하십시오.
8. Shadow 종료, v1 사용 종료, 프록시 제거와 관측 기록 정리의 결과를 각각 기록하십시오.

**판정:** 잔존 의존이나 직접 호출 계약·관측의 미검증 사항을 남긴 채 전체 종료로 판정하지 마십시오. Shadow 종료 후 품질·부하, cold 상태 복귀 시간, 복귀 기간·수단의 기준이 미정이거나 근거가 부족하면 해당 조건에 의존하는 종료를 보류하십시오. 서비스 종료만을 이유로 기한이 남은 보존 대상을 삭제하지 마십시오. 기한이 도래한 데이터의 정리 결과를 별도로 확인하십시오. 각 종료 결과의 완료·실패·미확인을 구분하십시오.

**증거:** 전체 v2 serving의 업무 주기·피크 관측, 잔존 의존 목록, shadow 종료·v2 단독 부하 결과, cold 상태 복귀 목표·실측 시간, 직접 v2 호출·관측 결과, 복귀 기간·수단을 남기십시오. 목적별 보존 기한과 실제 정리 결과, 종료 뒤의 정리 책임과 실행 방법, 각 종료 결과와 판단의 제한 사항도 남기십시오.

## T-40. 업무별 비교 확장의 최소 범위와 회귀

요구사항: [FR-26](../comparison/normalization.md), NFR-08, NFR-10

**대상 조건:** 두 번째 API에 기본 정책으로 표현할 수 없는 비교 요구가 실제로 있는지 확인하십시오. 필요성이 확인된 경우에만 해당 API의 최소 확장 규칙과 기존 API의 회귀 입력을 준비하십시오.

1. 두 번째 API의 계약 입력에 확장 규칙을 적용하십시오.
2. 확장 결과를 두 번째 API의 계약과 대조하십시오.
3. 기존 API의 입력에 기존 정책을 적용하십시오.
4. 기존 API의 결과를 기존 계약과 대조하십시오.

**판정:** 확장은 확인된 업무 필요와 대상 경로에 한정되어야 한다. 두 번째 API의 요구를 충족하면서 기존 경로의 비교·공개 응답 계약을 바꾸어서는 안 된다. 확장이 필요하지 않은 경우 확장을 구현해야 할 필수 기능으로 취급하지 마십시오.

**증거:** 확장 필요 근거, 대상 API·정책 revision·규칙, 확장 결과와 기존 계약의 회귀 결과를 남기십시오.

## T-41. backend·비교 정책·데이터 문맥 변경과 증거 유효성

요구사항: [FR-21](../collection/event-model.md), [FR-28](../observability/coverage-and-analysis.md), [FR-30](../rollout/stages-and-gates.md), NFR-10

**대상 조건:** 프록시 설정 revision이 같은 상태의 backend rolling 배포를 준비하십시오. 비교 정책 변경과 필수 데이터 문맥 변경은 별도 사례로 구성하십시오.

1. 각 변경 중 요청이 실행된 실제 backend 배포 revision과 문맥을 확인하십시오.
2. 혼재 구간과 변경 후 구간을 구분하십시오.
3. 각 구간의 비교 결과를 별도로 집계하십시오.
4. 기존 gate 증거가 변경된 조건에도 유효한지 재평가하십시오.

**판정:** 실제 backend 배포 revision을 확인할 수 없으면 `unknown`을 기록해야 하며 프록시 설정 revision으로 대신해서는 안 된다. 서로 다른 조건의 구간을 동일 epoch로 무조건 합산하지 마십시오. 기존 gate 증거는 조건 변경에 맞춰 유효성을 다시 판단하십시오.

**증거:** 변경 시각, 확인 가능한 실제 배포 revision과 미확인 범위, 비교 정책·데이터 문맥, 구간 분리와 증거 재평가 결과를 남기십시오.

**증거:** 적용 deadline·timeout, pool 대기와 chunk 시각, 역할별 종료·정리 결과, 후속 요청의 연결 사용과 잔여 task 상태를 남기십시오.

## T-47. 내부 관측·단일 healthcheck·비공개 접근 검증

요구사항: [FR-07](../routing/http-forwarding.md), [FR-27](../observability/metrics.md), NFR-07, NFR-08

**대상 조건:** 사용자 API 전달 포트와 별도 loopback health listener를 준비하십시오. 요청 수락 준비·미준비 상태와 loopback이 아닌 접속 peer를 재현하는 사례를 준비하십시오. token 또는 전달 헤더로 loopback 접근을 주장하는 사례도 포함하십시오. 원문·인증 정보·예외의 비노출 검사에는 식별 가능한 합성 marker를 사용하십시오. 인터넷 직접 접근의 차단 여부는 검증 대상 배포 환경에서 확인하고, 해당 환경이 없으면 그 항목을 미실행으로 남기십시오.

1. health listener에 loopback이 아닌 바인드 주소를 지정한 설정의 거부 여부를 확인하십시오.
2. loopback에서 준비·미준비 상태의 `GET /healthcheck` 응답을 각각 확인하십시오.
3. 실제 접속 peer가 loopback이 아닌 사례의 접근 거부 여부를 확인하십시오.
4. 같은 사례에 token 또는 전달 헤더를 추가해도 접근이 허용되지 않는지 확인하십시오.
5. loopback에서 health listener의 `/metrics`, `/state`, `/health/live`, `/health/ready`가 404를 반환하는지 확인하십시오.
6. 메트릭·상태의 HTTP 조회를 활성화하는 설정이 없는지 확인하십시오.
7. 사용자 요청과 비교 사례를 실행한 뒤 내부 snapshot·상태 조회에서 counter·histogram·gauge와 실행 상태를 확인하십시오.
8. 합성 marker와 내부 공급자의 예외 사례에서 health 응답·서버 로그·표준 출력·표준 오류를 검사하십시오.
9. 사용자 API 전달 포트의 동작과 내부 계측의 집계 범위·재시작 경계를 확인하십시오.
10. 배포 환경에서 프록시 전달 포트의 인터넷 직접 접근이 차단되는지 확인하십시오.

**판정:** 별도 health listener는 loopback에만 바인딩해야 하며 실제 접속 peer도 loopback이어야 한다. token, 전달 헤더나 peer 검증 우회로 외부 접근을 허용해서는 안 된다. `GET /healthcheck`는 요청 수락 준비 상태에 따라 200 또는 503과 최소 준비 상태만 반환해야 한다. `/health/live`·`/health/ready` alias와 `/metrics`·`/state` 관측 HTTP endpoint, 이를 활성화하는 설정은 없어야 한다.

내부 계측·snapshot·상태 조회·비교·이벤트 수집은 계속 동작해야 한다. health 응답에는 route 목록·revision·메트릭·상세 설정을 포함해서는 안 된다. 합성 marker나 원문 예외를 health 응답과 로그에 노출해서는 안 된다. 신원 공급자의 예외는 backend 호출 없이 고정 503으로 종료해야 하며 정상적인 신원 키 누락과 구분해야 한다.

사용자 API 전달 포트는 health listener와 분리하고 기존 backend 전달 계약을 유지해야 한다. 같은 이름의 path에 대한 사용자 요청을 health 응답으로 가로채서는 안 된다. 배포 구성은 이 포트의 인터넷 직접 접근을 차단해야 한다. 문서나 로컬 설정만으로 실제 클라우드의 접근 차단을 검증했다고 판정해서는 안 된다.

내부 관측 결과는 실행 중인 대상과 명시한 수집 범위를 나타내야 한다. 메모리 메트릭의 재시작 초기화와 미수집 구간을 구분하십시오. `/healthcheck`의 성공을 backend 요청 성공이나 이벤트 저장 성공의 증거로 해석하지 마십시오.

**증거:** 바인드 주소별 설정 검증, 접속 peer별 접근 결과, 제거한 경로의 404 응답과 단일 healthcheck의 상태별 반환 필드를 남기십시오. 내부 지표·상태 변화, 집계 범위·재시작 경계, 사용자 요청과 backend 실행 결과를 기록하십시오. 합성 marker의 비노출 결과, 확인한 배포 환경과 인터넷 직접 접근 차단 증거 또는 미실행 상태를 함께 남기십시오.
