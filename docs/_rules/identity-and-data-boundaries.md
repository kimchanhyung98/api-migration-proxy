# 인증·권한과 데이터 동기화 책임

이 문서는 같은 논리 요청을 v1과 v2에서 실행할 때 보존해야 하는 권한 의미와 데이터 준비의 책임을 정의한다. API 개발자는 요청의 권한·업무 계약을 정의하고, 데이터 담당자는 데이터 준비 증거를 제공한다. 마이그레이션 담당자는 그 증거를 비교와 전환 판단에 사용한다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 입력 | 호출자의 token·tenant·scope, 신원을 검증하는 경계, v1/v2의 DB·스키마·데이터 최신성 관계와 각 요청의 외부 효과이다. |
| 확인할 결과 | 양쪽 실행의 권한 의미가 유지되는지, 결과를 비교할 데이터 조건이 성립하는지, shadow와 v1 복귀를 허용할 범위가 무엇인지 확인한다. |
| 금지 사항 | 응답을 일치시키기 위한 권한 확대를 해서는 안 된다. |
| 책임에서 제외하는 기능 | 읽기 프록시는 쓰기 동기화, 원자적 dual-write와 데이터 복구를 수행하지 않는다. 이러한 작업은 서비스·데이터 계층의 계약에 따라 수행한다. |

## 데이터·업무 책임 경계

아래 표에서 프록시의 책임은 관측과 판단에 필요한 문맥을 보존하는 범위이다. 문맥을 기록했다는 이유로 서비스·데이터 계층의 작업이 완료된 것으로 표시해서는 안 된다.

| v1/v2의 관계 | 프록시 책임 | 서비스·데이터 계층 책임 |
| --- | --- | --- |
| 같은 DB를 읽는다. | 요청 문맥을 보존하고 실행 결과와 지연을 비교한다. | 쿼리·스키마·권한의 호환성을 확인하고 공유 DB의 추가 부하를 관리한다. |
| 독립 DB를 읽는다. | 비교에 필요한 데이터 원천과 최신성 문맥을 기록한다. | 초기 적재, 변경분과 삭제의 반영, 처리 순서와 실패 복구를 수행한다. |
| v1에서 쓴 데이터를 v2에서 읽는다. | 읽기 결과를 관측하고 serving 전환 판단에 사용한다. | v2의 반영 시점과 필요한 read-after-write 조건을 충족한다. |
| v2 전용 데이터나 필드를 사용한다. | v1 복귀가 불가능한 사유를 전환 판단에 반영한다. | v1이 해석할 수 있는 표현, 변환과 복원 계약을 정의한다. |
| 외부 시스템을 호출한다. | Shadow 실행 여부와 실행 결과를 관측한다. | 외부 효과의 차단 방법, 격리된 실행 환경의 범위, quota와 중복 비용 계약을 정의한다. |

두 API를 순서대로 호출하고 양쪽의 성공을 확인해도 원자적 처리가 성립하는 것은 아니다. 한쪽만 성공하거나 timeout 뒤 실제 처리 여부를 확인하지 못할 수 있다.

## 쓰기 복제를 검토할 때 필요한 계약

초기 프록시 범위에는 쓰기 동기화를 추가하지 않는다. 쓰기 복제를 별도 범위로 검토할 경우 API 개발자와 데이터 담당자는 다음 항목을 정의해야 한다.

| 항목 | 정의할 내용 |
| --- | --- |
| 데이터 원천 | 어느 시스템의 기록을 authoritative source, 즉 정합성 판단의 기준 원천으로 사용할지 정한다. |
| 성공 확인 | 어떤 기록과 반영 상태를 충족해야 성공 ACK를 반환할지 정한다. |
| 작업 식별 | 재시도와 재생에서도 같은 업무 작업을 식별할 stable operation ID를 정한다. |
| 중복·순서 | 멱등성을 보장하는 범위와 작업 순서를 보존해야 하는 범위를 정한다. |
| 불완전한 결과 | 부분 성공, 실패와 timeout 후 처리 여부 미확인을 구분하고 각각의 복구 동작을 정한다. |
| 재처리 | 재시도·재생의 조건과 필요한 기록의 보존 기간을 정한다. |
| 복구 책임 | 결과 확인과 복구를 수행할 담당자를 정한다. |

환경, 저장소 또는 외부 제공자가 다르면 같은 idempotency key를 보내도 중복 방지 영역을 공유하지 않을 수 있다. 담당자는 key의 문자열 일치뿐 아니라 중복을 판단하는 저장 범위와 유효 기간을 확인해야 한다.

결제, 알림과 같이 외부 효과가 있는 요청은 효과의 차단·중복 방지 계약을 먼저 확인해야 한다. JSON 응답이 일치한다는 사실을 외부 효과가 안전하다는 증거로 사용해서는 안 된다.

## 비교·전환 전 데이터 준비 확인

이 절차의 대상은 비교 문맥을 설정하거나 serving 전환을 판단할 route이다. 데이터 담당자는 원천과 동기화 증거를 제공하고, API 개발자는 읽기·권한·업무 계약을 제공한다. 마이그레이션 담당자는 각 증거가 해당 route와 관측 구간을 포함하는지 확인한다.

1. **비교할 데이터 범위를 기록하십시오.** v1/v2의 authoritative source, 논리 데이터 범위와 데이터 세대의 관계를 기록하십시오.
2. **독립 저장소의 동기화 상태를 확인하십시오.** 확인 대상은 초기 적재 기준점, 변경분 checkpoint, 반영 지연, 미해결 실패와 삭제 반영 결과입니다.
3. **읽기 가시성 조건을 확인하십시오.** 확인 대상은 API 성공 시점, 조회 반영 시점, read-after-write 요구, 허용 시차와 업무 불변식입니다.
4. **읽기 가시성의 확인 결과를 기록하십시오.** 허용 시차 또는 업무 불변식을 위반했으면 그 결과를 전환 gate의 증거에 포함하십시오.
5. **데이터 검증의 범위를 확인하십시오.** 확인 대상은 범위별 개수, ID, 업무 필드와 삭제 표본입니다.
6. **검사하지 않은 데이터 범위를 기록하십시오.** 응답 표본의 일치는 전체 데이터의 무결성을 보장하지 않습니다.
7. **v1 복귀 조건을 확인하십시오.** 확인 대상은 v2의 쓰기·스키마에 대한 v1의 해석 가능성, 동기화 유지 기간과 로그 보존 기간입니다.
8. **확보한 문맥을 비교 판단에 연결하십시오.** [비교 가능 조건](../comparison/context-and-outcomes.md)을 적용하십시오.
9. **전환·복귀 증거를 해당 gate에 연결하십시오.** [단계와 gate](../rollout/stages-and-gates.md) 및 [복귀 절차](../rollout/rollback-and-bypass.md)의 조건을 적용하십시오.

각 단계에서 아래 조건이 발생하면 해당 분기를 적용하십시오.

| 확인 결과 | 담당자의 조치 |
| --- | --- |
| 원천·범위·세대 관계를 확인할 수 없다. | 문맥 불명으로 분류하십시오. 데이터 정합성 통과로 표시하지 마십시오. |
| 동기화 작업 worker의 종료만 확인했다. | 데이터 준비 완료로 표시하지 마십시오. 적재·변경분·삭제 반영의 증거를 확인하십시오. |
| 허용 시차 또는 업무 불변식을 위반했다. | 위반 결과를 전환 gate에 반영하십시오. |
| v1 프로세스의 생존만 확인했다. | 복귀 준비 완료로 표시하지 마십시오. 데이터·스키마·동기화·보존 조건의 증거를 확인하십시오. |
| 판단에 필요한 증거가 없다. | 증거가 없는 항목을 미확인으로 기록하십시오. |

위 순서는 증거를 정리하고 판독하는 순서이다. 적재·동기화 구현의 실행 순서를 정의하지 않는다. 데이터 준비가 완료되었다는 판단은 대상 범위의 계약과 증거에 근거해야 하며, 이 목록을 읽거나 값을 기록한 것만으로 완료되지 않는다.

다음 예외를 적용한다.

- 같은 DB를 사용해도 요청 시점, transaction 관점과 배포된 스키마가 다를 수 있다. 저장소가 같다는 이유로 해당 문맥 확인을 생략해서는 안 된다.
- 독립 DB의 내부 checkpoint는 서로 다른 단위를 사용할 수 있다. 같은 원본 기준과 의미임을 확인하기 전에는 숫자 크기나 일치 여부로 동등성을 판단해서는 안 된다.
- 프록시는 준비 상태와 문맥을 비교·전환 판단에 사용한다. 이 절차를 프록시가 데이터 동기화 엔진을 제공한다는 뜻으로 해석해서는 안 된다.

## 접근·인증·본문 보호

아래 기준은 제품 요구사항이며, 현재 구현이나 배포 구성이 이를 충족한다는 증거는 아니다. 각 항목은 별도의 책임 경계이다. 한 항목을 충족했다는 이유로 다른 항목을 충족한 것으로 판단해서는 안 된다.

| 경계 | 적용할 요구사항 | 확인할 대상 |
| --- | --- | --- |
| Backend 목적지 | 운영자가 등록한 backend로 목적지를 제한해야 한다. 요청 URL이나 header로 임의 호스트를 지정하도록 허용해서는 안 된다. | 등록된 목적지와 실제 전달 대상이다. |
| 호출자 신원 | 호출자 신원을 검증할 위치와 신뢰할 forwarded header를 정의해야 한다. 인증 담당 위치는 기존 서비스 구조에 맞춰 결정한다. | 신원 검증 주체와 신뢰 경계이다. |
| v1/v2 권한 의미 | v1 token을 v2에 전달할 때 audience, scope와 tenant의 의미가 유지되는지 확인해야 한다. 응답을 일치시키기 위해 권한을 확대해서는 안 된다. | 각 backend가 실제 허용하는 대상과 작업 범위이다. |
| Backend 연결 | 인증서 검증을 유지해야 한다. Credential은 기존 비밀 관리 방식으로 공급해야 한다. | 인증서 검증 설정과 credential의 공급 경로이다. |
| 저장·조회 | 저장소 계정, 조회 권한과 요청 실행 권한을 구분하고 각각 필요한 범위만 부여해야 한다. | 저장·조회 가능한 route와 데이터 범위이다. |
| 관측 데이터 | 일반 로그, trace, exception과 diff에도 수집 정책을 적용해야 한다. 허용되지 않은 원문과 인증 정보를 노출해서는 안 된다. | 저장 이벤트뿐 아니라 관측 데이터가 나가는 모든 해당 경로이다. |
| 본문 처리 | 압축 해제, JSON 파싱과 마스킹에 자원 제한을 적용해야 한다. 실패한 처리와 드롭 사유를 관측에서 구분해야 한다. | 각 처리의 한도, 실패 상태와 기록한 사유이다. |

이 요구사항의 적용 범위는 프록시가 처리하는 요청과 관측 데이터의 경계이다. 별도 보안 플랫폼이나 권한 관리 제품의 구축을 요구하는 것은 아니다.

### 신원 공급 결과와 예외 처리

`identity_provider` 등 내부 공급자가 예외를 발생시켜도 원문 traceback이나 자유 형식 예외 메시지를 출력해서는 안 된다. 예외 메시지에 신원, 인증 정보나 요청 원문이 포함될 수 있으므로 진단에는 미리 정한 고정 문구만 기록해야 한다.

신원 공급자가 예외로 실패하면 v1과 v2 어느 backend도 호출하지 않고, 예외 내용을 포함하지 않는 고정 HTTP 503 응답으로 요청을 종료해야 한다. 공급자가 정상적으로 반환했지만 serving 배정에 필요한 신원 키가 없는 경우에는 v1 serving으로 배정하고 shadow를 실행하지 않아야 한다. 신원 키의 정상적인 누락을 공급자의 예외 실패와 같은 상태로 처리해서는 안 된다.

### 관측 데이터의 처리·조회·전송 경계

비교 판정, 집계와 데이터 보호는 프록시 내부에서 수행해야 한다. 내부 메모리의 counter와 histogram은 항상 계측해야 한다. 메트릭 snapshot과 `observation_status()`는 프로세스 내부의 상태 확인에 사용한다.

프록시는 메트릭·상세 상태의 HTTP 조회와 이를 활성화하는 설정을 제공하지 않는다. 외부 수집기·SaaS로 보내는 SDK나 exporter도 연결하지 않는다. 선택한 이벤트 저장소에 기록하는 기능과 외부 관측 연동을 구분해야 한다.

Health는 전용 loopback listener의 `GET /healthcheck` 하나만 제공해야 한다. 요청 수용 가능 상태이면 200과 `{"ready":true}`, 그렇지 않으면 503과 `{"ready":false}`만 반환해야 한다. Health 경로의 별칭이나 route·설정·메트릭을 포함한 상세 응답을 제공해서는 안 된다.

Health listener의 바인드 주소와 실제 접속 peer는 모두 loopback으로 제한해야 한다. 인증 token이 있다는 이유로 외부 바인드나 외부 peer를 허용해서는 안 된다. 요청 header의 주소를 실제 접속 peer 대신 사용해서도 안 된다.

메트릭의 route와 트래픽 정보도 민감정보로 취급해야 한다. summary의 허용 필드에도 요청·route·전환을 식별하거나 서로 연결할 수 있는 정보가 있으므로 익명 데이터로 간주해서는 안 된다. 내부 집계값과 저장 이벤트를 조회하거나 별도로 반출할 때에는 해당 목적의 접근 범위와 데이터 보호 정책을 적용해야 한다.

요청·응답의 원문 body, header, cookie, query, raw URL과 자유 형식 예외 메시지를 기본 로그에 기록해서는 안 된다. 이 제한은 애플리케이션 로그뿐 아니라 서버 로그와 오류 출력에도 적용해야 한다. stdout도 배포 환경의 logging driver를 통해 외부로 전송될 수 있으므로, stdout 출력을 외부 비전송의 근거로 사용해서는 안 된다.

현재 SQLite 구현은 수집 대상으로 선택한 shadow 비교 이벤트를 저장한다. 이벤트에 개별 실행의 status와 latency가 포함되어도 SQLite는 메트릭 집계 DB가 아니며, 저장 이벤트 수는 전체 요청의 분모가 아니다. 저장 표본에서 계산한 값을 전체 요청의 집계로 표시해서는 안 된다.

[Prometheus 보안 지침](https://prometheus.io/docs/operating/security/)은 계측 애플리케이션을 포함한 관측 HTTP endpoint를 공개 인터넷에 노출하지 않도록 안내한다. [OpenTelemetry의 민감정보 처리 지침](https://opentelemetry.io/docs/security/handling-sensitive-data/)은 관측 도구가 업무상 민감정보를 스스로 판별하지 못하며, 수집·처리하는 주체가 필요한 정보만 수집할 책임이 있음을 설명한다. 관측 HTTP 조회를 제공하지 않고 loopback health만 허용하는 것은 이 제품의 계약이다.
