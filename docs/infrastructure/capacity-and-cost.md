## 실행량과 비용 모델

- 적용 범위: 복제 가능한 요청만 있는 구간
- Q: 해당 구간 입력 QPS
- p: 실제 v2 serving 요청 비율
- s: serving 버전에 관계없이 동일하게 적용하는 반대편 shadow 선택 비율
- 가정: 재시도·제한·취소 없음, 양쪽 실행 각각 최대 한 번

```text
v1 QPS = Q × ((1 - p) + p × s)
v2 QPS = Q × (p + (1 - p) × s)
전체 backend QPS = Q × (1 + s)
```

- 합성 예시: Q=100, p=0.25, s=0.5 → v1 87.5 QPS, v2 62.5 QPS, 합계 150 QPS
- s=1인 경우: p와 관계없이 양쪽 모두 100 QPS, 합계 200 QPS
- 수식의 용도: 실행량 추정; 성능 예측·실측 증거 대체 불가

- 전체 트래픽 확장 시 Q는 전체 입력 QPS, f는 그중 복제 가능한 요청 비율로 정의
- 같은 가정의 전체 실행량: `Q × (1 + f × s)`
- 위 v1/v2별 수식의 전체 트래픽 적용 시 주의: 복제 적격성에 따른 serving 분포 차이 고려 필요
- 실측 대상: backend 오류·client 취소·연결 재시도·공유 의존 부하 포함
- 사용자 cohort 비율을 실제 요청 비율 p로 대입 금지
- 논리 요청 수·프록시 backend 호출 수·backend 내부 DB/외부 호출 수의 별도 계측

- shadow 선택 표본의 예상 유입량: `Q × f × s`
- 선택 유입량과 실제 dispatch·비교 가능·저장 완료량의 구분
- 실행 생략·timeout·비교 불가·저장 실패도 관측 대상에 포함; 유실·상세 표본·이벤트 크기에 따른 실제 적재량 차이 기록

```text
요약 저장량 = 저장된 이벤트 수/초 × 평균 요약 bytes × 보존 초
상세 저장량 = 상세 표본 수/초 × 평균 상세 bytes × 보존 초
총 저장 여유 = 요약 + 상세 + 인덱스 + 저장소 로그·복제·백업 + 운영 여유
추가 비용 = 프록시 실행 + 추가 backend 실행 + 공유 의존 부하
          + 네트워크 전송 + 관측 저장·조회·삭제 + 모니터링
```

- 검증 기간의 비용: 양쪽 실행·관측에 따른 증가 가능
- v1 실행·리소스 축소 시점: [복귀 가능 기간](../rollout/rollback-and-bypass.md)과 함께 결정
- 실행량 감소와 실제 비용 감소의 구분: 고정 용량·저장·보존·기존 약정 비용까지 확인

## cache·공유 의존·실험 조건

- shadow의 공유 자원 영향: backend cache·DB connection·외부 API quota·rate limit·로그·메트릭 소비
- 가능하면 계측에서 shadow 실행 구분
- shadow 표식에 따른 업무 처리 변경 시 비교 조건 차이 기록; 계측 편의를 위한 의미 변경 금지
- 공유 cache의 선행 실행으로 hit 비율·지연이 인위적으로 개선되거나 공유 DB·quota 부하로 양쪽 backend 지연과 사용자 응답이 함께 악화될 수 있음. 공유 자원·cache 조건을 기록하고 같은 대표 부하의 shadow 실행·중지 및 v2 단독 구간을 확인; v1을 독립 대조군으로 간주하거나 양쪽 지연 차이를 신규 구현만의 효과로 단정 금지. [Google SRE의 의존성 격리·traffic teeing](https://sre.google/workbook/canarying-releases/)

- 프록시 자체 응답 cache: MVP 제외
- 기존 cache 계층의 key·인증·Vary 의미 보존 검증
- warm 상태 성공과 cold start·배포·피크 상태 보장의 구분
- v1 shadow 중지 후 cold 상태의 복귀 시간 재평가

## 용량 증거의 조건

| 검증 구간 | 필요한 조건 | 해석 제한 |
| --- | --- | --- |
| 프록시 추가 영향 | 같은 대표 부하의 v1 직접 경로와 프록시 v1 통과 비교 | 서로 다른 트래픽·시간대 결과의 단순 차감 금지 |
| 전체 shadow 목표 | 설정 비율 외 실제 dispatch·종료·timeout·cancel·drop, 대표 route·응답 크기별 분포 확인 | 상한으로 실행이 감소한 기간의 전체 부하 통과 판정 금지 |
| v2 전체 serving | v2의 목표 QPS·주요 업무 주기·공유 의존 부하 확인 | 소수 shadow 표본만으로 전체 처리 용량 보장 금지 |
| replica·worker 변경 | 인스턴스 전체 한도 × 최대 replica, 프로세스별 연결 pool·내부 큐·저장 유입량 합산 확인 | 프로세스별 상한을 인스턴스 또는 서비스 전체 상한으로 간주 금지 |
| shadow 종료 | v2 단독 serving 지표, v1 cold 상태의 재가동·warm-up 시간 확인 | shadow 실행 감소와 복귀 준비 유지의 동일시 금지 |

- 전체 실행 한도 `N×L`의 L은 인스턴스 전체 한도; 프로세스마다 독립 limiter를 두면 해당 프로세스 한도를 합산해 L 산정
- HTTP·DB pool·내부 큐도 프로세스별로 생성되는지 확인하고 동일 인스턴스 내 총량과 최대 replica에서의 총량을 각각 검증
