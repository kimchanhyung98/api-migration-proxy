# 실행 용량·공유 부하·수집 비용

이 문서는 shadow와 관측이 추가하는 backend 실행량, 메모리, 네트워크, 저장 비용의 산정 기준을 정의한다. 운영 담당자는 대표 요청 분포뿐 아니라 피크 부하와 cache가 준비되지 않은 cold 상태에서도 자원·비용 예산을 검증해야 한다. serving, shadow, cohort의 의미는 [공통 용어](../_rules/glossary.md)를 따른다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 실제 입력 QPS, 복제 적격 비율, 실제 serving 분포, shadow 표본율, 이벤트 크기, 보존 기간, replica 수, worker 프로세스 수를 확보해야 한다. |
| 결과·출력 | 전환 단계별 예상 실행량·저장량과 실제로 측정한 자원 사용량·비용을 기록한다. |
| 실패·제한 | 아래 실행량 수식은 재시도, 보호 상한에 따른 실행 생략, 취소, backend 내부의 간접 호출 부하를 포함하지 않는다. cohort 배정 비율을 실제 QPS 비율과 같다고 가정해서는 안 된다. |

## 실행량과 비용 모델

### 복제 적격 요청 구간의 backend 실행량

아래 첫 수식은 입력 요청 전체가 복제 가능한 구간에만 적용한다. QPS는 초당 요청 수를 뜻한다. 같은 관측 구간에서 다음 값을 정의한다.

| 기호 | 정의 |
| --- | --- |
| `Q` | 복제 가능한 해당 구간의 입력 QPS이다. backend 내부 호출 수가 아니다. |
| `p` | 해당 구간에서 실제로 v2 serving에 배정된 요청의 비율이다. 사용자나 테넌트 수의 비율이 아니다. |
| `s` | serving이 v1인지 v2인지와 관계없이 동일하게 적용하는 반대편 shadow 선택 비율이다. |

수식은 재시도, 실행 제한, 취소가 없고, 한 논리 요청에 대해 각 backend를 최대 한 번 실행한다고 가정한다. 따라서 serving 한 번에 더해 선택된 요청에서만 반대편 shadow 한 번이 추가된다.

```text
v1 QPS = Q × ((1 - p) + p × s)
v2 QPS = Q × (p + (1 - p) × s)
전체 backend QPS = Q × (1 + s)
```

설명용 합성 예시에서 `Q=100`, `p=0.25`, `s=0.5`이면 v1은 87.5 QPS, v2는 62.5 QPS, 합계는 150 QPS이다. 같은 예시의 `Q=100`을 유지하고 `s=1`로 바꾸면 `p`와 관계없이 양쪽이 각각 100 QPS, 합계가 200 QPS이다. 이 수치는 운영 기본값이 아니다.

이 수식은 가정이 성립하는 구간의 실행량을 추정하는 모델이다. 응답 지연이나 최대 처리 성능을 예측하는 식으로 사용하거나 실측 증거를 대체해서는 안 된다.

### 전체 트래픽으로 확장하는 경우

전체 트래픽을 계산할 때는 `Q`를 전체 입력 QPS로 다시 정의하고, `f`를 그중 복제 가능한 요청의 비율로 정의한다. 재시도·실행 제한·취소가 없다는 같은 가정 아래 전체 backend 실행량은 `Q × (1 + f × s)`이다.

전체 트래픽의 v1/v2별 실행량을 계산할 때는 복제 적격 비율과 적격·부적격 요청 각각의 serving 분포를 반영해야 한다. 앞의 v1/v2별 수식에서 `Q`와 `p`는 복제 적격 구간의 값이다. 복제 부적격 요청이 포함되면 전체 입력 QPS와 전체 serving 비율을 그 자리에 그대로 대입해서는 안 된다. 사용자 cohort의 배정 비율도 실제 요청 비율인 `p`로 대입해서는 안 된다.

shadow 선택 표본의 예상 유입량은 `Q × f × s`이다. 이 값은 선택된 요청 수의 추정치이며 실제 shadow 실행 시작량, 비교 가능량, 저장 완료량과 같지 않을 수 있다. 실행 생략, timeout, 비교 불가, 저장 실패도 관측해야 한다. 유실, 상세 표본, 이벤트 크기로 실제 적재량이 추정과 달라진 경우 그 원인을 기록해야 한다.

실측에서는 backend 오류, client 취소, 연결 재시도, 공유 의존 자원의 부하를 포함해야 한다. 다음 세 수량은 별도로 계측해야 한다.

- 호출자가 보낸 논리 요청 수를 계측한다.
- 프록시가 시작한 backend 호출 수를 계측한다.
- backend 내부에서 발생한 DB·외부 API 호출 수를 해당 의존 자원의 계측으로 확인한다.

### 저장량과 추가 비용

저장량은 실제로 저장된 이벤트의 유입률, 평균 크기, 보존 기간을 사용하여 추정해야 한다. 요약과 상세의 크기는 bytes, 보존 기간은 초, 유입률은 초당 건수를 사용한다. 요약과 상세의 보존 기간이 다르면 각각의 기간을 사용해야 한다.

```text
요약 저장량 = 저장된 이벤트 수/초 × 평균 요약 bytes × 보존 초
상세 저장량 = 상세 표본 수/초 × 평균 상세 bytes × 보존 초
총 저장 여유 = 요약 + 상세 + 인덱스 + 저장소 로그·복제·백업 + 운영 여유
추가 비용 = 프록시 실행 + 추가 backend 실행 + 공유 의존 부하
          + 네트워크 전송 + 관측 저장·조회·삭제 + 모니터링
```

이 식의 상세 표본 수는 실제 상세 데이터가 저장된 표본의 유입률이다. 상세 표본으로 선택했지만 마스킹 또는 저장에 실패한 요청을 저장 완료량에 포함해서는 안 된다. `총 저장 여유`는 빈 공간만을 뜻하지 않으며, 보존할 데이터와 인덱스·로그·복제·백업을 수용하고 운영 여유까지 확보하는 데 필요한 총량을 뜻한다.

검증 기간에는 양쪽 실행과 관측으로 비용이 증가할 수 있다. v1 실행량이나 리소스를 줄이는 시점은 [복귀 가능 기간](../rollout/rollback-and-bypass.md#복귀-가능-기간)과 함께 결정해야 한다. 실행량이 줄어도 고정 용량, 저장·보존, 기존 약정 비용이 유지될 수 있으므로 실행량 감소를 실제 비용 감소로 간주해서는 안 된다.

## cache·공유 의존·실험 조건

shadow는 backend cache, DB 연결, 외부 API quota, rate limit, 로그와 메트릭 수집 자원을 소비할 수 있다. 기존 계측에서 구분할 수 있으면 shadow 실행을 별도로 식별하는 것을 권장한다. 이 구분은 shadow의 추가 부하를 확인하기 위한 것이다.

shadow 표식 때문에 backend의 업무 처리가 달라지면 그 차이를 비교 조건에 기록해야 한다. 계측을 편하게 하기 위해 업무 의미를 바꿔서는 안 된다.

공유 cache를 먼저 채우는 실행 때문에 다른 요청의 cache hit 비율과 지연이 인위적으로 개선될 수 있다. 반대로 공유 DB나 quota의 추가 부하 때문에 양쪽 backend 지연과 사용자 응답이 함께 악화될 수 있다. 운영 담당자는 공유 자원과 cache 조건을 기록해야 한다. 같은 대표 부하에서 shadow 실행 구간, shadow 중지 구간, v2 단독 serving 구간을 구분하여 확인해야 한다. v1을 독립적인 대조군으로 간주하거나 양쪽 지연 차이를 신규 구현만의 효과로 단정해서는 안 된다. 이 해석 제한은 [Google SRE의 의존성 격리·traffic teeing](https://sre.google/workbook/canarying-releases/)과 관련된다.

프록시 자체의 응답 cache는 MVP에 포함하지 않는다. 기존 cache 계층을 통과하는 경우에는 cache key, 인증, `Vary`의 의미가 유지되는지 검증해야 한다.

cache와 연결이 준비된 warm 상태에서의 성공은 cold start, 배포 직후, 피크 부하에서도 같은 결과를 보장하지 않는다. v1 shadow를 중지한 뒤에는 v1이 cold 상태가 되었을 때의 재가동과 warm-up을 포함하여 복귀 시간을 다시 평가해야 한다.

## 용량 증거의 조건

각 행은 검증해야 할 구간과 결과의 해석 조건을 나타낸다. 행 순서가 모든 실험의 직렬 실행 순서를 뜻하지는 않는다. 전환 단계의 선행 조건은 [전환 단계와 승격 판단](../rollout/stages-and-gates.md)을 따른다.

| 검증 구간 | 필요한 조건 | 해석 제한 |
| --- | --- | --- |
| 프록시 추가 영향 | 같은 대표 부하에서 v1 직접 경로와 프록시를 거친 v1 경로를 비교해야 한다. | 서로 다른 트래픽이나 시간대의 결과를 단순 차감하여 프록시의 추가 지연으로 계산해서는 안 된다. |
| 전체 shadow 목표 | 설정 비율뿐 아니라 실제 dispatch, 종료, timeout, cancel, drop과 대표 route·응답 크기별 분포를 확인해야 한다. | 보호 상한 때문에 실행이 줄어든 기간을 전체 목표 부하 통과로 판정해서는 안 된다. |
| v2 전체 serving | v2의 목표 QPS, 주요 업무 주기, 공유 의존 부하를 확인해야 한다. | 소수 shadow 표본만으로 전체 사용자 요청의 처리 용량이 확보되었다고 판단해서는 안 된다. |
| replica·worker 변경 | 인스턴스 전체 한도와 최대 replica 수를 확인해야 한다. 프로세스별 연결 pool·내부 큐·저장 유입량은 합산해야 한다. | 프로세스별 상한을 인스턴스 또는 서비스 전체의 상한으로 간주해서는 안 된다. |
| shadow 종료 | v2 단독 serving 지표와 v1의 cold 상태 재가동·warm-up 시간을 확인해야 한다. | shadow 실행이 감소했다는 사실만으로 v1 복귀 준비가 유지된다고 판단해서는 안 된다. |

전체 실행 한도 `N×L`에서 `N`은 인스턴스 수이고 `L`은 인스턴스 전체 한도이다. 프로세스마다 독립 limiter를 사용하는 경우에는 해당 인스턴스의 프로세스별 한도를 합산하여 `L`을 산정해야 한다. 서비스 전체 상한을 검토할 때는 최대 replica 수를 적용해야 한다.

HTTP·DB 연결 pool과 내부 큐도 프로세스별로 생성되는지 확인해야 한다. 독립적으로 생성된다면 같은 인스턴스 안의 총량과 최대 replica에서의 서비스 총량을 각각 검증해야 한다. 같은 계측 값을 중복 합산하거나 일부 worker를 누락한 값을 전체 용량으로 제시해서는 안 된다.

용량과 비용의 판단 절차는 운영 담당자가 수행한다. 3~4단계에는 필수 선후관계가 없다. 5단계 전에 추정값과 실측값을 모두 확보하십시오.

1. 검증할 전환 단계와 위 표의 해당 구간을 정하십시오.
2. 해당 구간의 실제 입력 분포와 수식의 가정이 일치하는지 확인하십시오.

   - 일치하지 않는 항목은 추정의 제한으로 기록하십시오.

3. 단계별 예상 실행량과 저장량을 계산하십시오.
4. 같은 부하 조건의 자원 사용량, 완료율, 비용 측정값을 확보하십시오.
5. 추정값과 실제 측정값을 비교하십시오.
6. 측정 결과를 대상 API의 자원·비용 예산과 대조하십시오.

   - 예산을 초과하면 해당 부하 조건을 충족한 것으로 판정하지 마십시오.

7. 검증한 부하 범위와 남은 미확인 조건을 기록하십시오.

   - 운영 목표값이나 필요한 측정값이 없으면 충족 여부를 `unknown`으로 남기십시오.

## 검증 기준

실행 증폭, 수집 비용, 공유 의존 영향은 [T-27, T-37, T-38](../validation/test-catalog.md)의 관련 시나리오로 확인해야 한다. 수식에 의한 추정값과 실제 측정값은 검증 결과에서 구분해야 한다.
