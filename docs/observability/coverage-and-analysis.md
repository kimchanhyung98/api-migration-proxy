# 비교 커버리지와 실험 분석

비교 커버리지는 복제 적격 요청 중 실제로 비교 판정까지 완료한 요청의 범위다. 선택·실행·종료·비교·저장 단계의 수를 각각 유지해야 하며, 성공한 일부 비교 사례만으로 전체 전환의 안전성을 판정해서는 안 된다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 같은 route, 같은 관측 epoch, 같은 요청 시작 구간에 속한 E/S/D/T/C/M/X/W와 실패·유실·비교 문맥 분류를 사용한다. |
| 결과·출력 | 비교 범위, 비교 가능한 응답 안의 조건부 차이율, 저장 완료율을 제공한다. 수치를 해석할 수 없는 경우에는 데이터 없음과 관측 미확인을 구분한다. |
| 실패·제한 | 구간 종료 시점에 진행 중인 작업을 최종 유실로 처리해서는 안 된다. 서로 다른 epoch나 응답 분류의 표본을 조건 설명 없이 혼합해서는 안 된다. |

## 분모 정의

집계 대상은 route, 관측 epoch, 요청 시작 구간의 세 조건이 모두 같은 요청 집단이어야 한다. [Epoch](../_rules/glossary.md)는 설정·비교 정책·backend 배포·데이터 문맥·실험 부하 조건이 같은 것으로 해석할 수 있는 구간이다. 이 문서의 요청 시작 집단은 serving 배정에 사용하는 사용자 cohort와 구분한다.

요청 시작 구간은 시작 시각을 포함하고 종료 시각을 제외하는 `[시작, 종료)`로 정의한다. 종료 시각 이후에 비교나 저장이 완료되어도 해당 요청의 결과는 원래 요청 시작 집단에 속한다. 구간의 시각이 끝났다는 이유만으로 잔여 요청의 유실을 확정해서는 안 된다.

| 기호 | 포함 조건 |
| --- | --- |
| E | 등록된 route이고 전환이 활성화되어 있으며, 효과·권한·입력 의미에 관한 복제 적격성을 통과하고 필요한 cohort 키가 누락되지 않은 요청 수다. 네 조건을 모두 충족해야 한다. |
| S | E 중 shadow 표본으로 선택된 요청 수다. |
| D | S 중 반대편 backend의 요청 실행이 실제 시작된 수다. |
| T | D 중 양쪽 backend 실행이 모두 종료된 수다. 성공뿐 아니라 실패·timeout·취소로 끝난 실행도 포함한다. |
| C | T 중 비교 조건을 충족하여 `matched` 또는 `different`로 판정된 수다. |
| M | C 중 `matched`로 판정된 수다. |
| X | C 중 `different`로 판정된 수다. |
| W | S에 해당하는 비교 이벤트 중 저장이 확인된 고유 이벤트 수다. 같은 event ID를 재시도한 횟수는 포함하지 않는다. |

다음 포함·제외 규칙을 적용해야 한다.

- 전환이 비활성인 요청, 지원 범위 밖의 요청, 복제 부적격 요청 또는 필요한 cohort 키가 누락된 요청은 E에서 제외해야 한다. 해당 요청을 전체 요청 지표와 shadow 선택 판정 지표에서도 제거해서는 안 된다.
- Shadow 중지 상태이거나 표본 비율이 0이어도 적격 요청은 E에 유지해야 한다. 이 조건에서는 신규 S가 증가하지 않는다.
- 표본 선택 후 슬롯 부족, 크기 상한 또는 종료 제한으로 실행하지 못한 요청은 S에 유지하고 D에서는 제외해야 한다.
- T를 증가시키려면 양쪽 실행이 모두 끝나야 한다. Shadow가 먼저 timeout으로 끝났더라도 serving이 실행 중이면 T가 아니다.
- W에는 비교 가능한 응답뿐 아니라 실행 실패·비실행 결과의 이벤트도 포함할 수 있다. W를 C의 부분집합으로 가정해서는 안 된다.

관측 유실 없이 처리가 끝난 고정 요청 집단에서는 다음 관계가 모두 성립해야 한다.

- `E ≥ S ≥ D ≥ T ≥ C`
- `C = M + X`
- `0 ≤ W ≤ S`

계측 또는 저장 확인 경로가 유실되어 관계를 확인할 수 없으면 미확인으로 표시해야 한다. 관계에 맞추기 위해 수치를 강제로 보정해서는 안 된다. 미확인을 0으로 대체해서는 안 된다.

### 집계 출처와 시각 경계

| 집계 | 출처·갱신 지점 | 지켜야 할 제한 |
| --- | --- | --- |
| E·S·D·T | 프록시의 적격 판정, 표본 선택, 실행 시작, 양쪽 실행 종료 지점에서 각각 갱신한다. | 이벤트 저장 성공 여부와 독립적으로 계측해야 한다. 프로세스·계측 경로 유실로 누락될 수 있다. |
| C·M·X | 비교 판정이 끝난 지점에서 갱신한다. | 비교 큐에서 드롭되어 판정하지 못한 요청은 포함하지 않는다. 저장된 상세 표본에서 역산해서는 안 된다. |
| W | 고유 event ID의 저장 ACK 또는 해당 ID의 저장소 고유 행 조회로 확인한다. | ACK 미확인, 저장 지연, 보존 만료와 중복 재시도의 영향을 구분해야 한다. |

런타임 counter는 각 단계가 처리된 시각에 증가한다. 따라서 같은 벽시계 구간에서 얻은 E·S·D·T·C·W의 증가량이 모두 같은 요청 시작 집단을 나타낸다고 가정해서는 안 된다. 실시간 비율에는 이전 구간의 잔여 작업과 현재 진행 중인 작업이 포함될 수 있으므로 잠정값임을 표시해야 한다.

고정 구간을 검증하는 담당자는 다음 순서로 집계하십시오.

1. 분석할 route, epoch와 요청 시작 구간을 정하십시오.
2. 설정·배포·문맥·부하 조건이 다르면 분석 구간을 분리하십시오.
3. 구간 시작 전에 진행 중이던 작업은 새 요청 시작 집단에서 제외하십시오.
4. 종료 시각 전에 시작했지만 끝나지 않은 요청은 해당 집단의 잔여 작업으로 유지하십시오.
5. 집계 대상 요청의 실행·비교·저장 상태를 추적하십시오.
6. 처리가 끝난 선택 요청의 저장 결과를 저장 확인, 확정 드롭 또는 ACK 미확인으로 분류하십시오.
7. ACK가 미확인이면 같은 event ID의 저장 여부를 재확인하십시오.
8. 저장을 확인한 고유 이벤트만 W에 반영하십시오.
9. 요청 시작 구간이 종료되고 잔여 작업의 상태가 정리됐으면 구간을 마감하십시오.
10. ACK 또는 계측 경로의 완전성을 확인하지 못했으면 집계의 완전성을 미확인으로 기록하십시오.
11. 분모 관계와 누락 사유를 확인하십시오.
12. 완전성 확인 결과에 따라 아래 비율을 해석하십시오.

저장소 고유 행으로 저장 여부를 확인하는 경우에는 해당 기록의 보존 만료 전에 조회해야 한다. ACK 미확인을 저장 실패 확정으로 처리해서는 안 된다. 원래 요청 집단을 확인할 수 없으면 정확한 분모 검증을 완료했다고 기록해서는 안 된다.

DB에 남아 있는 이벤트만으로 유실된 E·S를 복원해서는 안 된다. Exporter 재시작, 중복 수집 또는 프로세스 강제 종료가 있었다면 counter와 저장소 건수의 불일치 원인을 조사하고 완전성을 확인하지 못한 구간을 표시해야 한다.

운영 환경의 집계 방식과 허용 유실 수준은 미정이다. 분석 구간, 허용 지연, 재시작 빈도와 기존 모니터링 기능을 확인한 뒤 결정해야 한다. 이 결정이 없으면 실제 구간의 수집 완전성이 운영 기준을 충족한다고 판정할 수 없다.

### 비율과 상태 해석

| 지표 | 계산 | 해석 |
| --- | --- | --- |
| shadow 선택률 | S / E | 적격 요청 중 선택된 표본의 비율이다. |
| shadow 실제 시작률 | D / S | 선택된 요청 중 반대편 실행을 시작한 비율이다. |
| 선택 표본 비교 완료율 | C / S | 선택된 요청 중 비교 판정을 완료한 비율이다. |
| 전체 적격 비교 범위 | C / E | 전체 적격 요청 중 비교 판정을 완료한 비율이다. |
| 조건부 차이율 | X / C | 비교 가능한 응답 쌍 안에서 차이가 발견된 비율이다. |
| 저장 완료율 | W / S | 선택된 요청 중 요약 이벤트의 저장이 확인된 비율이다. |
| 실제 v2 배정 요청 비율 | v2 serving 배정 요청 / 전환 대상 요청 | 실제 요청 수에 따른 배정 분포다. 사용자 cohort의 비율과 같다고 가정해서는 안 된다. |

비율을 표시할 때는 먼저 계측 완전성을 확인해야 한다. 완전성이 미확인이면 분모 값이나 비교 종료 여부와 관계없이 미확인을 우선 적용해야 한다. 그 밖의 조건은 다음과 같이 구분한다.

| 조건 | 표시와 판단 |
| --- | --- |
| 분자·분모 또는 계측 완전성을 확인하지 못함 | `미확인`으로 표시해야 한다. 비율을 0으로 표시해서는 안 된다. |
| 비교 실행 구간이며 완전성을 확인한 분모가 0임 | `데이터 없음`으로 표시해야 한다. 오류가 없거나 비교가 통과했다는 증거로 사용해서는 안 된다. |
| 비교를 의도적으로 종료했고 관련 분모가 0임 | 계획된 비교 종료로 표시해야 한다. 관측 장애나 신규 비교 통과로 해석해서는 안 된다. |
| 분모가 0보다 크지만 해당 요청 집단이 아직 마감되지 않음 | 계산값은 잠정 관측치로 표시해야 한다. 마감된 구간의 최종 완료율과 구분해야 한다. |
| 분모가 0보다 크고 해당 요청 집단이 마감됐으며 완전성이 확인됨 | 해당 집단의 확정 비율로 해석할 수 있다. 별도의 최소 표본·관측 기간 기준 충족 여부도 확인해야 한다. |

요청 집단의 마감 여부는 비율의 상태와 별도로 표시해야 한다. 분모가 0인 경우에도 해당 요청 집단이 아직 마감되지 않았다면 데이터 없음 또는 비교 종료 표시와 함께 미마감 상태를 남겨야 한다.

S5에서 신규 shadow 선택을 중지했더라도 적격 요청 E는 계속 집계한다. E가 0보다 크고 S가 0이면 선택률은 0이며, 분모 S를 사용하는 비율은 계획된 종료 상태로 해석한다. 종료 전 요청의 잔여 결과와 신규 요청을 혼합해서는 안 된다. 종료 시 필요한 과거 비교 증거와 현재 serving 검증은 [단계별 증거 기준](../rollout/stages-and-gates.md)을 따른다.

C·M·X는 `comparison_class=success`, `expected_rejection`, `mixed`로 구분해야 한다. 성공·예상 거절 혼합 쌍은 X와 `mixed`에 포함하며, 성공 쌍이나 예상 거절 쌍의 통계에 중복 포함해서는 안 된다. v2 배정 비율을 계산할 때도 성공·실패·client 취소를 모두 포함해야 한다. 성공한 사용자 응답만으로 배정 비율을 계산해서는 안 된다.

### 분모 해석 예시

합성 구간에서 확인한 수가 E=1,000, S=100, D=95, T=95, C=80, M=76, X=4, W=90이라고 가정한다. 아래 표는 이 수로 계산한 예시이며 운영 목표가 아니다. 계산값을 확정 비율로 사용할 수 있는지는 작업 마감과 관측 완전성을 별도로 확인해야 한다.

| 계산 결과 | 값 |
| --- | --- |
| 선택률 S/E | 10% |
| 실제 시작률 D/S | 95% |
| 선택 표본 비교 완료율 C/S | 80% |
| 전체 적격 비교 범위 C/E | 8% |
| 조건부 차이율 X/C | 5% |
| 저장 완료율 W/S | 90% |

이 예시에서는 비교 판정에 이르지 않은 20건이 미실행 5건과 실행 후 판정 불가 15건으로 확인됐다고 가정한다. 실제 구간에서는 각 요청의 상태를 확인해야 한다. 단계 수의 차이만으로 진행 중인 비교와 최종 판정 불가를 구분해서는 안 된다.

저장 확인이 없는 10건은 비교 판정에 이르지 않은 20건과 겹칠 수 있다. 따라서 두 수를 합쳐 유실 30건으로 보고해서는 안 된다. 저장 확인이 없는 원인은 확정 드롭인지, 처리 중인지, ACK 미확인인지 따로 조사해야 한다.

10건이 모두 확정 드롭이고 나머지 관측이 완전한 마감 구간이면 저장 완료율을 90%로 확정할 수 있다. 작업이 진행 중이면 잠정값이다. ACK 미확인이 남아 있으면 저장 완료율의 상태는 미확인이다.

M/C가 95%라는 사실만으로 전환이 가능하다고 결론 내려서는 안 된다. 전체 적격 요청 중 비교한 범위가 8%라는 점, 비교 미완료 사유, 저장 확인 상태를 함께 검토해야 한다.

## 실험 해석

동일 요청의 계약 비교, 실제 사용자 canary, 용량·캐시 검증은 서로 다른 목적의 실험이다. 한 실험의 결과를 다른 목적의 검증 완료 증거로 대체해서는 안 된다.

- 비율·설정·backend 배포·비교 정책이 변경되면 epoch를 분리하고, 이전 결과와 합산할 때의 한계를 기록해야 한다.
- 알려진 데이터 drift는 source와 freshness 문맥을 함께 기록하여 분류해야 한다. 관측된 불일치를 모두 데이터 시차로 간주하여 제외해서는 안 된다.
- Shadow가 공유 DB·cache·외부 quota를 사용하면 v1 사용자 요청에도 영향이 생길 수 있다. 해당 공유 자원의 부하와 사용자 지표를 함께 확인해야 한다.
- Route, 사전에 정의한 요청군, 응답 크기 구간별 coverage를 확인해야 한다. 큰 응답이나 느린 요청이 선택적으로 누락되면 그 범위와 원인을 보고해야 한다.
- 사용자 전환율·구매·검색 만족도는 기존 서비스 계측과 연결할 수 있다. 프록시 HTTP 성공·지연 지표로 이 결과를 대체해서는 안 된다.
- 전체 v2 단계에는 동시 v1 serving 사용자 대조군이 없다. 이후의 변화를 모두 마이그레이션의 효과로 귀속해서는 안 된다.
