# 운영 화면·사례 조사·알림

운영 화면 또는 보고서는 현재 전환 조건, 사용자 영향, 비교·수집 상태를 함께 제시해야 한다. 운영 담당자는 이 근거를 사용하여 비율 확대 중지, shadow 축소 또는 serving 복귀를 판단한다. 이 문서는 화면에 필요한 정보와 알림 해석 기준을 정의하며, 특정 대시보드 제품의 구성을 지정하지 않는다.

프록시 내부의 비교·집계·이벤트 보호는 대시보드나 외부 수집기 없이 수행해야 한다. 아래 항목은 운영 판단에 필요한 정보의 기준이다. 현재 제품은 전용 웹 화면, 관측 HTTP endpoint와 외부 관측 SDK 연동을 제공하지 않는다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 실행·비교·수집 지표, 실제 적용 revision, 전환 변경 이력과 조회 권한 안의 이벤트를 사용한다. |
| 결과·출력 | 현재 상태, 원인별 경보와 확대 중지·축소·복귀 판단의 근거를 제공한다. |
| 실패·제한 | 지표가 누락된 상태를 정상으로 표시해서는 안 된다. 전용 웹 콘솔과 자동 승격은 초기 필수 범위에 포함하지 않는다. |

## 최소 운영 화면 또는 보고서

내부 보고서나 권한 있는 조회 방법을 사용할 수 있다. 기존 대시보드·조회 도구를 선택하는 경우에도 아래 정보를 제공해야 한다. 화면 배치는 달라도 되지만, 판단에 필요한 항목을 생략해서는 안 된다. Serving·shadow·stage·revision은 [공통 용어](../_rules/glossary.md), E/S/D/T/C/M/X/W는 [비교 분모](coverage-and-analysis.md)의 정의를 따른다.

| 영역 | 반드시 제공해야 할 정보 | 해당 정보로 확인할 내용 |
| --- | --- | --- |
| 현재 전환 | Stage, 설정 비율, 실제 v2 배정·응답 분포, 설정·backend 배포 revision을 제공한다. | 의도한 설정과 실제 적용 상태가 같은지, 여러 revision이 혼재하는지 확인한다. |
| 사용자 상태 | Serving 오류·지연·전송 불완전·취소를 각각 제공한다. | 사용자 품질 기준 초과 여부와 serving 롤백 필요성을 확인한다. |
| 양쪽 실행 | v1/v2와 serving/shadow별 시작·종료·오류·지연·inflight를 제공한다. | Shadow 부하와 사용자 요청을 처리하는 backend의 품질을 구분한다. |
| 비교 품질 | M·X·C, 실행 오류·비교 불가 사유와 성공·예상 거절·혼합 쌍별 비교율을 제공한다. | 계약 차이와 비교 조건 미충족을 구분한다. |
| 관측 상태 | Queue depth·age, 저장 오류·유실과 E/S/D/T/C/W를 제공한다. | 판단에 필요한 표본·완료율이 충족됐는지, 증거가 누락됐는지 확인한다. |
| 데이터 문맥 | 확인 가능한 source·revision·freshness와 문맥 미확인·시차 초과의 분포를 제공한다. | 데이터 drift와 코드 차이를 구분할 근거가 있는지 확인한다. |
| 사례 조회 | 기간·route·result·revision으로 범위를 제한한 이벤트 검색을 제공한다. | 허용된 입력·계약 단서로 차이 또는 실패 사례를 조사한다. |
| 변경 이력 | 실제 적용·롤백 시각, 이전·다음 설정과 변경 사유를 제공한다. | 품질 악화 시점과 설정·배포 변경의 관계를 확인한다. |

실시간 잠정값, 마감된 요청 집단의 값, 데이터 없음, 관측 미확인을 구분해서 표시해야 한다. Route·요청군·응답 크기별 coverage도 확인할 수 있어야 하며, 특정 집단의 누락을 전체 평균으로 감춰서는 안 된다.

대시보드 접근 권한과 상세 표본 조회 권한은 분리해야 한다. 내부 route·트래픽 메트릭과 식별·상관 정보가 남은 이벤트 요약에도 접근 제한을 적용해야 한다. 상세 값의 저장이 허용되지 않는 경우에는 허용된 필드 경로, 오류 분류, 정책과 trace 요약을 사용하여 조사해야 한다. 조사를 위해 금지된 원문을 추가로 저장하거나 공개해서는 안 된다.

내부 snapshot과 `observation_status()`는 프로세스 내부 인터페이스이며, HTTP 조회나 전용 CLI로 노출하지 않는다. 관측 HTTP 조회를 활성화하는 설정도 없다. 별도로 보고서나 알림 자료를 작성할 때에는 필요한 지표와 허용 필드만 사용해야 한다. 원문 요청·응답이나 자유 형식의 예외를 포함해서는 안 된다.

Health는 loopback 전용 `GET /healthcheck`에서 요청 수용 가능 여부만 확인한다. 성공은 200과 `{"ready":true}`, 준비되지 않은 상태는 503과 `{"ready":false}`로 구분한다. 이 응답을 메트릭 조회나 전환 gate의 통과 증거로 사용해서는 안 된다.

현재 메모리 메트릭은 재시작하면 초기화된다. SQLite에 남은 비교 이벤트로 개별 사례는 조사할 수 있지만, 전체 요청의 지연 분포와 단계별 분모를 대신할 수는 없다. 확보하지 못한 이전 구간은 화면과 보고서에서 미확인으로 표시해야 한다.

### 상태 확인과 사례 조사 순서

운영 담당자는 다음 순서로 조사하십시오.

1. 조사할 route 또는 cohort group과 관측 구간을 선택하십시오.
2. 선택한 구간의 stage, 설정 revision과 확인 가능한 backend 배포 revision을 기록하십시오.
3. 메트릭 수집 범위와 누락 여부를 확인하십시오.
4. 분모나 수집 경로를 확인할 수 없으면 관측 상태를 미확인으로 표시하십시오.
5. 사용자 오류·지연·취소·불완전 전송을 같은 구간의 backend 역할별 실행 결과와 대조하십시오.
6. 비교 완료율과 차이율을 분모·결과 분류별로 확인하십시오.
7. 비교 불가·미실행·드롭 사유를 확인하십시오.
8. 사례 조사가 필요하면 기간·route·result·revision으로 조회 범위를 제한하십시오.
9. 허용된 문맥과 변경 이력으로 사례의 원인을 조사하십시오.
10. 확인된 근거와 미확인 항목을 기록하십시오.
11. [승격 기준](../rollout/stages-and-gates.md) 또는 [복귀 절차](../rollout/rollback-and-bypass.md)에 따라 조치를 판단하십시오.

관측 미확인을 오류 0건 또는 gate 통과로 해석해서는 안 된다. 사용자 응답 완료와 backend 완료를 같은 시각의 사건으로 가정해서는 안 된다. 조치를 요청한 사실과 실제 적용 결과는 구분해야 한다.

## 알림과 대응

아래 첫 대응은 장애 조사 시의 제안이다. 실제 중지·복귀 판단은 해당 route의 정해진 기준과 복귀 준비 상태를 따라야 한다. 필수 gate의 증거가 없거나 기준을 충족하지 못하면 승격해서는 안 된다.

| 관측 신호 | 권장하는 첫 대응 | 함께 확인할 항목 |
| --- | --- | --- |
| Serving 오류 또는 p99가 해당 기준을 초과함 | 사용자 노출 확대를 막기 위해 비율 확대 중지를 권장한다. | v2 자체 문제인지, 프록시 또는 공유 의존 서비스의 문제인지 구분하십시오. |
| Shadow 오류·timeout이 증가하여 정한 알림 조건을 충족함 | 추가 실행 부하를 줄이기 위해 shadow 축소 또는 중지를 권장한다. | Serving 자원을 침범하는지와 대상 backend의 처리 용량을 확인하십시오. |
| 비교 완료율이 정한 기준을 충족하지 못함 | 불충분한 비교 근거로 확대하지 않도록 승격 중지를 권장한다. | 큰 응답, 문맥 부족, 파싱 실패, 큐 또는 deadline 사유를 확인하십시오. |
| 권한·테넌트 불변식 위반을 발견함 | 해당 route의 전환 중지와 복귀 검토를 권장한다. | 영향을 받은 사용자 범위와 허용된 증거를 확인하십시오. 확인한 허용 증거를 보존하십시오. |
| 저장 오류 또는 queue age가 증가함 | 수집 드롭 계측을 권장한다. 수집 부하가 원인이면 shadow 축소 검토를 권장한다. | 저장소, batch 처리와 만료 정리 상태를 확인하십시오. |
| 대상 인스턴스·worker의 revision이 의도한 값과 다름 | 혼합 설정에서의 확대를 피하기 위해 비율 확대 중지를 권장한다. | 적용 실패 여부와 전파 시간을 확인하십시오. |
| Data freshness 기준을 초과하거나 필수 문맥이 누락됨 | 비교 근거의 유효성 확인을 권장한다. 비율 확대 중지도 권장한다. | 데이터 동기화 담당 경로와 문맥 누락 원인을 구분하십시오. |
| 선택한 관측 방식에서 필요한 메트릭 snapshot 또는 상태 확인이 누락됨 | 관측 상태를 미확인으로 처리해야 한다. | 내부 계측과 프로세스 상태를 확인하십시오. 별도 수집 경로를 사용한다면 그 경로도 확인하십시오. |

알림별 숫자 임계값, 연속 관측 창, 담당자와 통보 경로는 미정이다. 실제 서비스 수준 목표인 SLO와 운영 방식을 확인한 뒤 정해야 한다. 이 값이 정해지지 않은 상태에서 임의 수치를 초과 기준으로 사용하거나 알림 준비가 끝났다고 판단해서는 안 된다.

저장 성공이 0건인 경우에는 먼저 해당 구간의 요청·shadow 선택 수와 수집 경로의 상태를 확인해야 한다. 트래픽이 없는 상태와 수집 장애를 같은 상태로 처리해서는 안 된다. 자동 승격과 자동 롤백은 MVP 범위에 포함하지 않는다.
