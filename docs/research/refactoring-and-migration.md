# API 리팩토링·마이그레이션 패턴과 적용 경계

이 문서는 점진적 교체, 사용자에게 결과를 노출하지 않는 실행, 전환 기간에만 유지하는 임시 구성을 API 마이그레이션에 적용하는 조건을 설명한다. 패턴의 목적과 특정 서비스의 지원 기능을 구분하며, 도구의 채택 여부를 결정하지 않는다. serving, shadow, route의 의미는 [공통 용어](../_rules/glossary.md)를 따른다.

## 적용 원리

| 원리 | 의미 | 적용 조건 |
| --- | --- | --- |
| 점진적 기능 교체 | 기존 진입점 앞의 프록시가 기능별 요청을 기존 구현 또는 신규 구현으로 분기한다. 이 과정에서는 내부 호출과 데이터 의존도 함께 처리해야 한다. | 전환 대상 route를 제한해 시작한다. 외부 HTTP 요청이 신규 구현으로 전환됐다는 사실만으로 내부 의존이 제거됐다고 판정해서는 안 된다. |
| Dark launching | 신규 동작을 실행하되 그 결과를 사용자 응답으로 선택하지 않는 방식이다. 기존·신규 실행 결과를 수집하면 두 결과를 비교할 수 있다. | 본 제품에서는 shadow 실행과 비교의 근거로 사용한다. 일부 사용자에게 신규 응답을 제공하는 canary 구간에서는 실제 사용자 영향을 별도로 확인해야 한다. |
| 임시 전환 구성 | 기존·신규 구현의 공존에 필요한 구성을 두고, 전환 목적을 달성한 뒤 제거하는 방식이다. | 본 제품의 종료 조건에는 프록시 제거와 직접 v2 호출 경로의 검증이 모두 포함된다. |

위 원리의 근거는 [Strangler fig](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/strangler-fig.html), [Dark Launching](https://martinfowler.com/bliki/DarkLaunching.html), [Transitional Architecture](https://martinfowler.com/articles/patterns-legacy-displacement/transitional-architecture.html)이다. 이 패턴들은 마이크로서비스 분해를 필수 전제로 하지 않는다. 같은 서비스의 언어, 내부 구조 또는 실행 인프라를 교체할 때에도 공개 계약과 의존성에 맞는 적용 범위를 정할 수 있다.

## 서로 다른 네 가지 제어

| 제어 | 답하려는 질문 | 그 자체로 증명하지 못하는 것 |
| --- | --- | --- |
| 경로 분기 | 해당 기능을 기존 구현과 신규 구현 중 어디에서 처리하는가? | 같은 입력에 대한 양쪽 응답의 일치를 증명하지 못한다. |
| 사용자 canary | 일부 사용자에게 신규 응답을 제공했을 때 허용한 품질 기준을 충족하는가? | 관측하지 않은 요청의 동작이나 전체 전환 시 처리 용량을 증명하지 못한다. |
| shadow 실행 | 사용자 응답의 제공자를 유지하면서 반대편도 실행하는가? | 양쪽 결과의 수집이나 응답 비교의 완료를 증명하지 못한다. |
| 비교·수집 | 양쪽 실행 결과가 어떻게 다르며, 선택한 요청 중 관측 기록이 얼마나 남았는가? | 전체 데이터 정합성, 업무 효과의 안전성, 운영 전환의 성공을 단독으로 증명하지 못한다. |

본 제품은 요청별 serving을 먼저 배정하고, 적격성과 표본 조건을 충족한 요청에 대해서만 반대편을 shadow로 실행한다. 양쪽 결과를 같은 논리 요청에 연결하며, 상세 저장 표본은 serving 비율 및 shadow 표본과 독립적으로 선택한다. 이 설명은 실행과 결과 연결의 책임을 구분한 것으로, serving을 완료한 뒤 shadow를 순차 실행한다는 의미가 아니다.

도구를 검토하는 담당자는 위 네 가지 제어 중 도구가 제공하는 범위와 별도 연결이 필요한 범위를 구분해야 한다. 운영 적합성은 구성 요소의 개수가 아니라 사용자 영향, 응답 차이, 관측 누락, 복귀 가능성으로 판단해야 한다. 각 동작의 기준은 [serving 배정](../routing/serving-and-cohorts.md), [shadow 실행](../shadow/parallel-execution.md), [비교 결과](../comparison/context-and-outcomes.md)를 따른다.

## 리팩토링 유형별 선행 조건

아래 확인 작업은 각 변경 유형의 담당자에게 적용한다. 담당 책임은 표의 마지막 열에 명시한다.

| 변경 유형 | 전환 전 확인 | 프록시 밖의 담당 범위 |
| --- | --- | --- |
| 같은 계약의 코드 재구현 | 양쪽의 입력, 권한, 오류 계약이 같은지 확인하십시오. 의도한 차이를 목록으로 기록하십시오. | API 개발자가 v1/v2 구현과 계약 fixture, 즉 기대 입력·응답을 지정한 검증 자료를 관리한다. |
| 배포 환경·런타임 교체 | 인증, 네트워크, HTTP 전달 동작, 대표 부하 처리, 종료 중 요청·작업의 수명을 확인하십시오. | 운영 담당자가 실행 환경 구성, 배포, 용량 확보를 담당한다. |
| 서비스 경계 분리 | 외부 HTTP 요청과 함께 내부 호출, 배치 작업, 메시지 소비자의 의존성을 확인하십시오. | 해당 서비스의 API 개발자가 호출자 변경, 호환 adapter, 데이터 소유권을 담당 계층과 정한다. |
| 공개 응답 변경 | 비교를 위한 필드 매핑과 호출자에게 호환 응답을 제공하는 처리를 구분하십시오. | API 또는 호출자 소유 계층의 개발자가 호환 처리나 클라이언트 마이그레이션을 담당한다. |
| 독립 데이터 저장소 도입 | 초기 적재, 변경분과 삭제의 반영, 데이터 시차, v1 복귀 준비를 확인하십시오. | 데이터 담당자가 데이터 파이프라인, 원천 소유권, 복구 계약을 관리한다. |

호환 adapter가 필요한 경우에는 API 또는 호출자 소유 계층에서 그 위치, 책임, 제거 조건을 정해야 한다. 비교용 정규화를 사용자 응답의 자동 변환에 사용해서는 안 된다. 외부 route의 전환 완료를 모든 내부 호출과 데이터 의존의 종료로 간주해서도 안 된다. 책임과 종료의 세부 조건은 [적용 범위](../product/scope-and-workflows.md), [데이터 책임](../_rules/identity-and-data-boundaries.md), [종료](../rollout/retirement.md)를 따른다.

## 서비스 선택 시 적용 조건

AWS의 Strangler Fig 예제에 등장하는 Refactor Spaces는 패턴을 구현하는 서비스의 하나이며, 패턴 자체와 동일하지 않다. [AWS 이용 조건 안내](https://docs.aws.amazon.com/migrationhub-refactor-spaces/latest/userguide/migrationhub-availability-change.html)는 2025-11-07부터 Refactor Spaces의 신규 고객 수용을 중단하고 기존 고객의 이용을 허용한다고 설명한다.

서비스를 선정하는 담당자는 이용 자격이 확인되지 않은 계정에서 Refactor Spaces를 신규 구축의 기본 후보로 선정해서는 안 된다. 다른 현대화 서비스의 명칭만으로 해당 서비스가 요청별 양쪽 응답 비교까지 제공한다고 추정해서도 안 된다. 채택 전에는 실제 계정과 리전의 이용 가능성, 제공 기능, 비용, 유지보수 상태 및 종료 공지를 확인해야 한다.

## 적용 범위와 서비스별 결정 사항

제품은 요청당 하나의 serving 응답, 자원 상한이 있는 shadow, 비교와 관측의 책임 분리, 수동 점진 전환, 종료 조건을 유지한다. 실제 배치 위치, 호환 처리, 내부 의존의 정리 방법, 외부 도구의 응답 수집 연계는 적용 서비스별로 결정해야 한다.

Python/FastAPI는 확정된 구현 스택이다. 운영 배포 환경, 운영 저장소, 관측 플랫폼의 선택은 미정이며, 이 문서의 패턴 비교가 특정 후보의 채택을 의미하지 않는다. 기존 인프라의 재사용 여부, serving 배정 담당 구성, 실행 환경은 [실행 구조](../infrastructure/deployment-and-stack.md)의 조건과 대상 환경을 대조하여 결정해야 한다. 운영 적합성은 대상 API의 계약과 [검증 시나리오](../validation/test-catalog.md)의 실행 증거를 기준으로 판단해야 한다.
