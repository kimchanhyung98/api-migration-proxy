# 비교 이벤트와 전환 이력 모델

[비교 이벤트](../_rules/glossary.md)는 한 논리 요청의 양쪽 실행 결과와 최종 비교 판정을 연결하는 기록이다. 전환 이력은 stage나 설정을 변경한 사실과 근거를 남기는 별도 기록이다. 두 기록은 목적과 유실 허용 조건이 다르다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 내부 요청 식별자, backend별 실행 결과, 비교 판정, 설정·정책 revision 및 비교 문맥을 사용한다. |
| 결과·출력 | 고유 comparison event와 별도 rollout change 기록에 필요한 논리 필드를 정의한다. |
| 실패·제한 | 외부 request ID를 이벤트의 고유 키로 사용해서는 안 된다. 비교 요약의 유실 허용 정책을 중요한 전환 변경 이력에 자동 적용해서는 안 된다. |

## 수집 단위와 필드

논리 엔터티는 `comparison_event`와 `rollout_change`로 구분한다. `comparison_event`는 shadow 표본으로 선택한 논리 요청 한 건당 최대 하나를 만든다. 이 이벤트에는 `matched`와 `different`뿐 아니라 미실행, 실행 오류 및 비교 불가 결과도 포함할 수 있다. 표본에서 제외된 요청은 메트릭에 남기며, 비교 이벤트를 반드시 만드는 대상에는 포함하지 않는다.

프로세스 내부 메트릭은 요청 처리 단계에서 얻은 수량과 지연을 메모리에 집계한다. 이 집계값과 `comparison_event`는 별개의 데이터이다. 이벤트의 표본 제외, 드롭, 저장 지연 또는 만료가 전체 요청의 집계 분모를 바꾸어서는 안 된다. 저장된 비교 이벤트로 전체 요청 통계를 다시 만들어서는 안 된다. 프로세스 재시작 후 집계값이 자동 복원된다고 가정해서도 안 된다.

최종 요약은 serving backend 결과, shadow 결과 또는 미실행 사유, 사용자 응답 전송의 종료 결과를 모두 확보한 뒤 확정한다. Backend가 본문을 전부 보냈어도 느린 client에 대한 전송이 끝나지 않았다면 사용자 응답 완료로 기록해서는 안 된다. 프록시는 정해진 상한 안에서 상태를 유지한다. 종료 시 실제 완료·취소·전송 실패 결과를 구분한다.

다음 표는 비교 이벤트에서 논리적으로 구분해야 하는 내용을 나타낸다. 기본 저장소는 로컬 SQLite이다. 여러 호스트의 공유 저장이나 쓰기 경합 때문에 사설 PostgreSQL을 선택하더라도 같은 논리 필드와 보존 기준을 유지해야 한다. 물리 스키마와 인덱스는 선택한 저장소의 적재·조회·정리 부하에 맞춰 정한다. 설정 원문과 원본 API 데이터를 이벤트에 함께 넣어서는 안 된다.

| 이벤트 묶음 | 필수 내용 |
| --- | --- |
| 식별 | event ID, 요청 시작 시각, 사용자 요청 종료 시각, route ID 및 환경·마이그레이션 식별자를 포함한다. |
| 정책 | 실제 요청에 적용한 configuration revision, comparison policy revision 및 epoch 식별자를 포함한다. |
| 배정 | serving backend, 응답 출처, 사용자 요청 종료 결과, shadow 선택·실제 시작 여부 및 배정 방식을 구분한다. 비민감 cohort 분류는 선택적으로 포함한다. |
| 양쪽 결과 | [backend 결과 모델](../comparison/context-and-outcomes.md)에 따라 버전, 역할, 배포 revision, 실행 결과, 계약 class, status, 지연, 수신 크기·완전성 및 캡처 상태를 구분한다. |
| 비교 | `result`, `reason`, `comparison_class`를 포함한다. 정책 적용 후 차이 개수와 집계 제한 여부를 포함한다. 허용된 차이 경로, 목록 절단 여부 및 정책 적용 내역도 포함한다. |
| 문맥 | 데이터 source·revision 또는 freshness 수준 등 비교에 필요한 비민감 문맥을 나타낸다. 확인하지 못한 문맥을 확인된 것으로 대체하지 않는다. |
| 수집 | 양쪽 backend 종료, 비교 완료, 이벤트 생성 및 저장 시각을 구분한다. Schema version, 상세 표본 선택 여부·상태 및 목적별 보존 만료 기준을 포함한다. |
| 상관관계 | 내부 request ID를 사용한다. Trace ID는 검증된 경우에 선택적으로 포함한다. |

현행 저장 요약의 차이 개수와 경로는 정책 적용 후 결과이다. 비교 엔진이 반환하는 정책 적용 전 raw 차이 정보까지 모두 저장한다고 해석해서는 안 된다. 엔진의 반환 정보와 저장되는 필드의 범위는 구분해야 한다.

### 요약의 데이터 보호 경계

요약은 허용된 메타데이터이며 익명 데이터라는 뜻은 아니다. 시각, route, 내부 request ID 또는 trace ID를 다른 기록과 결합하면 개별 요청을 연결할 수 있다. 요약에도 접근 권한과 보존 기간을 적용해야 한다.

- 프록시는 요청마다 내부 UUID를 생성해야 한다. 외부 request ID, 사용자 ID 또는 인증 정보를 내부 request ID 대신 저장해서는 안 된다.
- Route, 환경, revision, 이유 및 문맥 필드에는 운영자가 승인한 비민감 코드만 사용해야 한다. 문자열의 길이·문자 형식 검사는 개인정보 검사를 대신하지 않는다.
- Trace ID는 신뢰된 제공자가 검증한 상관관계 식별자인 경우에만 선택적으로 보관해야 한다. 외부 요청 header를 그대로 복사해서는 안 된다. 기본 CLI가 외부 trace ID를 수집한다고 가정해서는 안 된다.
- URL, query, header, cookie, 원본 body, 예외 원문 및 diff 원문 값은 요약에 넣어서는 안 된다. 허용된 차이 경로에도 사용자 ID나 업무 원문이 포함되지 않아야 한다.
- 상세는 기본 비활성이다. 상세가 필요하면 [상세 표본·마스킹](detail-sampling.md)의 별도 허용 조건을 적용해야 한다.

이 기준은 이벤트를 만드는 프록시와 내부 확장 코드의 공통 계약이다. 저장소를 직접 호출하거나 다른 어댑터를 연결해도 수집 허용 범위가 넓어지지 않는다. 요청·응답 전체를 저장 어댑터나 오류 로그로 넘기지 않아야 한다.

이벤트 식별·시각·제한 정보에는 다음 규칙을 적용한다.

- Event ID는 저장 재시도 및 배치 일부 성공 확인에 사용하는 중복 방지 키이다. 저장 성공 응답이 유실되어 재시도하더라도 같은 ID를 사용해야 한다. 같은 이벤트의 복수 행 생성을 방지해야 한다. 저장 완료의 중복 집계도 방지해야 한다.
- 내부 요청 UUID는 외부 request ID의 중복 또는 재사용과 무관하게 생성한다. 외부 ID만으로 서로 다른 요청을 하나의 이벤트로 합쳐서는 안 된다.
- 식별 시각은 UTC 등 공통 형식으로 나타내야 한다. 요청 시작, 사용자 전송 종료, 늦게 끝난 shadow, 비교 완료 및 저장 시각을 같은 시각으로 대체해서는 안 된다. Backend 종료 시각은 응답 연결 정리 후 실행 결과를 확정한 시각이다.
- 지속 시간은 단조 시계로 측정한 값을 보존해야 한다. 서로 다른 호스트의 벽시계 시각을 빼서 backend 지연을 계산해서는 안 된다.
- Backend 배포 revision은 실제 실행 버전을 확인할 수 있을 때만 기록한다. 확인할 수 없으면 `unknown`으로 유지한다. 프록시 설정 revision으로 대신 채워서는 안 된다.
- 필수 문맥을 확인할 수 없으면 `unknown` 또는 해당 이유 코드로 나타내야 한다. 빈 문자열이나 임의 기본값을 확인된 문맥처럼 사용해서는 안 된다.
- 차이 개수의 집계가 제한되어 전체 수를 확정하지 못했다면 제한 여부를 함께 표시해야 한다. 차이 경로 목록이 제한되거나 일부 경로가 저장 대상에서 제외되어도 실제 차이가 없어진 것은 아니다.
- 요약과 상세의 보존 만료는 최초 이벤트 생성 시각을 기준으로 유지한다. 저장이 늦어지거나 재시도했다는 이유로 보존 기한을 새로 시작해서는 안 된다.

### 비교 이벤트 예시

다음은 양쪽 성공 응답의 값이 다른 합성 사례이다. 논리 필드의 관계를 설명하기 위한 예시이며, 실제 DB 컬럼 정의나 모든 필드를 갖춘 전송 schema가 아니다.

```json
{
  "schema_version": 1,
  "event_id": "example-event-001",
  "route_id": "catalog_detail",
  "configuration_revision": "example-revision-003",
  "comparison_policy_revision": "catalog-compare-001",
  "epoch_id": "example-epoch-003",
  "serving_backend": "v1",
  "shadow_selected": true,
  "backends": {
    "v1": {
      "role": "serving",
      "deployment_revision": "example-v1-build-007",
      "execution_outcome": "http_response",
      "contract_class": "success",
      "status_code": 200,
      "duration_ms": 42
    },
    "v2": {
      "role": "shadow",
      "deployment_revision": "example-v2-build-012",
      "execution_outcome": "http_response",
      "contract_class": "success",
      "status_code": 200,
      "duration_ms": 55
    }
  },
  "comparison": {
    "result": "different",
    "reason": "json_value_mismatch",
    "comparison_class": "success",
    "difference_paths": ["/price"]
  },
  "detail_sampled": false
}
```

### 전환 이력

`rollout_change`는 변경 ID, 대상 route 또는 그룹, 변경 주체, 변경 시각 및 이전·다음 revision을 구분해야 한다. 운영 문맥으로 이전·다음 stage, 비율, 변경 사유, gate evidence 참조, 적용 결과 및 복귀 대상 revision을 남겨야 한다. 적용을 요청한 사실과 실제 적용을 확인한 결과를 같은 것으로 기록해서는 안 된다.

비교 요약은 제한 큐에서 유실될 수 있지만 이 정책을 전환 이력에 그대로 적용해서는 안 된다. 관측 저장소 장애 중에도 긴급 중지·복귀를 수행한 사실은 기존 배포 이력 등 추적 가능한 경로에 남겨야 한다. 별도 저장 제품이나 자동 변경 제어기의 존재를 전제하지 않는다. 기록의 적용 범위와 절차는 [운영 변경 기록](../rollout/change-management.md)을 따른다.

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-21 | P0 | 한 논리 요청의 양쪽 결과를 하나의 요약으로 수집해야 한다. | 내부 요청 식별자와 revision, backend 역할·오류·지연 및 비교 결과를 같은 요청의 기록으로 연결할 수 있다. |
