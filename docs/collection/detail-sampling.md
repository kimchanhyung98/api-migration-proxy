# 상세 표본 선택과 데이터 마스킹

상세 표본은 조사에 사용할 수 있도록 선택한 일부 이벤트의 저장용 필드이다. 비교용 캡처는 응답을 메모리에서 비교하기 위한 입력이고, 상세 표본은 허용·선택·마스킹 조건을 통과한 저장 데이터이다. 응답을 캡처했다는 이유로 그 본문을 상세에 저장해서는 안 된다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 실행·비교 결과, 상세 표본율, 허용 필드, 바이트 상한, 마스킹 정책 및 보존 정책을 사용한다. |
| 결과·출력 | 허용된 상세 표본을 포함한 이벤트 또는 안전한 요약만 포함한 이벤트를 만든다. |
| 실패·제한 | token, cookie, 민감 정보가 포함된 예외 및 허용되지 않은 diff 값을 저장해서는 안 된다. 조사 목적으로 편향시킨 상세 표본으로 전체 불일치율을 계산해서는 안 된다. |

## 요약·상세·민감 정보

| 구분 | 수집 기준 |
| --- | --- |
| 메트릭 | 요청 처리 단계에서 집계할 수 있는 수치를 기록한다. 원문 사용자 식별자나 query를 label로 사용해서는 안 된다. |
| 비교 요약 | shadow 표본으로 선택된 요청의 실행 결과, 비교 판정 및 허용된 차이 경로를 중심으로 구성한다. |
| 상세 표본 | 기본값은 비활성이다. 활성화하려면 허용 필드, 최대 크기, 표본율, 마스킹 및 보존 정책을 정해야 한다. |
| 인증·비밀 | Authorization, cookie 값, API key, 서명 및 credential이 포함된 URL을 저장해서는 안 된다. |
| 검색어·업무 원문 | 요약의 기본 필드에 포함하지 않는다. 상세로 취급할 필요가 있으면 목적, 보존 기간 및 조회 권한을 먼저 결정해야 한다. |
| 개인정보 hash | hash로 바꿨다는 이유만으로 익명 정보로 간주해서는 안 된다. 원문 대신 hash를 저장해야 하는 이유와 재식별 가능성을 검토해야 한다. |

같은 데이터 보호 기준을 파일 이름, 예외 메시지 및 diff 값에도 적용해야 한다. 비교에 필요한 필드를 저장 대상에서 제외했더라도 비교 정책이 바뀐 것으로 취급해서는 안 된다.

## 선택과 마스킹 순서

프록시는 실행·비교 판정이 정해진 후 상세 처리를 수행한다. 상세가 제외되거나 생성에 실패해도 이미 안전하게 만든 요약의 판정은 변경하지 않는다. 다음 절차는 프록시의 자동 처리 순서이다.

1. 상세 저장 여부와 독립적으로 실행 결과와 비교 결과를 확정한다.

   상세를 저장하지 않는 요청도 요약 비교와 메트릭의 대상이 될 수 있다.

2. 상세 수집 허용 정책과 표본율에 따라 상세 표본을 선택한다.

   비활성이거나 표본으로 선택하지 않았으면 요약만 유지한다.
   이 경우 상세 필드 제공과 마스킹을 수행하지 않는다.

3. 선택된 표본에서 허용된 필드만 마스킹 대상으로 가져온다.

   허용되지 않은 필드나 객체 전체를 저장 대상으로 넘기지 않는다.

4. 인증 정보, 개인정보, 예외 내용, diff 값 및 객체 키에 적용되는 마스킹 정책을 실행한다.

   마스킹에 실패하면 상세를 저장 대상에서 제외한다.
   이 경우 `masking_failed` 상태를 남긴다.

5. 마스킹된 상세의 바이트 수를 상한과 비교한다.

   상한을 초과하면 상세를 저장하지 않는다.
   이 경우 `oversized` 상태를 남긴다.
   불일치 우선 표본 정책을 사용하더라도 크기 상한을 면제하지 않는다.

6. 상세 표본 선택 여부, 생성 상태 및 만료 기준을 이벤트에 기록한다.

7. 안전하게 생성한 이벤트를 저장 대상으로 제출한다.

   안전한 상세가 있으면 요약과 함께 제출한다.
   상세가 없으면 요약만 제출한다.
   저장 대상으로 제출한 상태와 저장을 확인한 상태는 다르다.

상세 표본율은 0 이상 1 이하의 값이다. 기본 `detail_sample_ratio=0`은 상세 수집만 비활성화한다. 요약, 비교 또는 메트릭까지 비활성화한다는 뜻이 아니다. 허용 필드가 없거나 마스킹 후 남은 값이 없으면 상세 없음 상태로 구분한다. 이 상태를 빈 원문의 성공적인 수집으로 표현해서는 안 된다.

마스킹 전 원문은 허용된 메모리 범위에서만 취급해야 한다. 마스킹 실패 로그, 임시 파일 또는 원문 재시도 큐로 전송해서는 안 된다. 시간 예산 안에 안전한 상세를 만들지 못했으면 상세를 제외한다. 이미 생성한 안전한 요약은 유지한다.

자동 HTTP 계측을 적용할 때에도 URL, query, header 및 exception에 같은 수집 허용 정책을 적용해야 한다. 상세 표본율 0만으로 자동 계측의 민감 정보 수집도 차단되었다고 가정해서는 안 된다. Exporter에 전달되는 실제 데이터에서 금지 값이 제거되었는지 확인해야 한다. [OpenTelemetry 민감정보 처리](https://opentelemetry.io/docs/security/handling-sensitive-data/)는 수집 최소화 원칙을 확인하는 참고 자료이다. 특정 관측 플랫폼의 채택을 전제하지 않는다.

## 상세 상태 구분

`detail_sampled`는 표본으로 선택했는지를 나타낸다. `detail_state`는 상세 데이터의 생성·저장·만료 상태를 나타낸다. 두 값은 서로 대체할 수 없다.

| 상태 | 의미 |
| --- | --- |
| `disabled` | 상세 정책이 비활성이다. 상세 표본을 선택하지 않았다. |
| `not_selected` | 상세 정책은 활성이나 해당 이벤트는 표본에서 제외되었다. |
| `pending` | 선택된 표본의 안전한 상세가 생성되어 저장을 기다린다. 저장 완료를 뜻하지 않는다. |
| `stored` | 해당 상세가 저장되었다. 현재 조회 가능 여부는 권한과 만료 시각을 추가로 확인해야 한다. |
| `masking_failed` | 선택되었지만 안전한 상세를 생성하지 못했다. 요약만 유지할 수 있다. |
| `oversized` | 선택되었지만 마스킹된 상세가 허용 크기를 초과했다. 상세는 저장하지 않는다. |
| `no_allowed_fields` | 선택되었지만 허용 필드에서 저장할 값이 남지 않았다. |
| `expired` | 상세의 보존 기한이 지났다. 조회 시점에 계산할 수 있으며, 이 상태만으로 물리 삭제까지 완료되었다고 단정해서는 안 된다. |

저장 ACK 미확인은 위 생성 상태와 별도로 [적재 결과](async-storage.md)에서 해석한다. 안전한 상세를 만들었다는 사실이나 저장소 호출이 끝났다는 사실만으로 저장 성공을 확인한 것으로 처리해서는 안 된다. 상세 미선택, 마스킹 실패, 크기 초과, ACK 미확인 및 만료를 모두 같은 “상세 없음”의 성공 상태로 합쳐서는 안 된다.

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-23 | P0 | 요약 수집과 상세 표본 수집을 구분해야 한다. | 상세 표본율 0에서도 메트릭과 요약 비교를 유지한다. |
| FR-24 | P0 | 허용 필드·크기·보존 정책을 적용해야 한다. | 인증 정보를 저장하지 않는다. 허용되지 않은 값이 로그·오류·diff로도 유출되지 않는다. |
