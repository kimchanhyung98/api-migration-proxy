# 이벤트 조회와 보존 기간 관리

조회는 저장된 비교 사례를 허용된 기간·route·행 수 안에서 찾는 기능이다. 보존 관리는 목적별 만료 시각이 지난 요약과 상세를 조회에서 제외하고 정리하는 기능이다. 저장 행이 있다는 사실만으로 해당 데이터의 현재 조회 권한이나 보존 기한을 충족한다고 판단해서는 안 된다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 기간, route, 비교 결과·이유, revision 또는 event ID 등의 조건과 조회 권한·상한을 사용한다. 보존 작업에는 요약·상세·이력별 보존 정책이 필요하다. |
| 결과·출력 | 조건과 권한에 맞는 이벤트 조회 결과, 만료 정리 결과 및 남은 적체를 구분한다. |
| 실패·제한 | 무제한 export와 전체 body 인덱싱을 제공 범위로 가정해서는 안 된다. 삭제 실패 또는 남은 만료 데이터를 정리 완료로 표시해서는 안 된다. |

## 조회와 보존

최소 검색 조건은 기간, route, `result`, `reason`, backend와 그 역할, 설정·비교 정책 revision 및 event ID이다. 조사 목적에 따라 backend 배포 revision도 사용한다. 조회는 내부 운영 권한 안에서 수행한다. 전용 웹 콘솔이나 공개 HTTP 조회 API는 필수 범위가 아니다. 제공 방식에는 내부 도구, 제한된 SQL 또는 프로세스 내부 조회가 있다.

조회 권한, 최대 행 수, 최대 기간, export 허용 범위 및 허용된 마스킹 상세의 수집·보존 여부를 명시해야 한다. 요약, 상세 및 전환 이력은 목적별 보존 기간을 구분해야 한다. 보존 기간을 늘리려면 추가 용량, 조회 비용 및 삭제 처리량을 다시 확인해야 한다.

기본 SQLite와 선택 구성인 사설 PostgreSQL에 같은 조회·보존 계약을 적용한다. 저장소를 결정할 때에는 실제 조회 범위와 예상 적재량을 기준으로 기간·route·결과·revision 및 만료 조건의 인덱스를 검토해야 한다. 무제한 JSON 저장, 전체 body 인덱싱 및 별도 검색 클러스터는 초기 구성에 포함하지 않는다.

### 저장 파일과 DB 접근 권한

단일 호스트의 기본 SQLite는 하나의 writer가 기록한다. 프록시는 새 SQLite 파일과 접근할 기존 파일에 `0600`, 새 데이터 디렉터리에 `0700` 권한을 적용해야 한다. 기존 상위 디렉터리의 권한은 자동으로 변경하지 않는다. 운영자는 실행 계정의 접근 범위를 확인해야 한다. DB 파일뿐 아니라 저널과 백업 파일의 위치·권한도 관리해야 한다.

여러 호스트가 사설 PostgreSQL을 공유하면 쓰기 계정과 조회 권한을 업무 범위에 맞게 제한해야 한다. 사설망 연결만으로 모든 사용자에게 조회 권한을 부여해서는 안 된다. DB 자격 증명과 접속 문자열을 이벤트·메트릭·오류 로그에 기록해서도 안 된다.

조회 권한은 신뢰된 내부 호출자가 설정해야 한다. 조회자가 보낸 route 목록이나 상세 요청을 그대로 권한으로 받아들여서는 안 된다. 요약 접근 권한과 상세 접근 권한은 구분한다. 집계 지표를 조회할 수 있다는 이유로 비교 이벤트나 상세까지 제공해서는 안 된다.

파일 권한과 SQL 행 삭제는 저장 암호화나 백업 삭제를 보장하지 않는다. 만료 정리 결과를 삭제된 DB 페이지의 복구 불가 보장으로 해석해서는 안 된다. 암호화, 백업 보존 및 저장 매체 폐기 조건은 운영자가 별도로 정하고 확인해야 한다.

## 조회 절차

다음 절차는 조회자가 수행한다. Event ID로 사례를 좁히더라도 기간, route 및 행 수의 상한을 생략하지 마십시오.

1. 조사할 route를 지정하십시오.
2. 이벤트 생성 시각을 기준으로 조회 시작 시각과 종료 시각을 지정하십시오.
3. 조회할 최대 행 수를 지정하십시오.
4. 조사 목적에 맞는 추가 조건을 지정하십시오.
5. 지정한 조건으로 조회를 실행하십시오.
6. 조회가 오류 없이 완료되면 반환된 행의 비교 상태와 수집 상태를 확인하십시오.

### 조회 기능의 자동 처리

조회 기능은 다음 조건을 모두 확인한다. 조건을 하나라도 충족하지 못하면 조회를 거부한다.

| 검증 대상 | 조회를 허용하는 조건 |
| --- | --- |
| route | route 집합이 비어 있지 않고, 모든 route가 허용 범위 안에 있다. |
| 기간 | 종료 시각이 시작 시각보다 뒤이고, 조회 기간이 허용 기간 상한 이하이다. |
| 행 수 | 요청 행 수가 양의 정수이고, 허용 행 수 상한 이하이다. |

조건이 유효하면 조회 기능은 지정한 필터를 모두 적용한다. Backend와 역할·배포 revision을 함께 지정한 경우에는 같은 backend의 조건으로 해석한다.

조회 기간은 이벤트 생성 시각을 기준으로 시작 시각을 포함하고 종료 시각은 제외한다. 요청 시작 시각을 기준으로 하는 구간과 혼동하지 마십시오. 요약 만료 시각이 조회 시각과 같거나 더 이르면 조회 기능은 해당 행을 반환하지 않는다.

상세 권한이 없거나 상세 만료 시각이 조회 시각과 같거나 더 이르면 조회 기능은 요약만 제공한다. 상세를 제공하지 않았다는 사실만으로 마스킹 실패나 상세 미선택을 추론하지 마십시오. 조회에서 제외되었다는 사실과 물리 삭제가 완료되었다는 사실은 별개이다.

행 수 상한이나 보존 만료 때문에 사례가 반환 목록에서 제외될 수 있다. 반환 목록을 전체 요청 집합으로 해석하지 마십시오. 조회 권한 거부, 조건 오류 또는 저장소 오류를 “일치하는 이벤트 0건”으로 표시하지 마십시오.

오류 없이 완료된 조회에서 0건을 받았더라도, 그 결과는 지정한 조건과 남아 있는 보존 데이터의 범위에 한정한다.

## 조회 시나리오

아래 목적별 조건은 앞 절의 필수 기간·route·행 수 제한에 추가하는 조건이다.

| 조사 목적 | 추가 조건 또는 조회 단서 | 결과에서 확인할 것 |
| --- | --- | --- |
| 신규 버전의 값 차이 조사 | `different`를 지정하십시오. | 비교 정책 revision, 허용된 차이 경로 및 양쪽 backend 상태를 확인하십시오. |
| 특정 적용 이후의 실패 조사 | configuration revision, backend 배포 revision 및 오류 이유를 지정하십시오. | 해당 backend의 역할·실행 지연과 관측 epoch를 확인하십시오. |
| 한 요청의 양쪽 결과 조사 | event ID를 사용하십시오. 검증된 trace 상관관계는 해당 이벤트를 찾는 단서로 사용할 수 있다. | Serving 선택, 입력 문맥, 양쪽 결과 및 저장 시각을 확인하십시오. |
| 수집·비교 한계 사례 조사 | `not_comparable`과 해당 `reason`을 지정하십시오. | 캡처 상한, 파싱 또는 데이터 문맥 중 판정을 제한한 조건을 확인하십시오. |

저장 이벤트만으로 전체 적격 요청 수 E나 선택 요청 수 S를 복원하지 마십시오. 두 분모는 [선택·실행 단계의 관측](../observability/coverage-and-analysis.md)에서 얻는다. 조회 행 수에는 드롭, ACK 미확인, 저장 지연 및 보존 만료의 영향이 있을 수 있다.

## 기본 CLI의 자동 정리 계약

현재 기본 CLI는 외부 스케줄러 없이 프록시 내부에서 만료 정리를 주기적으로 수행한다. SQLite와 PostgreSQL 모두 같은 정리 worker를 사용한다. 실행 구성은 [구현 구성](../implementation/README.md)에서 확인한다.

| 항목 | 요구되는 동작 |
| --- | --- |
| 실행 주기 | 양수인 주기를 설정하고, 한 주기마다 한 배치를 처리한다. 이전 정리 작업이 실행 중이면 중복 작업을 시작하지 않는다. |
| 배치 상한 | 한 배치에서 제거할 상세 수와 요약 수의 상한을 각각 적용한다. 배치 행 수 제한을 실행 시간 제한으로 해석하지 않는다. |
| 실패 관측 | 삭제 실패 횟수와 확인한 만료 적체를 내부 상태에 남긴다. DB 오류 원문이나 데이터 값을 로그로 내보내지 않는다. 확인하지 못한 삭제 수를 0으로 채우지 않는다. |
| 요청 처리 | 정리 작업은 사용자 응답 완료의 선행 조건이 되어서는 안 된다. 저장 쓰기와 정리의 경합을 포함해 처리 예산을 검증한다. |
| 종료 | 새 정리 작업을 중지하고 종료 유예 안에서 기다린다. 유예가 끝나면 정리 대기를 취소한다. 실제 DB 작업이 계속되면 자원을 추적하고, 대기 취소를 삭제 완료로 기록하지 않는다. |

정리 주기와 배치 크기는 실제 적재량과 삭제 처리량에 맞춰 정해야 한다. 만료 데이터가 계속 쌓이면 설정과 저장소 용량을 다시 평가해야 한다. 메모리 큐 상한은 DB 파일의 용량 상한이 아니다.

## 수동 만료 정리 절차

다음 절차는 만료 작업 담당자가 진단이나 복구를 위해 수행한다. `purge-events`로 수동 실행하는 경우에도 자동 정리와 같은 만료 조건을 적용한다. 입력은 저장 대상으로 확정한 보존 정책과 삭제 배치 상한이다.

1. 정리 작업에 적용할 보존 정책을 확인하십시오.
2. 정리 기준 시각을 확인하십시오.
3. 삭제 배치 상한을 지정하십시오.
4. 지정한 조건으로 만료 정리 작업을 실행하십시오.
5. 작업이 완료되면 삭제 결과와 남은 만료 데이터 수를 확인하십시오.

| 작업 결과 | 담당자의 처리 |
| --- | --- |
| 만료 데이터가 남아 있다. | 전체 정리가 완료되었다고 보고하지 마십시오. |
| 삭제가 실패했다. | 실패 상태를 남기십시오. |
| 삭제 수를 확인하지 못했다. | 미확인 삭제 수를 0 또는 성공으로 채우지 마십시오. |

한 번의 배치 완료와 해당 기준 시각까지의 만료 데이터 전체 정리 완료를 구분하십시오. 배치 상한 없이 전체 데이터를 한 번에 정리하는 동작을 전제하지 마십시오.

### 정리 기능의 자동 처리

정리 기능은 다음 순서로 처리한다.

1. 상세 만료 시각이 기준 시각과 같거나 앞선 데이터를 배치 상한 안에서 제거한다.
2. 상세를 제거한 요약의 상세 상태를 만료로 표시한다.
3. 요약 만료 시각이 기준 시각과 같거나 앞선 이벤트를 배치 상한 안에서 제거한다.
4. 실제 삭제한 상세 수, 요약 수 및 남은 만료 데이터 수를 반환한다.

정리 기능은 반복 실행하거나 중단 후 재개해도 같은 만료 조건을 적용한다. 만료되지 않은 데이터를 삭제해서는 안 된다. 요약보다 상세가 오래 남는 고아 데이터를 만들어서는 안 된다. 별도 보존 근거가 없으면 상세의 보존 기한은 요약보다 늦어서는 안 된다.

운영 환경의 조회·삭제 배치 크기와 범위 상한은 저장소를 선택한 뒤 실제 적재량으로 검증해야 한다. SQLite와 PostgreSQL 모두 한 배치의 성공과 만료 적체 전체의 해소를 구분해야 한다.
