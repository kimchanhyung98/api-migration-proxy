# 비동기 적재·재시도·유실 처리

수집 경로는 사용자 응답을 전달하는 경로와 분리하여 비교, 마스킹 및 저장을 수행한다. 저장 장애가 발생해도 serving 응답이 저장 완료를 동기적으로 기다리게 해서는 안 된다. 이 분리는 메모리 큐의 무손실 보존을 보장한다는 뜻이 아니다.

메트릭은 프록시 내부에서 실행 단계별로 집계한다. 이 집계와 비교 이벤트 저장은 독립적이다. 이벤트를 저장하지 못해도 이미 관측한 요청·실행·비교 집계를 표본 행 수로 대체해서는 안 된다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | backend 실행 결과, 사용자 응답 전송 종료 결과, 제한된 캡처, 큐·배치·작업 시간·저장 재시도 예산을 사용한다. |
| 결과·출력 | 고유 이벤트의 저장 결과와 큐 체류 시간, 저장 지연, 저장 실패 및 감지된 드롭을 구분해 남긴다. |
| 실패·제한 | 프로세스 메모리 큐는 강제 종료 시 유실될 수 있다. 저장 장애 때문에 serving이 동기 대기하도록 연결해서는 안 된다. |

## 수집 생명주기

Serving과 shadow의 실행은 독립적으로 진행된다. 비교 큐 제출 전에 두 실행과 사용자 전송의 종료 결과가 필요하다. 수집 경로는 다음 순서로 자동 처리한다.

1. 실행 중 최소 메타데이터와 비교에 필요한 제한된 캡처를 수집한다.

   본문 수신과 사용자 본문 전송은 별도로 취급한다.

2. 비교에 필요한 종료 결과를 확정한다.

   Serving backend 종료, shadow 종료 또는 미실행, 사용자 전송의 완료·취소·실패가 모두 확정되어야 한다.
   하나라도 끝나지 않았으면 최종 비교 요약을 제출하지 않는다.
   Shadow deadline이나 backend 수신 완료를 사용자 응답 완료로 대신 기록하지 않는다.

3. 비교 작업을 수량·크기 상한이 있는 큐에 제출한다.

   제출할 수 없으면 드롭 사유를 계측한다.
   선택된 shadow가 미실행이어도 나머지 종료 결과가 확보되면 `not_executed` 요약 생성을 시도한다.

4. 비교 작업의 남은 수명을 확인한다.

   수명이 끝났으면 작업을 드롭한다.

5. 수명이 남은 작업에 비교 정책을 적용한다.

   비교 처리가 실패하여 유효한 요약을 만들 수 없으면 수집 작업을 드롭한다.
   수집 작업 실패를 backend 실행 실패로 바꾸어 기록하지 않는다.

6. [상세 표본·마스킹 절차](detail-sampling.md)에 따라 저장 허용 필드만 남긴다.

   상세 생성에 실패해도 이미 안전하게 생성한 요약은 저장 대상으로 유지한다.

7. 저장소에 제한된 크기의 이벤트 배치 저장을 요청한다.

8. 저장소 응답을 고유 event ID별로 해석한다.

   재시도가 필요하면 아래의 시간·횟수 예산과 ACK 규칙을 적용한다.

9. 작업의 종료 상태를 남긴다.

   종료 상태는 저장 확인, 확정 실패에 따른 드롭 또는 ACK 미확인이다.
   각 상태의 이벤트 수와 저장 시도 실패 횟수를 구분한다.

만료 데이터 정리는 위 절차로 생성된 요약·상세를 대상으로 하는 별도 [보존 절차](query-and-retention.md)이다. 새 이벤트 저장마다 모든 만료 데이터 삭제가 완료된다고 가정해서는 안 된다.

큐 대기, 비교, 마스킹 및 저장 재시도의 경과 시간을 수집 작업의 수명 판단에 포함해야 한다. 저장 큐에 들어갔다고 시작 시각을 새로 잡거나, 재시도마다 최대 수명을 다시 부여해서는 안 된다.

비동기 작업의 timeout은 실행 중인 CPU 작업을 선점해 중단한다는 뜻이 아니다. 현행 비교·마스킹 작업은 응답 처리와 분리된 worker에서 수행한다. 기다림이 끝났어도 실제 계산이 남아 있으면 입력과 실행 자원을 계속 추적한다. 같은 event loop에서 동기 파싱·비교·마스킹을 수행하는 구성은 CPU 격리를 보장하지 않는다. 이 제약은 [Python asyncio 실행 지침](https://docs.python.org/3/library/asyncio-dev.html#running-blocking-code)을 참고한다.

실행 위치와 자원 예산은 허용 최대 입력량·복잡도, 동시 처리 및 연속 취소 부하에서 검증해야 한다. 검증 대상은 serving 지연, 기다림 종료 후 남은 작업 및 메모리 상한이다. 별도 process나 worker 구성은 이 예산을 만족하는 데 필요한 경우에 검토한다.

## SQLite와 PostgreSQL의 공통 저장 계약

기본 로컬 SQLite와 선택 구성인 사설 PostgreSQL에는 다음 계약을 동일하게 적용해야 한다. 다른 저장소를 연결할 때에도 [이벤트의 데이터 보호 경계](event-model.md#요약의-데이터-보호-경계)를 먼저 적용한다.

| 항목 | 공통 계약 |
| --- | --- |
| 저장 입력 | 허용된 요약과 마스킹을 통과한 상세만 전달한다. 원본 요청·응답, 인증 정보 및 예외 원문을 저장 호출이나 진단 로그에 추가하지 않는다. |
| 성공 확인 | 해당 event ID의 행을 확정한 뒤 저장 ACK를 반환한다. 프로세스 메모리 버퍼나 DB로의 송신 완료를 저장 완료로 처리하지 않는다. |
| 중복 방지 | 같은 event ID의 재시도는 기존 행을 중복 생성하지 않는다. 재시도 때문에 최초 생성 시각이나 보존 만료 시각을 바꾸지 않는다. |
| 실패·미확인 | 확정된 저장 실패와 응답 유실·timeout에 따른 미확인을 구분한다. 연결이 끊겼다는 이유만으로 실제 저장도 취소되었다고 단정하지 않는다. |
| 조회·정리 | 같은 기간·route·행 수·상세 권한 제한과 요약·상세 만료 기준을 적용한다. 저장소가 바뀌었다는 이유로 무제한 조회나 무기한 보관을 허용하지 않는다. |
| 자원 상한 | 저장 연결, 실행 중 쓰기, 배치와 재시도에 상한을 둔다. 기다림이 끝나도 실제 작업이 입력을 보유하면 자원 예약을 유지한다. |

사설 PostgreSQL을 선택하면 데이터가 프록시 프로세스 밖의 DB로 이동한다. 연결 대상과 전송 필드를 운영자가 승인해야 한다. 이 선택은 공개 수집 endpoint나 외부 SaaS 전송을 활성화하는 동작이 아니다. 저장 ACK의 내구성 범위는 선택한 DB의 commit 정책에 따라 확인해야 한다. ACK만으로 백업, 복제본 복구 또는 무손실 장애 복구까지 검증되었다고 판단해서는 안 된다.

저장 어댑터의 배치 쓰기, 제한 조회 및 만료 정리는 각각 검증해야 한다. 하나의 기능을 연결했다는 사실로 나머지 기능의 연결도 완료되었다고 표현해서는 안 된다.

## 적재 상태와 재시도 경계

ACK는 저장소가 고유 event ID의 저장 성공을 확인한 응답을 뜻한다. 큐 제출 성공, 저장 호출 시작 또는 로컬 대기 종료는 ACK가 아니다. ACK를 받지 못했을 때에는 실제 저장소에 행이 남아 있을 수 있다.

| 상태 | 다음 동작 | 남길 증거와 해석 |
| --- | --- | --- |
| 큐 제출 성공 | 남은 작업 수명 안에서 비교·마스킹·배치 저장을 진행한다. | 제출·처리 시각과 대기 시간을 구분한다. 큐 제출을 저장 성공으로 집계하지 않는다. |
| 저장 시도 전 큐 포화·만료 | 해당 작업을 드롭한다. 사용자 응답은 수집 완료를 기다리지 않는다. | 감지한 드롭 사유와 이벤트 수를 남긴다. |
| 저장 성공 확인 | 해당 event ID를 완료 처리한다. 완료한 ID는 재시도 대상에서 제거한다. | 고유 ID별 저장 완료를 한 번만 집계한다. |
| 저장 실패 확인 | 남은 시간과 횟수 예산이 모두 있으면 같은 event ID로 재시도한다. | 저장 시도 실패와 최종 재시도 소진을 구분한다. |
| 저장 성공 여부 미확인 | 같은 event ID로 중복 방지 재시도를 수행하거나, 별도 재확인 근거를 확보한다. | 확인 전에는 ACK 미확인으로 유지한다. 저장소에서 확인되지 않은 성공을 집계해서는 안 된다. |
| 배치 일부 성공 | ID별 성공·실패·미확인을 분리한다. 성공이 확인되지 않은 ID만 재시도한다. | 성공한 행을 다시 생성하거나 같은 이벤트를 중복 완료로 집계해서는 안 된다. |
| 비교·마스킹 작업 오류 | 안전한 요약이 있으면 유지한다. 유효한 요약을 만들 수 없으면 드롭한다. | backend 실행 오류와 수집 작업 오류를 구분한다. 상세 마스킹 실패만으로 안전한 요약을 폐기하지 않는다. |
| 프로세스 강제 종료 | 남은 메모리 작업의 유실 가능 구간을 관측 해석에 반영해야 한다. | 정확한 마지막 유실 개수를 확인할 수 없으면 완전성 미확인으로 표시해야 한다. |

수집기는 다음 순서로 재시도를 처리한다.

1. 현재 배치에서 저장 성공을 확인한 ID를 제외한다.

   같은 이벤트에 새 ID를 발급하지 않는다.

2. 남은 이벤트별로 최대 수명과 남은 시도 횟수를 확인한다.

   시간과 횟수 예산이 모두 남아 있어야 재시도할 수 있다.

3. 예산이 남아 있으면 같은 event ID로 재시도한다.

4. 저장 성공을 확인한 ID를 한 번만 완료 처리한다.

   성공 여부가 충돌하거나 확인되지 않으면 성공으로 간주하지 않는다.

5. 예산이 끝난 이벤트의 종료 상태를 결정한다.

   저장 여부 미확인 시도가 남아 있으면 `ack_unknown`으로 종료한다.
   모든 시도의 실패가 확인되었으면 재시도 소진 또는 수명 만료에 따른 드롭으로 종료한다.

후속 시도의 실패 확인은 앞선 미확인 시도의 저장 여부까지 확정하지 않는다. `ack_unknown`은 수집 결과의 판정은 끝났지만 실제 저장 유무는 미확정인 상태이다. 재시도 횟수를 여러 이벤트의 유실 개수로 집계해서는 안 된다.

현행 수집기는 저장 응답 대기 시간이 끝나도 실행 중인 저장 작업을 취소하지 않는다. 이 경우 `ack_unknown`으로 판정을 종료하고, 실제 저장 작업이 끝날 때까지 이벤트 수와 바이트 예약을 유지한다. `queue_depth`와 `queue_bytes`에는 이 예약도 포함한다. 같은 저장 작업이 진행 중이면 중복 재시도를 시작하지 않는다. 뒤늦게 ACK를 받아도 종료한 판정을 `stored`로 바꾸거나 W를 늘리지 않는다. 종료 유예 시간이 끝나면 저장 작업의 완료를 더 기다리지 않고 반환하며, 남은 자원 예약은 실제 작업이 끝날 때 해제한다.

저장 확인된 고유 이벤트는 [W](../observability/coverage-and-analysis.md)에 해당한다. `not_executed`, `execution_error` 또는 `not_comparable` 이벤트도 저장이 확인되면 W에 포함될 수 있다. 반대로 비교가 완료되었어도 저장 ACK가 미확인이면 그 사실만으로 W에 포함해서는 안 된다.

알려진 드롭 개수와 관측 완전성 미확인은 서로 다르다. 마지막 유실 개수를 확인할 수 없는 구간을 0으로 채워서는 안 된다. 모든 관측의 보존이 필수인 요구가 생기면 내구성 기록 경로, 내부 큐 수명 및 사용자 응답 대기 계약을 함께 재검토해야 한다.
