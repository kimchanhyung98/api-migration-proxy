# 제품 요구·설계 기준·위험 관리

- 범위: 현행 기능 기획의 제품 요구·설계 기준과 주요 위험
- 제품 구현·성능·운영 전환: 검증 전

## 결정 수준

| 상태 | 의미 |
| --- | --- |
| 제품 요구 | 제품의 목적·방향과 문서 관리 원칙 |
| 현행 설계 기준 | 현재 기능 기획의 기준; 실제 구현·운영 검증과 구분 |
| 제안 | 채택·검증 전의 초기 설계 |

| 검증됨 | 재현 가능한 실제 증거가 있는 사항에만 사용 |

- 제품 구현·성능·운영 전환: 검증 전

## 현행 설계 기준

| ID | 기준 | 이유 | 재검토 조건 |
| --- | --- | --- | --- |
| D-01 | 부작용 없는 일반 HTTP JSON API부터 적용 | 효과·전달·비교의 초기 검증 범위를 작게 유지 | 첫 대상이 쓰기·stream·stateful API인 경우 |
| D-02 | 한 프록시 서비스와 내부 제한 큐 | 별도 브로커·비교 서비스 없이 시작 | 무손실 기록, CPU·메모리·장애 격리가 한계에 도달 |
| D-03 | serving·shadow·상세 저장 비율 분리 | 사용자 노출·검증 부하·저장 비용이 다른 목적 | 양방향 shadow 예산 또는 비교 자체의 별도 표본이 필요 |
| D-04 | serving 하나를 사전 선택하고 shadow와 독립 반환 | 느린 비교·저장이 응답 선택을 바꾸지 않음 | 별도의 hedging·fallback 요구가 확인됨 |
| D-05 | 자동 retry·fallback 비활성 | 중복 실행과 숨겨진 신규 오류·부하 증폭을 줄임 | 명시적 가용성 요구와 재시도 안전성이 검증됨 |
| D-06 | 필요한 그룹은 stable cohort, 무상태 API만 요청 배정 허용 | 사용자·연관 API 일관성과 단순성의 균형 | backend 종속 세션·cursor가 필요 |
| D-07 | 정책별 JSON 의미 비교와 오류·문맥·유실 분리 | 단순 문자열 동일성이나 성공 표본만의 왜곡 방지 | 검색 순위·확률적 결과 등 업무별 규칙이 필요 |
| D-08 | 요약 우선, 상세 기본 비활성 | 저장 비용·데이터 노출을 제한하면서 조사 가능 | 실제 불일치 조사에 특정 상세 필드가 필요 |
| D-09 | 버전 있는 설정과 수동 stage 변경 | 관리 UI·제어 플랫폼 없이 운영 시작 | 운영 대상 수·변경 빈도가 기존 방식 한계를 넘음 |
| D-10 | 데이터 동기화는 서비스·데이터 계층의 책임 | 임시 프록시에 쓰기·분산 복구 책임이 늘어나는 것을 방지 | 제품 자체가 쓰기 마이그레이션을 명시적으로 담당하게 됨 |
| D-11 | v1 준비 기간과 최종 프록시 제거를 별도 단계로 둠 | 비율 100%와 종료·복구 가능성은 다른 상태 | 프록시를 상시 공통 진입점으로 유지하려는 요구가 생김 |

- D-01~D-11: 현재 기능 기획의 설계 기준; 기술 스택·운영 수치의 확정과 구분
- 기준 변경 시 기록: 결정일·책임자·대안·영향·검증 조건
- 관련 요구사항·테스트 갱신 후 결정 상태 반영

## 주요 위험과 대응

| ID | 위험 | 감지 | 대응 설계 | 남는 한계 |
| --- | --- | --- | --- | --- |
| R-01 | 양쪽 실행의 업무 부작용 | 효과 목록·실제 API 테스트 | 초기 read-only eligibility와 별도 write 계약 | GET만으로 안전성을 보장 못 함 |
| R-02 | shadow가 공유 의존을 과부하 | 양쪽 QPS·DB·quota·사용자 지연 | 표본·동시 실행·전체 예산 제한 | 프로세스 내 pool 분리만으로 DB 격리 안 됨 |
| R-03 | 비교 완료된 빠른 사례만 남음 | E/S/D/T/C/W와 reason 분포 | 오류·취소·드롭·큰 응답을 별도 노출 | 심한 관측 장애에서는 정확한 분모도 불명 |
| R-04 | 데이터 시차를 코드 회귀로 오판 | source·freshness·동일 입력 검토 | route별 문맥 계약과 제한 판정 | 실시간 데이터의 완전 동일 시점 보장 어려움 |
| R-05 | 과한 정규화로 중요한 차이 은폐 | 제외 규칙 검토·fixture·정책 변경 이력 | 필요한 필드만 제외, 핵심 불변식 유지 | 잘못된 계약 자체는 별도 검토 필요 |
| R-06 | 동일한 권한 오류를 양쪽이 공유 | tenant·권한 contract test | 비교와 별도 불변식 검증 | v1을 절대적 정답으로 삼을 수 없음 |
| R-07 | 저장소 장애·재시작으로 관측 유실 | 드롭·age·heartbeat·저장 지연 | 제한 큐·배치·중복 방지·unknown 구간 표시 | 내부 메모리 큐는 무손실 보장 안 함 |
| R-08 | 배정 키·salt 변경으로 집단이 섞임 | revision·그룹·배정 분포 | 안정된 키·해시, 새 epoch 분리 | 요청량 차이로 실제 QPS 비율은 달라짐 |
| R-09 | v1은 살아 있지만 복귀 불가 | 데이터·schema·capacity 검증 | 복귀 gate·기간·실제 연습 | 파괴적 데이터 변경은 라우팅으로 복구 못 함 |
| R-10 | 프록시가 공통 장애점이 됨 | 사용자 오류·readiness·리소스 | 최소 구성 검증, 배포·우회 경로 | 운영 replica·장애 영역 결정 필요 |
| R-11 | 원문·token이 관측에 저장됨 | 합성 비밀을 넣은 검증·필드 감사 | 허용 필드·마스킹·보존·권한 | 기존 주변 로그 경로도 확인 필요 |
| R-12 | 임시 프록시가 상시 업무 계층으로 확대 | route 매핑·비교 밖 기능 증가 | 범위와 종료 조건을 요구사항으로 유지 | 의도적으로 장기화하면 제품 범위 재결정 |

## 후속 결정 기록 양식

```text
decision_id / date / owner:
question / affected_routes:
alternatives:
chosen_option / reason:
assumptions / accepted_limitations:
affected_requirements / tests / gates:
evidence / review_trigger:
status: proposed | decided | superseded
```

- 별도 이슈 트래커·ADR 시스템의 도입은 필수 범위에서 제외
- 결정한 항목부터 해당 본문 또는 기존 조직 기록 방식으로 관리

## 기술 선택 기준

- 기술 후보·운영 수치의 미정 상태 유지; 기능 기획의 기준을 제품·버전·운영값의 채택 결정으로 해석 금지
- 후보 제품의 공식 기능과 본 제품의 요구사항 충족 여부 구분
- 채택 조건: 해당 제품·버전의 지원 범위 확인과 실제 요청·부하·장애 테스트
- 세부 기준: [기술 자료 적용과 검증 기준](../_rules/technology-evaluation.md)
