# 제품 요구·설계 기준·위험 관리

이 문서는 제품 요구, 현행 설계 기준, 주요 위험과 대응의 한계를 정의한다. 구현 스택은 Python/FastAPI이다. 내부 계측·비교·정보 보호·제한 큐를 기본 구성으로 삼는다. 운영 실행 인프라, 외부 관측 제품과 대상 API별 운영 수치는 미정이다. 제품 역할과 책임은 [제품 개요](overview.md)를, serving, shadow, cohort, stage, epoch의 의미는 [공통 용어](../_rules/glossary.md)를 따른다.

## 결정 수준

| 상태 | 의미 |
| --- | --- |
| 제품 요구 | 제품이 달성해야 할 목적과 방향, 문서 관리 원칙이다. |
| 현행 설계 기준 | 현재 제품에 적용하는 설계상의 기준이다. 기준을 채택한 사실과 특정 실행 환경에서 충족을 검증한 사실은 구분해야 한다. |
| 제안 | 채택 여부를 결정하지 않은 설계안이다. 제안이 문서에 있다는 이유로 현재 제품의 필수 구성이나 구현된 기능으로 간주해서는 안 된다. |
| 미정 | 실제 환경, 선호 또는 계약 정보가 부족하여 결정하지 않은 항목이다. 필요한 결정과 그 결정에 영향을 받는 적용 절차를 확인해야 한다. |
| 검증됨 | 검증 대상, 조건, 결과를 재현 가능한 실제 증거로 확인한 상태이다. 증거가 적용되는 환경과 범위를 함께 명시해야 한다. |

현행 기준에 따른 구현 책임은 [구현 구성](../implementation/README.md)에 정리되어 있다. 운영 환경이 미선정이라는 사실은 이미 구현된 구성 요소가 구현 대기 상태라는 의미가 아니다.

## 제품 요구

| ID | 요구 |
| --- | --- |
| U-01 | Elasticsearch 마이그레이션의 요청 분기·응답 선택·관측 원리를 일반 API Migration Proxy에 적용해야 한다. |
| U-02 | 제품 요구를 충족하는 범위에서 구성을 최대한 단순하게 유지해야 한다. |
| U-03 | 복제 가능한 요청을 대상으로 v1/v2 양쪽 실행, 내부 메트릭과 보호된 이벤트 수집을 제공해야 한다. 외부 수집기나 SaaS를 필수 구성으로 요구하지 않는다. |
| U-04 | 사용자 응답을 v1에서 v2로 점진적으로 전환할 수 있어야 한다. |
| U-05 | Proxy는 Python/FastAPI를 기반으로 한다. 실행 환경과 저장소는 실제 운영 조건에 따라 선정한다. 외부 관측 제품은 필요한 경우에만 별도로 선택한다. |
| U-06 | 도메인별 문서는 적용 조건, 동작, 실패와 책임 경계를 독립적으로 이해하고 유지할 수 있도록 상세하게 작성해야 한다. |

## 현행 설계 기준

| ID | 기준 | 이유 | 재검토 조건 |
| --- | --- | --- | --- |
| D-01 | 부작용 없는 일반 HTTP JSON API부터 적용한다. | 업무 효과, 전달, 비교의 초기 검증 범위를 제한한다. | 첫 대상이 쓰기, 스트림 또는 상태를 유지하는 API인 경우 재검토한다. |
| D-02 | 한 프록시 서비스 안에서 계측·비교·정보 보호를 처리하고 제한된 수집 큐를 둔다. | 별도 수집기, 브로커 또는 비교 서비스를 초기 필수 구성으로 요구하지 않는다. | 무손실 기록 요구가 생기거나 CPU·메모리·장애 격리 요구를 현재 구성으로 충족하지 못하면 재검토한다. |
| D-03 | serving 비율, shadow 비율, 상세 저장 표본율을 분리한다. | 사용자 노출, 검증 부하, 저장 비용은 서로 다른 제어 대상이다. | 양방향 shadow에 서로 다른 예산이 필요하거나 비교 자체에 별도 표본 정책이 필요하면 재검토한다. |
| D-04 | 요청마다 serving 하나를 사전 선택한다. 사용자 응답은 shadow 결과와 독립적으로 반환한다. | 느린 비교나 저장 때문에 응답 출처가 바뀌지 않게 한다. | 다른 backend를 함께 실행하여 응답을 선택하는 hedging 또는 fallback 요구가 별도로 확인되면 재검토한다. |
| D-05 | backend 요청의 자동 retry와 fallback을 비활성화한다. | 중복 실행, 숨겨진 신규 오류, 부하 증폭을 줄인다. | 명시적인 가용성 요구와 재시도 안전성이 검증되면 재검토한다. |
| D-06 | 배정 일관성이 필요한 그룹에는 안정적인 cohort를 사용한다. 요청 단위 배정은 무상태 API에만 허용한다. | 사용자와 연관 API의 일관성을 유지하면서 불필요한 상태 관리를 제한한다. | backend에 종속된 세션이나 cursor가 필요하면 재검토한다. |
| D-07 | 정책별로 JSON의 의미를 비교한다. 실행 오류, 비교 문맥, 관측 유실은 서로 구분한다. | 단순 문자열 동일성이나 성공한 표본만으로 판단하는 왜곡을 방지한다. | 검색 순위나 확률적 결과처럼 업무별 비교 규칙이 필요하면 재검토한다. |
| D-08 | 허용된 요약을 접근이 제한된 저장소에 수집한다. 메트릭·상태의 HTTP 조회는 제공하지 않는다. 상세 수집은 기본 비활성으로 두며, 외부 관측 SDK·exporter는 연결하지 않는다. | 내부 관측을 유지하면서 저장 비용과 데이터 노출을 제한한다. | 상세 조사나 여러 인스턴스의 지표 합산이 필요하면 내부 조회·저장 범위를 검토한다. |
| D-09 | 버전이 있는 설정과 수동 stage 변경을 사용한다. | 별도 관리 UI나 동적 제어 플랫폼을 초기 필수 구성으로 요구하지 않는다. | 운영 대상 수나 변경 빈도를 기존 방식으로 관리할 수 없으면 재검토한다. |
| D-10 | 데이터 동기화는 서비스·데이터 계층에서 담당한다. | 임시 프록시에 쓰기와 분산 복구 책임이 추가되지 않게 한다. | 제품이 쓰기 마이그레이션을 명시적으로 담당해야 한다는 요구가 생기면 재검토한다. |
| D-11 | v1 복귀 준비를 유지하는 기간과 최종 프록시 제거를 별도 단계로 관리한다. | v2 비율 100%, 복귀 가능 상태, 마이그레이션 종료는 서로 다른 상태이다. | 프록시를 상시 공통 진입점으로 유지해야 한다는 요구가 생기면 재검토한다. |

D-01~D-11은 제품의 설계 기준이다. 채택한 기본 정책과 현재 실행 진입점에 연결된 기능은 [구현 구성](../implementation/README.md)에서 대조해야 한다. 이 기준만으로 특정 운영 인프라, 외부 관측 제품이나 운영 수치를 확정하지 않는다. D-02의 한 서비스는 하나의 논리 배포 서비스를 뜻한다. 현재 기본 CLI는 단일 프로세스이며 여러 인스턴스의 지표·revision 통합은 별도 책임이다. D-05의 retry는 backend 요청의 재실행을 뜻하며, [관측 저장의 제한된 재시도](../collection/async-storage.md)와 구분한다.

이벤트 저장소는 단일 호스트의 로컬 SQLite 또는 필요에 따라 사설 PostgreSQL을 선택한다. 여러 호스트의 동시 쓰기, 쓰기 경합, 보존·조회 요구를 근거로 선택해야 한다. 저장소를 공유하는 기능과 프로세스별 메트릭을 합산하는 기능은 구분한다. 선택 조건은 [실행 구조와 저장소](../infrastructure/deployment-and-stack.md)를 따른다.

메트릭·상태의 HTTP endpoint와 활성화 설정은 제공하지 않는다. 내부 계측·snapshot·상태 조회·비교·정보 보호·제한 큐는 계속 동작해야 한다. 선택한 이벤트 저장소에 기록하는 동작은 Proxy 외부 수신 주체로 메트릭·로그·trace를 전송하는 기능과 구분한다. 외부 수신 주체에는 조직 내부의 별도 수집기도 포함한다.

health는 별도 loopback listener의 `GET /healthcheck`로 통합한다. 요청 수락 준비 상태이면 200, 준비되지 않았으면 503과 최소 본문을 반환한다. 실제 접속 peer도 loopback인지 확인해야 한다. 기존 health 경로의 alias와 token으로 외부 접속을 허용하는 예외는 제공하지 않는다. 사용자 API 전달 포트도 인터넷에 직접 공개하지 않는 배포 구성을 사용해야 한다.

관측 자료는 기본적으로 승인된 사설 접근 경계 안에 보관한다. 외부 전송은 수신 주체와 허용 필드가 승인된 경우에만 검토한다. 조직 밖이나 SaaS로 보내려면 해당 데이터 반출 조건도 충족해야 한다. 계측 규격이나 특정 도구를 선택했다는 이유로 외부 전송을 자동 활성화해서는 안 된다.

재검토 조건에 해당하면 변경 필요성을 판단해야 한다. 조건에 해당한다는 이유만으로 기존 기준이 자동 폐기되는 것은 아니다. 기준 변경의 책임자는 다음 절차를 수행한다.

1. 결정일, 책임자, 검토한 대안, 선택 이유, 영향 범위, 검증 조건을 기록하십시오.
2. 영향을 받는 요구사항과 검증 항목을 변경 내용에 맞게 갱신하십시오.
3. 채택 여부에 맞춰 결정 상태를 반영하십시오.

   - 검증 증거가 없는 항목에 `검증됨` 상태를 사용하지 마십시오.

## 주요 위험과 대응

아래 감지 항목과 대응은 위험을 확인하거나 제한하기 위한 기준이다. 대응 수단을 적용한 사실만으로 마지막 열의 한계가 해소되었다고 판단해서는 안 된다. E/S/D/T/C/W와 비교 분모의 정의는 [비교 커버리지](../observability/coverage-and-analysis.md)를 따른다.

| ID | 위험 | 감지 | 대응 설계 | 남는 한계 |
| --- | --- | --- | --- | --- |
| R-01 | 같은 요청의 양쪽 실행이 업무 부작용을 만든다. | API 효과 목록과 실제 API의 동작을 확인한다. | 초기 적용을 부작용 없는 API로 제한하고 쓰기 계약은 별도로 검토한다. | GET method라는 사실만으로 복제 안전성을 보장할 수 없다. |
| R-02 | shadow가 공유 의존 자원을 과부하시킨다. | 양쪽 QPS, DB 부하, 외부 호출 quota, 사용자 지연을 확인한다. | 표본율, 동시 실행 수, 전체 서비스 예산을 제한한다. | 프로세스 내부의 pool 분리만으로 공유 DB까지 격리되지는 않는다. |
| R-03 | 비교를 빨리 완료한 사례만 관측에 남는다. | E/S/D/T/C/W와 종료·누락 이유 분포를 확인한다. | 오류, 취소, 드롭, 큰 응답을 성공 표본과 구분하여 드러낸다. | 심한 관측 장애에서는 정확한 분모 자체를 알 수 없을 수 있다. |
| R-04 | 데이터 시차를 코드 회귀로 오판한다. | 데이터 원천, 최신성, 동일 입력 여부를 검토한다. | route별 문맥 계약을 정의한다. 허용 범위를 벗어난 비교에는 제한 사유를 기록한다. | 실시간 데이터의 완전히 동일한 관측 시점을 보장하기는 어렵다. |
| R-05 | 과도한 정규화가 중요한 차이를 숨긴다. | 제외 규칙, 고정 입력·기대 결과인 fixture, 정책 변경 이력을 검토한다. | 필요한 필드만 제외하고 중요 업무 불변식을 유지한다. | 잘못 정의한 계약 자체의 적절성은 별도 검토가 필요하다. |
| R-06 | v1과 v2가 동일한 권한 오류를 가진다. | 테넌트·권한 계약 검증 결과를 확인한다. | 양쪽 비교와 별도로 중요 불변식을 검증한다. | v1의 결과를 절대적인 정답으로 사용할 수 없다. |
| R-07 | 저장소 장애나 재시작으로 관측 자료가 유실된다. | 드롭, 대기 이벤트의 age, 프로세스 생존 신호인 heartbeat, 저장 지연을 확인한다. | 제한 큐, 배치, 중복 방지, 판단 근거가 없는 구간의 `unknown` 표시를 사용한다. | 내부 메모리 큐는 무손실을 보장하지 않는다. 이벤트 저장소가 프로세스 내 메트릭까지 보존하는 것은 아니다. |
| R-08 | 배정 키나 salt 변경으로 비교 집단이 섞인다. | revision, cohort group, 실제 배정 분포를 확인한다. | 안정적인 키와 해시를 사용한다. 관측 조건이 바뀌면 새 epoch로 분리한다. | 사용자별 요청량이 다르면 cohort 비율과 실제 QPS 비율도 달라진다. |
| R-09 | v1 프로세스는 살아 있지만 실제 복귀는 불가능하다. | 데이터, 스키마, 처리 용량의 복귀 조건을 확인한다. | 복귀 gate, 복귀 가능 기간, 실제 복귀 연습 결과를 사용한다. | 파괴적인 데이터 변경은 라우팅 변경만으로 복구할 수 없다. |
| R-10 | 프록시가 공통 장애점이 된다. | 사용자 오류, 요청 수락 준비 상태인 readiness, 자원 사용량을 확인한다. | 최소 구성의 동작, 배포, 우회 경로를 검증한다. | 운영 replica 수와 장애 영역 배치는 해당 환경에서 결정해야 한다. |
| R-11 | 원문이나 token이 저장·로그·조회·전송 경로에 노출된다. | 합성 비밀값을 넣은 검증과 각 경로의 허용 필드 감사를 수행한다. | 허용 필드, 마스킹, 보존 기간, 접근 권한을 적용한다. 관측 HTTP endpoint는 제공하지 않으며 외부 전송은 기본 구성에서 제외한다. | 집계값에도 운영 정보가 포함될 수 있다. 프록시 외의 기존 로그 경로에도 같은 접근 경계가 필요하다. |
| R-12 | 임시 프록시가 상시 업무 계층으로 확대된다. | route 매핑과 비교 범위 밖의 기능이 추가되는지 확인한다. | 제품 범위와 종료 조건을 요구사항으로 유지한다. | 장기 운영을 의도적으로 선택하면 제품 범위를 다시 결정해야 한다. |

## 후속 결정 기록 양식

기존 기준의 재검토나 미정 항목의 채택을 기록할 때는 아래 항목을 사용한다. 이 양식은 별도 이슈 트래커나 ADR 시스템의 도입을 요구하지 않는다. 해당 문서 본문 또는 조직의 기존 기록 방식으로 관리할 수 있다.

```text
decision_id / date / owner:
question / affected_routes:
alternatives:
chosen_option / reason:
assumptions / accepted_limitations:
affected_requirements / tests / gates:
evidence / review_trigger:
status: proposed | decided | superseded
```

`proposed`는 채택 전 제안, `decided`는 선택이 확정된 결정, `superseded`는 후속 결정으로 대체된 상태를 뜻한다. `decided`를 특정 환경의 검증 완료와 동일하게 취급해서는 안 된다. 검증 증거와 남은 한계는 별도 항목에 기록해야 한다.

## 기술 선택 기준

Python/FastAPI는 선정된 구현 스택이다. SQLite와 사설 PostgreSQL의 선택 조건은 위 저장 계약을 따른다. 그 밖의 운영 실행 환경, 외부 관측 제품과 운영 수치는 해당 결정을 뒷받침할 정보가 확보될 때까지 미정으로 유지해야 한다. 기능 요구사항을 후보 제품, 버전 또는 운영값의 채택 결정으로 해석해서는 안 된다.

후보 제품의 공식 기능과 이 제품의 요구사항 충족 여부는 구분해야 한다. 채택하려는 제품·버전의 지원 범위를 확인해야 한다. 실제 대상의 요청, 대표 부하, 장애 조건에서 요구사항을 충족하는 증거를 확보해야 한다. 세부 판단 기준은 [기술 자료 적용과 검증 기준](../_rules/technology-evaluation.md)을 따른다.
