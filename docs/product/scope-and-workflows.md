# 적용 범위와 사용자 흐름

이 문서는 첫 대상 API의 적용 가능 여부, 담당자가 수행할 행동, 초기 범위의 한계를 정의한다. 역할별 책임은 [제품 개요](overview.md#사용자와-책임)를, serving, shadow, route, cohort, epoch의 의미는 [공통 용어](../_rules/glossary.md)를 따른다. 기능 확장 여부는 아래 초기 범위 밖 항목의 선행 조건과 해당 기능의 검증 계약을 확인한 뒤 결정해야 한다.

## 주요 사용 시나리오

### 같은 계약을 유지한 API 재구현

상품 상세 조회를 다른 언어 또는 구조로 재구현하되 공개 계약을 유지하는 경우에 해당한다. API 개발자는 상품 ID, 가격, 판매 상태, 접근 권한처럼 유지해야 할 값을 비교 계약에 명시해야 한다. 비결정적인 요청 ID 등은 비교 정책에 명시한 경우에만 비교 대상에서 제외할 수 있다.

마이그레이션 담당자는 v1 사용자 응답을 유지한 상태에서 복제 대상으로 선택한 요청을 v2에서도 실행해야 한다. 관측한 차이의 원인을 설명할 수 있고 오류, 지연, 관측 품질 기준을 모두 충족한 경우에만 v2 serving 확대를 판단해야 한다.

### API 실행 인프라 교체

동일한 공개 계약을 다른 배포 환경으로 옮기는 경우에 해당한다. API 개발자와 운영 담당자는 결과 일치뿐 아니라 연결 timeout, 큰 응답의 전달, 인증 대상, 네트워크 지연, 데이터 접근 지연을 확인해야 한다.

일부 요청을 shadow로 처리한 결과만으로 전체 v2 serving 용량을 판정해서는 안 된다. 운영 담당자는 전체 사용자 요청을 v2에서 처리하는 경로의 목표 부하와 지연을 별도로 검증해야 한다.

### 의도적인 응답 구조 변경

v2 내부 필드를 변경하면서 호출자가 사용하는 공개 계약을 유지해야 하는 경우에 해당한다. API 개발자는 비교를 시작하기 전에 API 측의 호환 응답 또는 필요한 범위의 명시적 매핑을 결정해야 한다.

비교용 필드 매핑은 비교 결과를 해석하는 규칙이다. 해당 매핑을 정의했다고 해서 사용자에게 전달하는 응답이 자동으로 호환되는 것은 아니다. 공개 계약을 깨는 변경은 클라이언트 마이그레이션과 함께 별도로 검토해야 한다.

### 일부 요청에서만 실패하는 신규 버전 조사

특정 데이터 크기 또는 입력군에서 v2 timeout이 증가하는 경우에 해당한다. 마이그레이션 담당자는 route, 응답 크기 구간, 실행 결과별로 완료율과 지연을 나누어 확인해야 한다. 상세 입력이 필요한 조사에는 수집 정책에서 허용한 상세 표본만 사용해야 한다.

수집하지 않은 입력을 임의로 복원하거나 운영 요청을 자동으로 재전송해서는 안 된다. 조사에 필요한 표본이 없으면 원인이 확인되었다고 기록하지 말고, 미확인 조건을 남겨야 한다.

### 전환 후 되돌리기

v2 serving의 사용자 오류가 증가한 경우 마이그레이션 담당자는 먼저 신규 비율 확대를 중지해야 한다. v1으로 복귀하려면 v1이 현재 데이터와 계약을 해석할 수 있고, 권한과 목표 부하를 처리할 조건을 충족하는지 확인해야 한다.

serving 복귀는 변경 적용 이후 요청의 배정을 바꾸는 조치이다. 이미 실행 중인 v2 요청을 무조건 v1에서 재실행해서는 안 된다. 프록시 자체에 장애가 있으면 serving 비율 변경과 구분하여 사전에 검증한 우회 경로를 사용해야 한다. 구체적인 판단과 조치는 [복귀와 우회](../rollout/rollback-and-bypass.md)를 따른다.

## 운영자의 사용 흐름

아래 절차는 마이그레이션 담당자가 대상 route 또는 cohort group에 적용한다. API 개발자, 운영 담당자, 데이터 담당자는 각 책임에 해당하는 계약과 증거를 제공한다.

시작 전에 [첫 대상의 준비 목록](../rollout/stages-and-gates.md#첫-대상의-준비-목록)을 확인하십시오. 준비 대상은 API 계약, 부작용, 데이터·권한 관계, 대표 부하, 비교·수집 정책, 품질 기준, 복귀 수단이다. 판단에 필요한 값이나 증거가 미정이면 해당 단계의 통과로 처리하지 마십시오.

1. 대상 route, v1/v2 목적지, 인증·입출력 계약을 등록하십시오.
2. 설정에 중복, 충돌, 필수값 누락이 없는지 검토하십시오.

   - 오류가 있으면 설정을 수정하십시오. 수정 후 2단계의 검토를 반복하십시오.

3. v1 serving과 shadow 비율 0을 지정한 설정을 적용하십시오.
4. 실제 적용 revision과 v1 serving 분포가 의도한 설정과 일치하는지 확인하십시오.

   - 적용이 누락되었거나 불일치하면 다음 단계로 진행하지 마십시오.

5. v1 직접 경로 대비 프록시의 추가 영향을 기준선으로 기록하십시오.

   - 기준선이 품질 기준을 충족하지 않으면 shadow를 확대하지 마십시오.

6. 대상 API에 정한 작은 shadow 표본 비율을 적용하십시오.
7. shadow의 선택, 실제 실행, 종료, 비교, 저장 개수와 각 실패 사유를 확인하십시오.

   - 설정된 표본 비율만으로 실제 양쪽 실행 또는 저장이 완료되었다고 판단하지 마십시오.

8. 차이와 누락 사례를 조사하십시오.

   - 조사에는 같은 요청의 양쪽 결과, 비교 정책, 권한·데이터 문맥, 캡처·실행 제한 사유가 필요하다.
   - 근거가 부족한 사례는 미확인으로 남기십시오.

9. [승격 gate](../rollout/stages-and-gates.md#승격-gate)가 다음 v2 비율 확대를 허용하는지 판단하십시오.

   - 미확인 사례를 제외한 성공 표본만으로 판단하지 마십시오.
   - 확대가 허용되지 않으면 다음 비율을 적용하지 마십시오.

10. 확대가 허용되면 다음 v2 응답 비율을 적용하십시오.
11. 실제 적용 revision과 serving 분포가 변경한 설정과 일치하는지 확인하십시오.
12. 해당 epoch의 사용자·비교 지표를 기록하십시오.

    - 전체 v2 serving에 도달하지 않았고 관측 기준이 충족되면 9단계에서 다음 확대를 판단하십시오.
    - 조건을 충족하지 못하면 추가 확대를 중지하십시오.

13. 전체 v2 serving이 기준을 충족하면 [종료 기준](../rollout/retirement.md)에 따라 종료를 수행하십시오.

    - 종료 판단에는 잔존 v1 의존, 데이터 복귀 기간, v1 shadow 중지 영향, 직접 v2 연결의 증거가 필요하다.
    - 각 종료 결과를 따로 기록하십시오.
    - v2 비율 100%만으로 v1 전체 사용 종료 또는 프록시 제거를 완료 처리하지 마십시오.

어느 관측 단계에서든 품질이 악화되면 추가 확대를 중지하십시오. 장애 원인에 따라 shadow 중지, 준비된 v1으로의 serving 복귀, 프록시 우회 중 필요한 조치를 선택하십시오. 조치 후에는 변경 전후 비율, 적용 지연, 실제 요청 경로, 사용자 지표의 회복을 확인하십시오. 이 장애 대응은 정상 확대 절차와 구분한다.

각 설정 변경은 의도한 값이 기록된 시점과 실제 요청에 적용된 시점을 구분해야 한다. 단계 판단이 설정 배포를 자동으로 수행한다는 의미는 아니다. 상세 변경 절차는 [설정 변경 운영](../rollout/change-management.md)을 따른다.

초기 운영은 설정 파일, 기존 배포 방식, 프록시 내부 계측과 제한된 이벤트 조회를 사용한다. 기존 모니터링과의 연동은 필요한 경우에만 선택한다. 전용 웹 콘솔은 초기 필수 범위에 포함하지 않는다. 운영 화면을 사용하는 경우에는 판단에 필요한 상태를 제공해야 하며, 내부 큐나 DB 구현 상세를 운영자의 판단과 무관하게 노출할 필요는 없다.

메트릭·상태를 내보내는 HTTP endpoint나 활성화 설정은 제공하지 않는다. 내부 snapshot·상태 조회와 이벤트 조회는 유지한다. 상태 확인에는 별도 loopback listener의 `GET /healthcheck`만 사용한다. 사용자 API 요청은 기존 전달 포트로 처리하며, 해당 포트를 인터넷에 직접 공개하지 않는 배포 구성을 사용해야 한다.

## MVP 범위

MVP는 이 문서에서 정한 초기 제품 범위를 뜻한다. 현재 구현의 구성별 책임은 [구현 구성](../implementation/README.md)을 따른다.

| 포함 범위 | 이유 |
| --- | --- |
| 유한한 일반 HTTP JSON API와 경로별 등록 | 전달, 비교, 실패의 경계를 명확하게 검증할 수 있다. |
| 부작용이 없다고 명시적으로 확인한 API의 양쪽 실행 | 중복 실행으로 업무 결과가 바뀌는 문제를 초기 범위에서 제한한다. |
| serving 선택과 반대편 shadow | 사용자 노출 비율과 검증 부하를 독립적으로 제어한다. |
| 기본 JSON, 상태 코드, 필수 헤더 비교 | 같은 논리 요청의 계약 회귀를 확인한다. |
| 요약 이벤트, 제한된 상세 표본, 운영 메트릭 | 조사에 필요한 자료를 제공하면서 수집 비용과 노출 범위를 제한한다. |
| 버전 있는 설정과 수동 단계 변경 | 별도 관리 UI나 동적 제어 시스템을 필수로 요구하지 않는다. |
| 실행·메모리·큐·저장 상한과 중지 수단 | 비교·수집 작업이 사용자 요청에 필요한 자원을 모두 소진하지 않도록 제한한다. |
| 운영 전환·롤백·종료 기록 | 판단의 근거를 재현하고 임시 프록시의 종료 여부를 확인한다. |

적용은 대상 API 하나의 등록부터 종료까지 전체 흐름을 검증하는 방식으로 시작한다. 다른 특성의 읽기 API가 필요하면 해당 계약을 확인한 뒤 확대한다. 여기서 API 하나는 점진적 적용의 시작 단위이며 제품이 허용하는 API 개수의 상한이 아니다.

## 초기 범위 밖과 확장 조건

| 범위 밖 | 확장을 검토할 조건 |
| --- | --- |
| 운영 쓰기 dual-write | 중복, 순서, 성공 응답, 복구, 동기화 계약이 별도로 정의되어야 한다. |
| 결제·예약·알림·메일의 실제 shadow 효과 | 격리된 대상 또는 실제 업무 효과를 실행하지 않는 검증 계약이 있어야 한다. |
| SSE·WebSocket·gRPC·무한 스트림 | 해당 프로토콜이 실제 대상에 필요한 경우 프로토콜별 전달·취소·비교 모델을 별도로 검토해야 한다. |
| 대용량 업로드·다운로드 shadow | 해당 요청의 복제가 실제로 필요한 경우 메모리 상한을 지키는 별도 복제 방식을 검토해야 한다. |
| 백엔드 종속 cursor·transaction | 세션 수명, 같은 backend를 유지하는 affinity, 복귀 정책이 마련되어야 한다. |
| 범용 게이트웨이·업무 변환 플러그인 | 여러 실제 API에서 같은 기능의 필요성이 입증되어야 한다. |
| 무손실 요청 기록·재생 | 관측 유실을 허용할 수 없는 요구가 확인되어야 한다. |
| 자동 승격·자동 fallback | 판단 기준과 실패 모드가 수동 운영에서 충분한 증거로 검증되어야 한다. |

표의 조건은 확장 검토를 시작하는 조건이며 현재 지원 또는 채택을 뜻하지 않는다. 확장 여부는 실제 API의 필요, 선행 계약, 운영 비용을 확인한 뒤 별도로 결정해야 한다.

v1 통과도 일반 HTTP 전달 계약을 검증한 경로에만 적용해야 한다. 미지원 프로토콜은 기존 진입점을 유지해야 하며, 프록시가 해당 프로토콜을 그대로 통과시킨다고 가정해서는 안 된다.

## 보존해야 할 불변식

- 요청마다 serving을 하나 선택해야 한다. shadow 결과를 사용자 응답에 혼합해서는 안 된다.
- shadow를 실행할 수 없어도 해당 요청의 serving 선택을 유지해야 한다.
- 양쪽 전송, 양쪽 실행 완료, 동일한 데이터 문맥, 동일한 응답 결과를 서로 다른 사실로 기록해야 한다.
- 저장소 장애는 관측 상태로 드러내야 한다. 관측 저장 성공을 사용자 요청의 동기 성공 조건으로 삼아서는 안 된다.
- 비교용 정규화는 비교 자료에만 적용해야 한다. 정규화한 결과로 사용자에게 전달하는 원문 응답을 바꿔서는 안 된다.
- 양쪽 실행의 사용자, 테넌트, 권한 의미가 같은지 확인해야 한다. 이 문맥을 확인하지 못한 비교를 정상 일치로 판단해서는 안 된다.
- 자동 fallback과 backend retry는 기본 비활성 상태를 유지한다. 호출자가 다시 보낸 요청은 별도의 논리 요청으로 처리한다.
- 설정 revision과 비교 policy revision을 기록해야 한다. 메트릭 label에 값의 종류가 무제한으로 늘어나는 항목을 넣어서는 안 된다.
- 관측 자료가 부족한 상태를 성공으로 판단해서는 안 된다.
- v1의 데이터 호환성, 최신성, 용량 중 하나라도 복귀 기준을 충족하지 못하면 롤백 준비가 완료되었다고 표시해서는 안 된다.

## 요구사항 변경 원칙

MVP를 확장할 때는 실제 API의 필요, 새 실패 모드, 운영 구성의 증가, 추가 검증 항목을 기록해야 한다. 기능을 보류하거나 제외할 때는 해당 API가 기존 v1 경로를 계속 사용할 수 있는지 확인해야 한다.

스택 선택은 정해진 동작 계약을 충족하는 구현 방법을 결정하는 작업이다. 특정 스택을 선택했다고 제품 요구사항의 충족이 입증되는 것은 아니다. 기능 요구사항인 FR과 품질 요구사항인 NFR의 검증 연결은 [검증 기준](../validation/README.md)을 따른다.
