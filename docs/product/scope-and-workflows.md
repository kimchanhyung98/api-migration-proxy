# 적용 범위와 사용자 흐름

- 문서 범위: 첫 대상 API의 적용 여부·담당자 행동·초기 범위의 한계
- 기능 추가 시: 아래 초기 범위 밖 항목의 확장 조건과 관련 기능·검증 계약 확인

## 주요 사용 시나리오

### 같은 계약을 유지한 API 재구현

- 상황: 상품 상세 조회를 다른 언어·구조로 재구현
- 시작: v1 사용자 응답 유지, 선택된 요청을 v2에도 실행
- 비교 필수값: 상품 ID·가격·판매 상태·접근 권한
- 제외 가능값: 명시한 비결정적 요청 ID 등
- 전환 조건: 차이 원인 설명 및 오류·지연·관측 기준 충족

### API 실행 인프라 교체

- 상황: 동일한 공개 계약을 다른 배포 환경으로 이전
- 확인 항목: 결과 일치, 연결 timeout, 큰 응답, 인증 대상, 네트워크·데이터 접근 지연
- shadow와 별도 확인: 실제 사용자에게 전체 v2 응답을 제공하는 경로의 용량·지연

### 의도적인 응답 구조 변경

- 상황: v2 내부 필드 변경과 호출자 계약 유지가 동시에 필요한 경우
- 선행 결정: API 측 호환 응답 또는 필요한 범위의 명시적 매핑
- 구분: 비교용 필드 매핑과 사용자에게 전달하는 응답의 호환성
- 공개 계약의 파괴적 변경: 클라이언트 마이그레이션 계획과 함께 별도 검토

### 일부 요청에서만 실패하는 신규 버전 조사

- 상황: 특정 데이터 크기·입력군에서 v2 timeout 증가
- 확인 항목: route·응답 크기 구간·실행 결과별 완료율과 지연
- 조사 자료: 수집 정책에서 허용한 상세 표본
- 금지 동작: 미수집 입력의 임의 복원, 운영 요청의 자동 재전송

### 전환 후 되돌리기

- 계기: v2 사용자 오류 증가
- 우선 조치: 신규 비율 확대 중지
- v1 복귀 조건: 현재 데이터·계약 해석 가능, 목표 부하 처리 가능
- 적용 범위: 이후 요청의 serving 배정 변경; 진행 중 v2 요청의 무조건 재실행 금지
- 프록시 자체 장애: 별도로 검증한 우회 경로 적용

## 운영자의 사용 흐름

| 순서 | 운영자의 행동 | 시스템에서 확인할 결과 |
| --- | --- | --- |
| 1 | route, v1/v2 목적지, 인증·입출력 계약 등록 | 중복·충돌·필수값 누락이 검출된 설정 검토 결과 |
| 2 | v1만 serving하도록 적용 | 적용 revision, 실제 v1 분포, 프록시 기준선 |
| 3 | shadow 표본을 작게 활성화 | 선택·실행·종료·비교·저장 개수와 실패 사유 |
| 4 | 불일치 사례 조사 | 같은 요청의 양쪽 결과, 비교 정책, 문맥·제한 사유 |
| 5 | v2 응답 비율을 올림 | 설정 적용 현황과 해당 epoch의 사용자·비교 지표 |
| 6 | 악화 시 중지 또는 롤백 | 변경 전후 비율, 적용 지연, 실제 serving 복귀 |
| 7 | 전체 v2 안정성 확인 후 종료 | 남은 v1 의존, 데이터 복귀 기간, 직접 연결 검증 |

- 초기 운영 수단: 설정 파일·기존 배포 방식·기존 모니터링·제한된 이벤트 조회
- 전용 웹 콘솔: 초기 필수 범위에서 제외
- 운영 화면: 판단에 필요한 상태 중심, 내부 큐·DB 구현 상세의 불필요한 노출 제외

## MVP 범위

| 포함 범위 | 이유 |
| --- | --- |
| 유한한 일반 HTTP JSON API와 경로별 등록 | 전달·비교·실패 경계를 명확히 검증할 수 있음 |
| 명시적으로 부작용 없는 API의 양쪽 실행 | 중복 실행으로 업무 결과가 바뀌는 문제를 초기 범위에서 피함 |
| serving 선택과 반대편 shadow | 사용자 노출과 검증 부하를 독립적으로 제어 |
| 기본 JSON·status·필수 헤더 비교 | 같은 논리 요청의 계약 회귀를 확인 |
| 요약 이벤트, 제한된 상세 표본, 운영 메트릭 | 조사 가능성과 수집 비용의 균형 |
| 버전 있는 설정과 수동 단계 변경 | 관리 UI·동적 제어 시스템 없이 시작 |
| 실행·메모리·큐·저장 상한과 중지 수단 | 비교 작업이 주 요청을 고갈시키지 않도록 제한 |
| 운영 전환·롤백·종료 기록 | 재현 가능한 판단과 임시 프록시의 종료 |

- 개발 순서: 첫 API 하나의 전체 흐름 검증 → 필요한 경우 다른 특성의 두 번째 읽기 API 검증
- API 개수: 제품 제한이 아닌 개발 순서의 예시

## 초기 범위 밖과 확장 조건

| 범위 밖 | 확장을 검토할 조건 |
| --- | --- |
| 운영 쓰기 dual-write | 중복·순서·성공 응답·복구·동기화 계약이 별도로 정의된 경우 |
| 결제·예약·알림·메일의 실제 shadow 효과 | 격리된 대상 또는 실행하지 않는 검증 계약이 있는 경우 |
| SSE·WebSocket·gRPC·무한 스트림 | 프로토콜별 전달·취소·비교 모델이 필요한 경우 |
| 대용량 업로드·다운로드 shadow | 메모리 상한을 지키는 별도 복제 방식이 필요한 경우 |
| 백엔드 종속 cursor·transaction | 세션 수명·affinity·복귀 정책이 마련된 경우 |
| 범용 게이트웨이·업무 변환 플러그인 | 여러 실제 API에서 같은 기능의 필요성이 입증된 경우 |
| 무손실 요청 기록·재생 | 관측 유실을 허용할 수 없는 요구가 확인된 경우 |
| 자동 승격·자동 fallback | 판단 기준과 실패 모드가 수동 운영으로 충분히 검증된 경우 |

- v1 통과: 일반 HTTP 전달 계약을 검증한 경로만 적용
- 미지원 프로토콜: 기존 진입점 유지; 임의 프록시 통과를 보장하지 않음
- 확장 여부: 실제 API의 필요·선행 계약·운영 비용을 확인한 뒤 별도 결정; 후보를 현재 MVP 요구사항으로 간주 금지

## 보존해야 할 불변식

- 요청당 serving 하나 선택; shadow 결과의 사용자 응답 혼합 금지
- shadow 실행 불가 시에도 serving 선택 유지
- 양쪽 전송과 양쪽 완료·동일 데이터·동일 결과의 구분
- 저장소 장애 공개; 동기 요청 성공 조건과 분리
- 비교용 정규화와 사용자 응답 원문의 분리
- 양쪽 사용자·테넌트·권한 의미의 일치
- 자동 fallback·backend retry 기본 비활성; 호출자 재시도는 별도 logical request로 처리
- 설정·비교 policy revision 기록; 메트릭의 무제한 label 사용 금지
- 관측 자료 부족을 성공으로 판단 금지
- v1 데이터 호환성·최신성·용량이 없는 상태의 롤백 준비 완료 표시 금지

## 요구사항 변경 원칙

- MVP 확장 시 기록: 실제 API의 필요·새 실패 모드·운영 구성 증가·검증 항목
- 기능 보류·제외 시 확인: 기존 v1 경로의 지속 사용 가능 여부
- 스택 선택: 정해진 동작 계약을 충족하는 구현 방법의 결정
- FR/NFR 검증 연결: [개발·검증 계획](../validation/README.md)
