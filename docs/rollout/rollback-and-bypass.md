# Shadow 중지·serving 롤백·프록시 우회

이 문서는 장애 위치와 복귀 준비 상태에 따른 조치 선택 절차를 정의한다. 변경 담당자는 추가 실행 중지, 이후 요청의 v1 serving 복귀, 프록시 자체 우회 중 필요한 조치를 선택한다. 세 조치는 효과가 다르다. 하나의 조치 완료를 다른 조치의 완료로 기록해서는 안 된다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 장애 신호, 현재 serving·shadow 비율과 revision, 영향받는 route 또는 cohort group, v1 최신성·스키마·권한·계약·용량 및 준비된 복귀·우회 경로를 확인한다. |
| 결과·출력 | 선택한 축소·중지·복귀 조치, 대상별 실제 적용 상태, 요청 분포와 복구 소요 시간을 기록한다. |
| 실패·제한 | v1 데이터·계약이 호환되지 않거나 준비 상태가 미확인이면 즉시 복귀 가능한 상태로 표시해서는 안 된다. 결과가 불명확한 진행 요청을 무조건 재실행해서는 안 된다. |

Serving·shadow·rollback의 정의는 [공통 용어](../_rules/glossary.md)를 따른다. 롤백은 이후 요청의 serving 배정을 바꾸는 조치이다. 이미 수행한 API 실행이나 데이터 변경은 되돌리지 않는다.

## 중지와 복귀의 차이

| 조작 | 새 설정 적용 후의 효과 | 이 조작만으로 바뀌지 않는 것 |
| --- | --- | --- |
| `shadow_sample_ratio=0` | 새 설정으로 처리하는 요청에서 반대편 shadow를 새로 선택하지 않는다. | Serving 선택 비율과 기존 snapshot으로 처리 중인 shadow는 변경하지 않는다. |
| `v2_serve_ratio=0` | 새 설정으로 배정하는 전환 대상 요청의 serving을 v1으로 선택한다. | Shadow 비율, 기존 snapshot으로 처리 중인 v2 요청, 데이터 자체는 변경하지 않는다. |
| 이전 설정 복귀 | 마지막 유효 설정을 복구 대상으로 삼아 설정 오류나 의도치 않은 정책 변경을 복구한다. | 별도로 변경된 API 배포나 DB 스키마는 복구하지 않는다. |
| 프록시 우회 | 기존 진입 경로를 변경하여 요청 경로에서 프록시를 제외한다. | 대상 API 자체 또는 데이터의 장애는 해결하지 않는다. |
| 서비스·데이터 복구 | 담당 서비스의 복구 절차로 신규 스키마·쓰기·데이터 문제를 처리한다. | 프록시의 단순 라우팅 변경으로 이 책임을 대체할 수 없다. |

v2 serving 중에 shadow만 중지하면 v1 추가 실행은 줄지만 사용자의 v2 노출은 유지된다. Serving만 v1으로 복귀하고 shadow 비율을 유지하면 v2 shadow는 계속 실행될 수 있다. v2 실행이 공유 자원 장애의 원인이면 v1 serving 복귀와 shadow 중지를 같은 복구 의도에 포함해야 한다. 두 조작의 이름, 적용 revision, 실제 실행량은 변경 이력에서 각각 구분해야 한다.

설정 적용 전 snapshot을 사용하는 요청은 기존 deadline과 취소 계약을 유지한다. 설정 변경을 이미 시작한 실행의 취소나 그 실행 결과의 복구로 해석해서는 안 된다.

## 장애별 대응 시나리오

아래 대응은 장애 원인에 따른 조치 선택의 제안이다. 실제 적용 여부는 사전에 정한 중지 조건과 현재 복귀 준비 상태에 따라 판단해야 한다. 선택한 조치의 실행에는 [조치 수행과 완료 확인](#조치-수행과-완료-확인)을 적용한다.

| 확인한 상황 | 권장하는 대응 | 조치 선택·복구 판단에 필요한 확인 항목 |
| --- | --- | --- |
| v2 shadow만 느려진다. | 추가 부하를 늘리지 않도록 shadow 확대 중지를 권장한다. 사전에 정한 중지 조건에 따라 shadow 비율 축소 검토를 권장한다. | v2 timeout, 공유 의존 부하, cold 상태, 실행 상한 도달 여부 |
| v2 serving 오류가 증가한다. | 사용자 노출 확대를 막기 위해 비율 확대 중지를 권장한다. v1 복귀 준비를 충족하면 serving 복귀 검토를 권장한다. | v1 용량·데이터·권한·공개 계약, 복귀 경로 |
| 양쪽 serving 성능이 악화된다. | 추가 부하를 줄이기 위한 shadow 축소를 권장한다. 원인 확인을 위한 프록시·공유 DB·외부 의존 조사를 권장한다. | Shadow가 공유 자원에 추가한 간접 부하 |
| 비교 저장소가 장애 상태이다. | 저장소 장애만 발생했고 serving이 요청을 처리할 수 있으면 serving 지속을 권장한다. 비교 근거가 부족한 상태의 확대를 막기 위해 승격 중지를 권장한다. 장애 영향 추적을 위해 유실·미확인 구간 기록을 권장한다. | Queue age, 유실, 복구 후 배치 적체 |
| 프록시가 과부하 상태이다. | 추가 부하를 줄이기 위한 shadow·capture 부하 제한 검토를 권장한다. 사전에 정한 중지 조건과 우회 준비 상태에 따라 프록시 우회 검토를 권장한다. | 기존 직접 경로의 사용 가능 상태, 실제 client 연결 갱신 |
| 잘못된 설정이 적용되었다. | 설정 오류를 복구하기 위해 마지막 유효 설정으로의 복구 검토를 권장한다. | 일부 인스턴스·worker에만 새 설정이 적용되었는지 여부 |
| 권한·테넌트 경계 위반이 발생한다. | 추가 노출을 막기 위해 해당 route의 노출 중지 또는 복귀 검토를 권장한다. | 영향 범위, 판단에 필요한 최소 증거, v1의 동일 결함 여부 |
| v1 데이터가 뒤처져 있다. | 복귀 준비 기준을 충족하기 전에는 v1을 즉시 복귀 가능한 상태로 표시해서는 안 된다. | 재동기화·재가동 소요 시간, 이미 정한 별도 복구 방안 |

취소되었거나 연결이 끊어진 요청은 backend에서 실행되었을 수 있다. Backend 실행 결과를 확인하지 못한 요청을 반대 backend로 무조건 재전송해서는 안 된다. Backend 간 이동의 지원·호환 정책이 미확인이면 상태성 세션이나 cursor를 강제로 재배정해서는 안 된다.

## 조치 수행과 완료 확인

현재 장애와 복구 대상이 확인되면 변경 담당자는 다음 절차를 수행하십시오. 긴급 조치에서는 일반 승격에 필요한 표본을 기다리지 마십시오. 사전에 정한 중지 조건과 복귀 준비를 기준으로 조치를 판단하십시오.

1. 장애 범위와 대상 route·cohort group·현재 revision을 기록하십시오.
   사용자 serving 장애, shadow의 추가 부하, 설정 오류, 프록시 경로 장애를 구분하십시오.
2. 위 조작 표에 따라 필요한 조치를 선택하십시오.
   Shadow 중지와 serving 복귀가 모두 필요하면 두 조치를 각각 기록하십시오.
   Shadow 중지 자체를 v1 serving 복귀 완료로 표시하지 마십시오.
3. v1 serving 복귀를 선택한 경우 [v1 복귀 판정](#v1-복귀-판정)을 수행하십시오.
   복귀 준비가 `pass`가 아니면 v1을 준비 완료로 표시하지 마십시오.
   준비 조건을 충족하지 못하면 이미 정한 서비스·데이터 복구 경로를 선택하십시오.
   v1 복귀 판정은 shadow 중지 자체의 실행 조건과 별개이다.
4. 설정 변경을 선택한 경우 [변경 적용 절차](change-management.md)에 따라 적용하십시오.
5. 프록시 우회를 선택한 경우 기존 진입 경로에서 우회 조치를 수행하십시오.
   기존 진입 경로는 프록시 제어 경로가 고장 나도 사용할 수 있어야 한다.
6. 적용한 조치의 실제 결과를 확인하십시오.
   설정 변경의 확인 대상은 인스턴스·worker별 신규 요청용 revision과 신규 serving·shadow 실행 분포이다.
   우회의 확인 대상은 실제 요청 경로, backend 실행량, client 연결 전환이다.
   DNS·로드밸런서 설정 변경 완료만으로 client 전환 완료를 판정하지 마십시오.
7. 변경 전 snapshot으로 시작한 요청의 잔존량과 종료 결과를 확인하십시오.
8. 신규 요청의 조치 적용과 기존 요청의 종료를 따로 기록하십시오.
9. 사용자 오류·지연이 정해진 복구 기준을 충족하는지 확인하십시오.
10. 실제 복구 소요 시간을 기록하십시오.
11. 조작의 적용 완료와 사용자 품질 회복을 별도로 판정하십시오.
12. 관측 유실 구간, 결과 미확인 요청, 남은 복구 제한, 후속 조치를 기록하십시오.

다음 중 하나라도 남아 있으면 그 부분의 완료를 선언하지 마십시오.

- 대상별 적용 상태가 미확인이다.
- 신규 요청이 의도와 다른 경로를 사용한다.
- 사용자 품질이 복구 기준을 충족하지 못한다.
- 복구 시간을 측정하지 못했다.

확인된 부분과 실패·미확인인 부분을 나누어 기록하십시오. 완료 조건을 충족하지 못한 동안 확대를 계속 보류하십시오.

## v1 복귀 판정

변경 담당자는 현재 조건으로 v1 serving 복귀의 준비 여부를 판단하십시오. 데이터 최신성, 스키마, 권한, 공개 계약, 처리 용량, 복귀 경로의 여섯 항목을 모두 확인하십시오. 과거 검증 후 조건이 바뀌었으면 과거 결과를 현재 준비의 증거로 자동 재사용하지 마십시오.

| 판정 | 조건 | 후속 조치 |
| --- | --- | --- |
| `pass` | 다음 조건을 모두 충족한다. 여섯 확인 항목이 모두 `pass`이다. 증거 참조가 있다. 실측 복구 시간과 목표 복구 시간이 모두 확인되어 있다. `실측 복구 시간 ≤ 목표 복구 시간`이다. | v1 serving 복귀를 선택할 수 있다. 복귀를 수행한 경우 실제 적용과 회복 결과를 별도로 확인하십시오. |
| `fail` | 여섯 항목 중 하나라도 `fail`이다. 또는 나머지 근거가 모두 확인된 상태에서 실측 복구 시간이 목표를 초과한다. | 즉시 복귀 가능한 상태로 표시하지 마십시오. 충족하지 못한 조건과 별도 복구 방안을 기록하십시오. |
| `unknown` | 확인 항목에 `unknown`이 있거나, 증거·실측 복구 시간·목표 복구 시간 중 필요한 값이 없다. 단, 확인된 항목의 `fail`이 있으면 `fail`로 판정한다. | 부족한 근거를 기록하십시오. 복귀 준비 완료 표시를 보류하십시오. |

목표 복구 시간은 서비스별 운영 조건으로 정해야 한다. 이 문서는 임의의 목표값을 제공하지 않는다. 정책 모듈은 입력된 확인 결과와 시간을 평가한다. 이 모듈의 판정 자체가 데이터 최신성 측정, v1 재가동 또는 실제 라우팅 변경을 수행하지는 않는다.

## 복귀 가능 기간

| v1/v2 데이터 관계 또는 운영 상태 | v1 복귀에 필요한 조건 |
| --- | --- |
| 동일 DB를 사용한다. | v1이 v2의 스키마·쓰기 결과를 해석할 수 있고 권한·성능이 유지되어야 한다. |
| 독립 DB를 사용한다. | v1의 최신성, 누락·삭제 반영, 스키마, source checkpoint가 정한 복귀 기준을 충족해야 한다. |
| v2만 새 기능·필드를 사용한다. | v1에서 표현할 수 있는 호환 방식 또는 복귀 가능한 제한 범위를 별도로 정의해야 한다. |
| v1을 축소·중지했다. | 재확장·재가동·warm-up·연결 복구의 실측 시간이 정한 목표 이내인지 검증해야 한다. |

v1 shadow 실행 여부와 v1 쓰기 데이터의 최신성은 별도로 검증해야 한다. 담당 서비스는 복귀 가능 기간, 원본 이벤트 보존, 데이터 동기화 유지, 관측 기록 보존의 관계를 확인해야 한다. 프록시가 데이터 동기화를 대행한다고 가정해서는 안 된다.

Warm 상태에서의 즉시 복귀 목표와 축소·중지 후 재가동·warm-up을 포함한 복귀 목표는 구분하여 기록해야 한다. 한 조건의 실측 시간을 다른 조건의 복귀 보장으로 사용해서는 안 된다.

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-16 | P0 | Shadow 중지와 serving 롤백을 별도로 제어해야 한다. | Shadow=0을 v2 serving=0으로 해석하지 않고 각 조작의 적용 결과를 확인할 수 있다. |
| FR-31 | P0 | 프록시 자체 장애에서 사용할 우회 계획을 제공해야 한다. | 프록시 설정 변경만으로 해결할 수 없는 장애에서 실제 호출 경로의 복구를 검증한다. |

## 검증 기준

[T-32, T-33, T-34, T-35](../validation/test-catalog.md)에 따라 shadow 중지·serving 복귀·프록시 우회의 효과를 구분하는지 검증한다. 복귀 준비가 미충족·미확인이면 준비 완료를 표시하지 않아야 한다. 실행 결과가 불명확한 진행 요청은 무조건 재전송하지 않아야 한다.
