# Shadow 중지·serving 롤백·프록시 우회

- 장애 위치에 따라 추가 실행 중지·이후 응답의 v1 복귀·프록시 자체 우회 구분

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 장애 신호, 현재 비율·revision, v1 최신성·권한·용량과 준비된 우회 경로 |
| 결과·출력 | 축소·중지·복귀 조치와 실제 적용 분포·복구 시간 |
| 실패·제한 | v1 데이터·계약 미호환 시 즉시 복귀 가능 표시 금지, 진행 요청의 무조건 재실행 금지 |

## 중지와 복귀의 차이

| 조작 | 효과 | 바뀌지 않는 것 |
| --- | --- | --- |
| `shadow_sample_ratio=0` | 반대편 신규 shadow 실행 중지 | 현재 serving 선택 비율, 이미 실행 중인 shadow |
| `v2_serve_ratio=0` | 이후 배정 가능한 요청을 v1 serving으로 전환 | shadow 비율, 이미 실행 중인 v2 요청, 데이터 자체 |
| 이전 설정 복귀 | 설정 오류나 의도치 않은 정책 변경 복구 | 별도로 바뀐 API 배포·DB 스키마 |
| 프록시 우회 | 프록시 장애의 공통 경로 제거 | 대상 API와 데이터의 장애 |
| 서비스·데이터 복구 | 신규 스키마·쓰기·데이터 문제 해결 | 단순 라우팅으로 해결되지 않는 별도 책임 |

- v2 serving 단계에서 shadow 중지: v1 추가 실행 감소, v2 사용자 노출 유지
- serving만 v1으로 복귀하고 shadow 비율 유지: v2 shadow 실행 지속 가능
- v2 실행 자체가 공유 자원 장애 원인인 경우: v1 serving 복귀와 shadow 중지를 같은 복구 의도에 포함
- 두 조작의 이름·적용 revision·실제 실행량을 변경 이력에서 구분
- 적용 전 스냅샷을 사용하는 진행 요청: 기존 deadline과 취소 계약 유지; 설정 변경을 과거 실행의 취소·복구로 해석 금지

## 장애별 대응 시나리오

| 상황 | 즉시 대응 제안 | 복구 전에 확인 |
| --- | --- | --- |
| v2 shadow만 느려짐 | shadow 확대 중지, 필요하면 비율 축소 | v2 timeout·공유 의존·cold 상태·실행 상한 |
| v2 serving 오류 증가 | 확대 중지, 준비된 v1으로 serving 복귀 | v1 capacity·데이터·권한·공개 계약 |
| 양쪽 serving 성능 악화 | shadow 축소, 프록시·공유 DB·외부 의존 조사 | shadow가 만든 간접 부하 여부 |
| 비교 저장소 장애 | serving 지속, 승격 중지, 유실 구간 기록 | queue age·유실·복구 후 배치 적체 |
| 프록시 과부하 | shadow·capture 부하 제한, 필요 시 우회 | 기존 직접 경로와 실제 client 연결 갱신 |
| 잘못된 설정 | 마지막 유효 revision 재적용 | 일부 인스턴스만 변경됐는지 여부 |
| 권한·테넌트 위반 | 해당 route 노출 중지·복귀 판단 | 영향 범위와 최소 증거, v1 동일 결함 여부 |
| v1 데이터가 뒤처짐 | 즉시 복귀 가능 상태로 표시하지 않음 | 재동기화·재가동 소요와 별도 복구 방안 |

- DNS·로드밸런서 설정 변경과 실제 client connection 전환 완료의 구분
- 실제 요청 경로·backend 실행량·복구 시간 확인
- 취소·연결 중단 후 backend 실행 결과가 불명확한 요청의 무조건 재전송 금지
- 상태성 세션·cursor의 backend 간 이동: 지원·호환 정책 확인 전 강제 재배정 금지

## 조치 완료 확인

1. 장애 범위와 복구 대상 route·cohort group·revision 확인
2. v1 데이터·권한·공개 계약·용량·복귀 경로의 현재 준비 상태 확인
3. shadow 중지·serving 복귀·우회 중 필요한 조작 선택 및 적용
4. 인스턴스별 revision·신규 요청 serving 분포·진행 요청 잔존량 확인
5. 사용자 오류·지연 회복 및 실제 소요 시간 기록
6. 관측 유실·미완료 요청·복구 제한을 포함한 후속 조치 기록

- v1 준비 미충족 시 자동으로 ready 표시 금지; 이미 정한 서비스·데이터 복구 경로 선택
- 프록시 우회는 프록시 제어 경로 자체가 고장 나도 실행 가능한 기존 진입 경로에서 검증

## 복귀 가능 기간

| v1/v2 데이터 관계 | v1 복귀 조건 |
| --- | --- |
| 동일 DB | v2의 스키마·쓰기 결과를 v1도 해석 가능하고 권한·성능이 유지됨 |
| 독립 DB | v1의 최신성, 누락·삭제 반영, 스키마와 source checkpoint가 복귀 기준 충족 |
| v2만 새 기능·필드 사용 | v1에서 표현 가능한 호환 방식 또는 제한된 복귀 범위를 별도 정의 |
| v1을 축소·중지함 | 재확장·warm-up·연결 복구 시간이 목표 안에 들어오는지 검증 |

- v1 shadow 실행과 v1 쓰기 최신성의 별도 검증
- 복귀 기간·원본 이벤트 보존·데이터 동기화 유지·관측 기록 보존의 정렬
- 프록시의 데이터 동기화 대행 제외
- warm 상태 즉시 복귀와 축소·중지 후 재가동·warm-up 복귀의 목표 시간 구분
