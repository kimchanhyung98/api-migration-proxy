# 점진적 전환 단계와 승격 판단

이 문서는 변경 담당자가 API별 전환 단계를 유지하고 다음 단계 또는 다음 v2 serving 비율로 확대할지를 판단하는 기준을 정의한다. 판단에는 사용자 품질, API 계약, 비교·수집 상태, 자원·비용, v1 복귀 가능성의 증거를 사용해야 한다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 현재 stage·epoch·revision, G-01~G-08의 판단 근거, 다음 단계와 목표 비율을 확보한다. |
| 결과·출력 | 현재 상태 유지, 확대 또는 확대 보류의 판단과 적용할 변경 의도를 기록한다. |
| 실패·제한 | 적용 대상인 필수 gate에 `fail` 또는 `unknown`이 하나라도 있으면 확대해서는 안 된다. 대상 API의 전체 v2 serving을 전체 v1 서비스의 종료로 해석해서는 안 된다. |

## 운영 단위

전환 단위는 등록 route 또는 호환된 cohort group이다. 각 단위에 대해 변경 담당자, 현재 stage, 설정 revision, 비교 policy revision, 관측 epoch, 마지막 유효 복귀 설정을 기록해야 한다. 용어의 의미는 [공통 용어](../_rules/glossary.md)를 따른다.

같은 stage를 유지하더라도 비율·비교 정책·backend 배포가 바뀌면 관측 조건을 재평가해야 한다. 변경 시점과 전파 구간을 기록해야 한다. 새 조건에서 필요한 최소 표본과 관측 기간을 확보해야 한다. 배포 완료와 gate 통과는 별도로 기록한다.

v1과 v2가 독립 데이터 원천을 사용하면 초기 적재, 변경분·삭제 반영, 최신성의 준비 여부를 외부 선행 조건으로 확인해야 한다. 이 외부 선행 조건을 프록시 자체의 데이터 동기화 단계로 추가해서는 안 된다.

## 단계별 상태

아래 표의 사용자 응답과 shadow 상태는 해당 전환 대상에 적용한다. 각 단계의 확인 항목은 그 단계에서 확보할 증거이며, 비율 설정이나 배포 명령만으로 확인을 완료한 것으로 처리해서는 안 된다.

| 단계 | 사용자 응답 | shadow | 해당 단계에서 확인할 조건 | 문제 발생 시 검토할 복귀 방식 |
| --- | --- | --- | --- | --- |
| S0 BASELINE | 기존 v1 직접 경로를 사용한다. | 실행하지 않는다. | 대상 계약·부작용·현재 오류·지연·트래픽의 기준선을 확보한다. | 기존 경로를 유지한다. |
| S1 V1_ONLY | 프록시를 통해 v1 응답을 제공한다. | 표본 비율은 0이다. | 프록시 추가 영향, 인증·헤더·오류 처리, 기존 경로 우회를 검증한다. | 검증된 기존 v1 직접 경로를 사용한다. |
| S2 SHADOW | v1 응답을 제공한다. | 대상별로 정한 초기 비율에서 목표 비율까지 확대한다. | 같은 요청의 비교, 양쪽 오류·부하, 수집 완료율을 검증한다. | 신규 shadow 실행을 중지한다. |
| S3 CANARY | 전환 대상 중 일부 요청에 v2 응답을 제공한다. | 검증 목적별로 정한 비율을 유지한다. | 실제 사용자 영향, 배정 일관성, v1 복귀를 검증한다. | v1 복귀 준비가 충족되면 v2 serving 비율을 0으로 변경한다. |
| S4 V2_PRIMARY | 전환 대상 전체에 v2 응답을 제공한다. | 검증·복귀 목적에 따라 v1 shadow를 유지할 수 있다. | 전체 serving 부하·주요 업무 주기의 기준 충족과 v1 복귀 준비를 확인한다. | v1 복귀 준비가 충족되면 v2 serving 비율을 0으로 변경한다. |
| S5 SHADOW_OFF | 전환 대상 전체에 v2 응답을 제공한다. | 신규 shadow 표본 비율은 0이다. | v2 단독 부하와 v1 cold 상태의 복귀 조건을 재평가한다. | 준비된 v1을 재사용하거나 검증된 재가동 절차를 수행한다. |
| S6 RETIRED | v2 직접 경로를 사용한다. | 프록시 shadow를 실행하지 않는다. | 잔존 v1 의존 제거, 프록시 우회·제거, 보존 종료 정책을 확인한다. | 기록된 별도 배포·서비스·데이터 복구 절차를 사용한다. |

S3의 `1% → 5% → 25% → 50%`는 비율 확대의 예시이다. 실제 비율과 유지 기간은 대상의 요청량·위험도·표본 확보·복귀 능력에 따라 결정해야 한다. 예시 비율에 도달했다는 사실만으로 승격 성공을 판정해서는 안 된다.

S4의 전체 v2 serving은 해당 전환 대상에 한정된다. 미등록 경로·미지원 프로토콜·쓰기·배치 중 하나라도 v1에 의존하면 v1 전체를 종료해서는 안 된다. S4 이후에는 동시에 v1 serving을 받는 사용자 대조군이 없으므로, 이전 canary 비교 증거와 현재 전체 serving의 SLO·업무 주기 증거를 구분해야 한다.

## 첫 대상의 준비 목록

변경 담당자는 첫 전환 대상에 대해 다음 항목을 확보하십시오. 서로 의존하지 않는 증거 수집은 병행할 수 있다. 증거의 존재와 증거의 기준 충족 판정을 구분하십시오.

| 준비 항목 | 확보할 내용 |
| --- | --- |
| 공개 계약 | Method·path, 입력·출력, 성공·예상 거절·업무 오류, 호환 기준을 문서화하십시오. |
| 양쪽 실행의 효과 | 조회수·cache·외부 호출·quota를 포함하여 각 API 실행이 만드는 효과를 확인하십시오. |
| 데이터·권한 | v1/v2의 데이터 원천·스키마·동기화·권한·세션 관계를 확인하십시오. |
| 기준선·대표 부하 | QPS·응답 크기·지연·오류의 대표 분포와 피크 구간을 확보하십시오. |
| 비교·데이터 수집 정책 | 비교 필드, 제외 규칙, 문맥 허용치, 수집 허용 필드, 보존 기간을 결정하십시오. |
| 품질·표본·예산 | 사용자 SLO, 비교 완료율, 필요한 표본·관측 기간, 자원·비용 예산을 결정하십시오. |
| 변경·복구 수단 | 변경 담당자와 실제 적용·중지·복귀 수단을 확인하십시오. |
| 프록시 우회 | 프록시 장애 시 사용할 v1 직접 경로와 실제 복구 시간을 검증하십시오. |

대상별 수치를 확보하지 못했으면 미정으로 기록하십시오. 미정 항목의 영향을 받는 gate를 통과로 판정하지 마십시오. 미정 항목의 근거가 필요한 확대는 보류하십시오.

## 승격 gate

Gate는 다음 단계 확대 전에 증거를 대조하는 판단 항목이다. 각 gate의 결과는 `pass`, `fail`, `unknown` 중 하나로 기록한다.

| 결과 | 판정 조건 | 확대 판단에 적용하는 방법 |
| --- | --- | --- |
| `pass` | 적용 기준이 정해져 있고 해당 epoch의 증거가 그 기준을 충족한다. | 그 gate의 충족으로 처리한다. 증거 참조를 함께 기록해야 한다. |
| `fail` | 확보한 증거가 적용 기준을 충족하지 않는다. | 적용 대상인 필수 gate이면 확대를 금지한다. |
| `unknown` | 기준·표본·관측 기간·측정 근거가 없거나 현재 epoch에 대한 판단이 불가능하다. | 적용 대상인 필수 gate이면 확대를 금지한다. 0 오류나 통과로 대체해서는 안 된다. |

해당 단계에 적용하지 않는 검사는 결과를 `pass`로 만들지 않는다. 적용 제외 사유와 대체 증거를 기록해야 한다. 정책 모듈의 제외 기록은 `status=unknown`, `applicable=false`를 사용한다. 비교가 실제 실행 중인 구간에서는 G-03을 적용 제외해서는 안 된다.

| Gate | 확인할 조건 | 필요한 증거 |
| --- | --- | --- |
| G-01 계약 | 공개 API 계약과 중요 업무 불변식이 유지된다. | Contract fixture, 차이 사례, 의도적 변경 목록을 대조하십시오. |
| G-02 사용자 품질 | 오류·지연이 정해진 기준 이내이다. | 동일 epoch의 serving 지표와 기준선을 대조하십시오. |
| G-03 비교 신뢰도 | 표본·완료율·제외·드롭이 정해진 기준을 충족한다. | [분모 정의](../observability/coverage-and-analysis.md#분모-정의)에 따른 E/S/D/T/C/W와 result·reason별 지표를 확인하십시오. |
| G-04 자원·비용 | 양쪽 실행·capture·저장의 자원 사용과 비용이 정해진 예산 이내이다. | Backend QPS, inflight, 메모리·큐·저장 사용량, 비용 추정을 확인하십시오. |
| G-05 데이터·권한 | 양쪽 API가 같은 의미의 데이터·권한으로 동작한다. | Source 관계, freshness, 스키마, 테넌트 경계를 검증하십시오. |
| G-06 복귀 | v1과 이전 설정을 사용한 복귀가 현재 조건에서 가능하다. | v1 최신성·용량·계약, 복귀 연습과 소요 시간을 확인하십시오. |
| G-07 적용 상태 | 모든 대상 인스턴스와 설정을 독립적으로 읽는 worker의 신규 요청용 revision이 의도한 값과 일치한다. | [설정 적용 현황](../routing/configuration.md)과 실제 serving 분포를 확인하십시오. |
| G-08 관측 기간 | 관측 구간에 필요한 업무 피크·배치·주기와 최소 표본이 포함된다. | 관측 시작·종료 시각, 대표 구간, 누락 구간과 그 영향을 기록하십시오. |

## 승격 판단 절차

변경 담당자는 다음 절차를 수행하십시오.

1. 평가할 route 또는 cohort group의 현재 stage·epoch·revision과 목표 stage·비율을 지정하십시오.
2. 현재 epoch의 G-01~G-08 결과와 증거 참조를 수집하십시오.
   이전 epoch의 결과만 있거나 gate 결과가 없으면 현재 판단을 `unknown`으로 기록하십시오.
3. 각 gate의 적용 여부를 확인하십시오.
4. 적용 제외 gate가 있으면 제외 사유와 대체 증거를 기록하십시오.
5. 아래의 단계별 증거 규칙을 대조하십시오.
6. 적용 대상인 필수 gate를 모두 판정하십시오.
   하나라도 `fail` 또는 `unknown`이면 확대를 보류하십시오.
   보류한 경우 충족하지 못한 조건을 기록하십시오.
   장애 중지 조건에 해당하면 [중지·복귀 절차](rollback-and-bypass.md)를 수행하십시오.
7. 필수 조건을 모두 충족하면 유지 또는 확대 판단과 근거를 기록하십시오.
8. 확대를 선택한 경우 [변경 적용 절차](change-management.md)를 수행하십시오.

판정 완료는 변경 의도와 근거가 기록된 상태이다. 실제 설정 적용 완료를 뜻하지 않는다. 정책 모듈은 입력된 판단의 일관성을 평가하며, 서비스별 임계값을 스스로 정하거나 설정을 배포하지 않는다.

## 단계별 증거 적용

| 구간 | 비교 증거의 처리 | 함께 확인할 조건 |
| --- | --- | --- |
| S0~S1 비교 미실행 | G-03의 적용 제외 사유를 기록해야 한다. 미실행을 비교 통과로 기록해서는 안 된다. | 기준선, 메트릭 경로, 프록시 추가 영향을 검증해야 한다. |
| S2~S4 비교 실행 구간 | 해당 epoch의 실제 비교 분모·완료율·제외·드롭을 확인해야 한다. | 최소 표본·기간과 사용자 품질·복귀 gate를 함께 확인해야 한다. |
| S5 shadow 중지 | 신규 shadow 선택 S=0을 확인해야 한다. 적격 요청 E는 계속 집계된다. 마지막 유효 비교 증거의 revision·기간을 보존해야 한다. | 잔여 비교·저장 작업, 현재 serving·수집 상태, v1 cold 상태와 복귀 시간을 재검증해야 한다. |
| S6 프록시 제거 | 프록시 비교를 종료한 사실과 마지막 비교 증거를 기록해야 한다. | 직접 v2 경로의 관측, 잔존 의존, 데이터 복구 수단을 검증해야 한다. |

S5의 S=0은 의도한 비교 종료 상태이다. 비교 실행 중 메트릭이 유실되어 S를 알 수 없는 상태와 구분해야 한다. 중지 전에 시작한 요청의 D·T·C·W는 잔여 실행·비교·저장이 끝날 때까지 증가할 수 있으며, 해당 요청의 기존 epoch에 귀속한다.

S4에서 이미 v1 shadow를 중지하는 경우에도 S5의 종료·복귀 준비 검증을 적용해야 한다. 비교 종료 단계에서는 마지막 유효 비교 증거와 현재 serving 증거를 함께 확보해야 한다. Shadow 종료 후 backend·공개 계약·데이터 문맥이 바뀌면 과거 비교 증거의 유효성을 재평가해야 한다. 필요한 검증을 충족하지 못하면 종료를 보류해야 한다.

전체 적격 요청의 양쪽 실행을 검증 목표로 선택한 경우에는 `shadow_sample_ratio=1`과 실제 선택·dispatch·종료·timeout·cancel·drop을 함께 확인해야 한다. 보호 상한·취소·드롭으로 실행량이 줄어든 구간을 전체 목표 부하의 검증 완료로 인정해서는 안 된다. 일부 shadow 표본만 검증했으면 검증한 부하 범위를 기록해야 한다. 전체 v2 serving 용량의 증거는 별도로 확보해야 한다.
