# 마이그레이션 종료와 프록시 제거

이 문서는 전환 대상의 전체 v2 serving 이후에 shadow, v1 사용, 프록시 경로, 관측 기록의 종료 조건을 각각 확인하는 절차를 정의한다. 변경 담당자는 잔존 v1 의존과 복구 수단을 확인해야 한다. 직접 v2 호출은 공개 계약과 운영 기준을 모두 충족해야 한다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 전환 대상의 전체 v2 serving 증거, 잔존 v1 호출자·업무 주기, 복귀 가능 기간, 직접 v2 연결 경로를 확보한다. |
| 결과·출력 | Shadow 종료, v1 사용 종료, 프록시 제거, 관측 기록 정리를 각각 구분한 결과와 증거를 기록한다. |
| 실패·제한 | 미등록 경로·batch·세션 등의 v1 의존이 남아 있으면 v1 전체 종료를 선언해서는 안 된다. Shadow 종료와 데이터 동기화 중지는 별도로 판단해야 한다. |

전환 단계와 관측 epoch의 의미는 [공통 용어](../_rules/glossary.md)를 따른다. 아래 절차의 전체 v2 serving은 해당 전환 대상에 한정된다. 대상의 전체 v2 serving을 미조사 API나 호출자의 전환 완료로 확대 해석해서는 안 된다.

## 종료 확인 절차

변경 담당자는 다음 절차를 수행하십시오. 잔존 호출자 조사, 직접 경로 계약 확인, 보존 책임 확인은 서로 의존하지 않으면 병행할 수 있다. 각 종료 조치는 자신의 시작 조건을 충족한 뒤 별도로 수행해야 한다.

1. 전환 대상의 v2 전체 serving 증거를 확인하십시오.
   관측 구간에는 필요한 주요 업무 주기와 피크가 포함되어야 한다.
   사용자 품질과 용량은 정한 기준을 모두 충족해야 한다.
   기간·표본·기준이 미정이거나 근거가 누락되었으면 종료 판단을 보류하십시오.
2. v1을 사용하는 미등록 API, batch, 관리자 도구, 내부 client, 상태성 세션을 조사하십시오.
3. 잔존 의존이 없다는 증거와 아직 확인하지 못한 범위를 구분하여 기록하십시오.
   확인하지 못한 호출자를 사용량 0으로 처리하지 마십시오.
4. v1 shadow 종료 전후의 부하·cache·지연을 비교하십시오.
   Shadow를 중지한 v2 단독 상태는 정한 기준을 충족해야 한다.
5. v1 cold 상태에서 재가동·warm-up을 포함한 복귀 시간을 검증하십시오.
   이미 S4에서 shadow를 중지했더라도 이 검증을 생략하지 마십시오.
6. 직접 v2 경로의 공개 계약을 검증하십시오.
   확인 대상은 인증, 헤더, DNS, 네트워크, 오류 처리, 연결 동작이다.
7. 프록시의 trace·계측·경로 매핑에 대한 호출자 의존을 확인하십시오.
8. 직접 경로에서 필요한 운영 상태를 관측할 수 있는지 확인하십시오.
9. 복귀 가능 기간과 남겨 둘 서비스·데이터 복구 수단을 확인하십시오.
10. 조건을 충족한 종료 변경을 각각 별도로 수행하십시오.
    v1 사용 종료와 프록시 제거의 선후는 잔존 호출 경로와 복구 의존에 따라 결정하십시오.
    한 변경의 완료를 다른 변경의 완료로 처리하지 마십시오.
11. 각 변경의 실제 요청 경로와 영향을 기록하십시오.
12. 비교 이벤트, 상세 표본, 설정 변경 이력의 보존·만료 담당과 기한을 확정하십시오.
13. 보존 기한이 도래한 데이터만 정리하십시오.
    남은 기록에는 해당 목적의 보존 정책을 계속 적용하십시오.
14. 각 종료 조치의 결과, 실제 추가 비용, 남은 한계, 종료 후 가능한 복구 수단을 기록하십시오.
    완료·실패·미확인 결과를 구분하십시오.

## 종료 결과와 완료 증거

| 결과 | 완료에 필요한 증거 | 완료로 간주해서는 안 되는 상태 |
| --- | --- | --- |
| v1 shadow 종료 | 신규 shadow 선택 중지와 기존 요청의 shadow 실행 종료를 모두 확인해야 한다. 실제 반대편 실행량과 v2 단독 사용자 지표를 기록해야 한다. | 표본 비율만 0으로 변경했고 실제 실행량이나 잔여 작업을 확인하지 못한 상태이다. |
| v1 사용 종료 | 미등록·관리·배치·내부 client·세션을 포함한 종료 대상 범위에 v1 의존이 남아 있지 않아야 한다. | 전환 대상 route만 전체 v2 serving이며 다른 호출자의 사용 여부는 미확인인 상태이다. |
| 프록시 제거 | 실제 직접 v2 경로의 인증·헤더·오류·연결 계약과 관측 수단을 모두 검증해야 한다. | 진입 설정만 변경했고 client 연결 전환이나 프록시 의존 제거를 확인하지 못한 상태이다. |
| 관측 기록 정리 | 목적별 보존·만료 담당과 기한을 확인해야 한다. 기한 도래 데이터의 정리 결과와 전환 결과 보고를 확인해야 한다. | 서비스가 종료되었다는 이유로 보존 기한이 남은 데이터를 조기 삭제한 상태이다. |

Shadow의 신규 선택을 중지해도 중지 이전 요청의 실행·비교·저장은 남을 수 있다. 신규 선택 중지와 잔여 작업의 종료를 구분하여 기록해야 한다. [단계별 증거 적용](stages-and-gates.md#단계별-증거-적용)에 따라 마지막 유효 비교 증거와 현재 serving 증거를 함께 보존한다.

## 실패·미확인 분기

변경 담당자는 확인 결과에 맞는 행의 조치를 수행하십시오.

| 확인 결과 | 수행할 조치 |
| --- | --- |
| v2 전체 serving의 업무 주기·피크·품질·용량 증거가 부족하다. | 영향을 받는 종료 조치를 보류하십시오. 부족한 조건을 기록하십시오. 비율 100%만으로 종료 완료를 판정하지 마십시오. |
| v1 잔존 의존을 발견했거나 조사가 끝나지 않았다. | v1 전체 사용 종료를 보류하십시오. 확인된 의존과 미확인 범위를 구분하여 기록하십시오. |
| Shadow 종료 후 사용자 품질·부하 기준을 충족하지 못한다. | 원인과 복귀 준비 상태를 확인하십시오. [중지·복귀 절차](rollback-and-bypass.md)에 따라 조치를 판단하십시오. |
| 직접 v2 경로의 계약 또는 관측을 검증하지 못했다. | 프록시 제거 완료를 선언하지 마십시오. 실패한 계약이나 미확인 경로를 기록하십시오. 부족한 검증을 완료하십시오. |
| 복귀 기간·복구 수단·보존 담당·기한 중 필요한 항목이 미정이다. | 미정 항목에 의존하는 종료·정리를 보류하십시오. 미정 값을 확인된 복구·보존 조건으로 대체하지 마십시오. |

종료 정책 모듈은 제공된 확인 항목과 증거 참조를 평가한다. 확인 항목 중 하나라도 `fail`이면 결과는 `fail`이다. `fail`은 없지만 `unknown` 또는 증거 누락이 있으면 결과는 `unknown`이다. 모든 확인 항목이 `pass`이고 증거 참조가 있어야 `pass`이다. 이 판정은 호출자 조사, 인프라 제거, 데이터 만료 정리를 자동으로 수행한 결과가 아니다.

## 종료 후 복구와 보존

종료 후에는 복귀에 배포 또는 데이터 복구가 필요한 경계와 남은 복구 수단을 기록해야 한다. 데이터 동기화 중지, 원본 로그 만료, v1 리소스 제거는 별도의 시점으로 관리한다. Shadow 종료만으로 이 세 작업이 허용되었다고 해석해서는 안 된다.

복귀에 필요한 원본 이벤트·백업의 보존을 끝내기 전에는 담당 서비스의 복구 가능성을 확인해야 한다. 관측 기록에는 서비스 종료 여부와 별개로 목적별 보존 기간을 적용해야 한다. 기한이 남은 기록을 서비스 종료만을 이유로 조기 삭제해서는 안 된다.

| --- | --- | --- | --- |

## 검증 기준

[T-39](../validation/test-catalog.md)에 따라 잔존 의존, 직접 경로 계약·관측, cold 상태 복귀, 복귀 기간, 보존 담당·기한, 최종 결과를 확인한 뒤 각 종료 결과를 구분하는지 검증한다.
