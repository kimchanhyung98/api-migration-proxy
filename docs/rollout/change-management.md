# 전환 변경 적용과 이력 관리

이 문서는 변경 담당자가 전환 판단을 실제 설정 변경으로 적용하고 그 결과를 기록하는 절차를 정의한다. 적용 요청, 전파 중 상태, 적용 완료, 일부 적용 실패, 복귀는 각각 구분해야 한다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 변경 담당자는 현재·다음 stage와 revision, gate 결과, 변경 사유, 대상 route 또는 cohort group, 복귀 대상을 확보한다. |
| 결과·출력 | 변경 결과, 대상 인스턴스·worker의 실제 revision, serving·shadow 분포, 관측 epoch를 기록한다. |
| 실패·제한 | 배포 완료를 gate 통과로 기록해서는 안 된다. 관측 저장소 장애 중에도 긴급 중지·복귀 이력을 추적할 수 있는 경로를 유지해야 한다. |

Stage·revision·epoch의 의미는 [공통 용어](../_rules/glossary.md)를 따른다. 이 절차는 담당자의 수동 판단과 기존 배포·변경 관리 방식을 사용하며, 별도 승인 제품이나 다단계 승인 워크플로의 도입을 요구하지 않는다.

## 설정 변경 절차

변경 담당자는 일반적인 유지·확대 변경에 다음 절차를 적용하십시오. 긴급 중지·롤백은 [실패·긴급 조치](#실패긴급-조치)를 적용하십시오. 긴급 조치에서 일반 승격에 필요한 표본이 모일 때까지 기다리지 마십시오.

1. 대상 route 또는 cohort group의 현재 상태를 확인하십시오.
   확인 대상은 stage, revision, 설정 비율, 실제 serving 분포, 실제 shadow 분포이다.
2. 변경 목적과 목표 상태를 변경 기록에 작성하십시오.
3. [승격 gate](stages-and-gates.md#승격-gate)의 결과와 근거를 기록하십시오.
   확대 변경의 필수 gate에 `fail` 또는 `unknown`이 있으면 확대를 보류하십시오.
   목표 수치나 필요한 표본이 미정인 항목을 `pass`로 기록하지 마십시오.
4. 변경에 사용할 이전 revision이 현재 revision과 일치하는지 확인하십시오.
   두 revision이 다르면 적용을 중지하십시오.
   중지 후에는 최신 상태를 기준으로 변경을 다시 검토하십시오.
5. 새 설정을 [설정 검증·충돌 처리](../routing/configuration.md)에 따라 검증하십시오.
   같은 cohort group의 route들은 전환 활성 상태·배정 정책·v2 비율이 모두 일치해야 한다.
6. 검증된 설정을 기존 배포·설정 적용 절차로 적용하십시오.
7. 설정 전파의 시작 시각과 새 revision을 기록하십시오.
   대상 중 서로 다른 revision이 적용된 기간은 혼합 revision 구간으로 구분하십시오.
8. 모든 대상 인스턴스의 실제 적용 상태를 확인하십시오.
   설정을 독립적으로 읽는 worker가 여러 개이면 각 worker의 신규 요청용 revision도 확인하십시오.
9. 대상별 실제 적용 상태를 기록하십시오.
   기록에서는 원하는 revision, 실제 보고 revision, 보고 누락, revision 불일치, 적용 실패를 구분하십시오.
10. 모든 대상의 신규 요청용 revision이 의도한 값과 일치하는지 판정하십시오.
    보고 누락·revision 불일치·적용 실패 중 하나라도 있으면 적용 완료로 기록하지 마십시오.
11. 실제 serving 분포와 shadow 분포를 확인하십시오.
    Cohort 배정 비율을 실제 요청 비율과 동일하다고 가정하지 마십시오.
12. 적용이 완료되면 새 관측 epoch의 조건을 확인하십시오.
    확인 대상은 설정, 비교 정책, backend 배포, 데이터 문맥, 부하 조건이다.
13. 확인한 조건과 새 epoch의 시작을 기록하십시오.
    변경 전 또는 전파 중에 시작한 요청의 늦은 결과에는 요청 시작 시점의 revision·epoch를 유지하십시오.
14. 새 epoch의 사용자 오류·지연, 비교 완료·제외·드롭, 수집 상태를 관측하십시오.
15. 관측 증거를 기준으로 현재 상태 유지 또는 다음 확대를 판단하십시오.
    다음 확대 전에 필요한 표본·기간과 gate 기준을 모두 충족해야 한다.
    기준이 악화되거나 필수 근거가 미확인이면 확대를 보류하십시오.
    보류 후 조치는 [중지·복귀 절차](rollback-and-bypass.md)에 따라 판단하십시오.

Backend 배포, 비교 정책, 비율 변경은 가능하면 별도 변경으로 수행하는 것을 권장한다. 같은 시점에 바꾸면 어느 변경이 결과에 영향을 주었는지 분리하기 어렵기 때문이다. 동시 변경이 필요한 경우 변경 항목과 원인 분리의 한계를 기록해야 한다.

## 적용 완료와 관측 구간

설정 적용 완료와 다음 단계 승격은 별도로 판정해야 한다. 모든 대상의 신규 요청용 revision이 일치해도 사용자 품질·비교 신뢰도 등의 gate가 자동으로 통과하는 것은 아니다.

전파 상태는 대상별 보고를 근거로 판단한다. 정책 모듈은 제공된 보고의 누락·불일치·실패를 평가한다. 보고를 수집하지 않은 인스턴스까지 실제 배포가 완료되었다고 해석해서는 안 된다.

요청은 시작할 때 확보한 설정 snapshot을 사용한다. 새 revision의 적용 완료 이후에도 이전 snapshot으로 시작한 요청이 남을 수 있다. 담당자는 신규 요청에 적용되는 revision과 기존 요청의 잔여 실행을 따로 확인해야 한다. 전파 전후의 데이터를 동일한 관측 조건으로 합산해서는 안 된다.

## 실패·긴급 조치

변경 담당자는 확인 결과에 맞는 행의 조치를 수행하십시오.

| 확인 결과 | 담당자가 수행할 조치 | 완료 또는 후속 판단 |
| --- | --- | --- |
| 설정 검증 실패 또는 이전 revision 충돌 | 새 설정 적용을 중지하십시오. 검증 오류 또는 최신 revision을 확인하십시오. | 마지막 유효 설정을 유지하십시오. 변경을 수정한 경우 검증 단계부터 다시 수행하십시오. |
| 일부 인스턴스·worker의 적용 실패, 보고 누락 또는 revision 불일치 | 확대를 중지하십시오. 대상별 실제 revision·실패 상태를 기록하십시오. | 보고가 누락된 대상은 실제 적용 상태부터 확인하십시오. 적용 실패로 복구가 필요하면 마지막 유효 설정을 복구 대상으로 선택하십시오. 선택한 복구 변경은 현재 revision을 기준으로 검증하십시오. 대상별 복구 결과를 확인하기 전에는 전체 복구 완료로 기록하지 마십시오. |
| 사전에 정의한 긴급 중지 조건 충족 | 일반 승격 표본 확보를 기다리지 마십시오. Shadow 중지·serving 복귀·우회 중 필요한 조치를 판단하십시오. | v1 serving 복귀를 선택했다면 현재 복귀 준비 상태를 확인하십시오. 준비 조건을 충족한 경우 복귀를 수행하십시오. 조치별 적용 결과와 소요 시간을 기록하십시오. |
| 관측 저장소 장애 | 기존 배포 이력 등 추적 가능한 경로로 긴급 중지·복귀 기록을 유지하십시오. | 저장되지 않은 구간과 복구 후 확인 가능한 범위를 기록하십시오. 비교 요약의 유실 허용 정책을 변경 이력에 자동 적용하지 마십시오. |

## 변경 기록 양식

다음 양식은 변경의 의도와 실제 결과를 구분하기 위한 최소 기록 항목이다. 기존 운영 이력에서 같은 정보를 확인할 수 있으면 별도 입력 제품을 도입할 필요는 없다.

```text
change_id / route_or_group / owner:
current_stage -> next_stage:
previous_revision -> next_revision:
v2_serve_ratio / shadow_sample_ratio / detail_sample_ratio:
backend deployment versions / comparison policy revision:
observation epoch / sample counts / missing intervals:
propagation started_at / mixed revision interval / stable_epoch_at:
G-01 through G-08 results and evidence:
stop conditions / rollback revision / v1 readiness:
requested_at / applied_at / applied_instances:
actual result / recovery time / follow-up:
```

`requested_at`은 변경을 요청한 시각이고, `applied_at`은 증거로 확인한 실제 적용 시각이다. `applied_instances`에는 실제 적용을 확인한 대상을 기록해야 한다. 독립적으로 설정을 읽는 worker가 있으면 worker별 확인 근거도 보존해야 한다. 적용 대상 전체를 확인하기 전에는 요청 시각이나 배포 명령의 종료 시각을 전체 적용 완료 시각으로 대체해서는 안 된다.

`actual result`에는 요청·적용 중·적용 완료·실패·일부 적용·복귀 결과를 구분하여 기록한다. 복구 시간, 관측 누락, 남은 미완료 요청 및 후속 조치는 확인된 값과 미확인 상태를 구분해야 한다.

## 검증 기준

[T-31, T-33](../validation/test-catalog.md)에 따라 revision 충돌·부분 적용·복귀 상황에서 변경 의도, 대상별 실제 상태, 관측 구간과 결과 기록이 구분되는지 검증한다.
