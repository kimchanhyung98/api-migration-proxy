# API Migration Proxy 기획

이 디렉터리는 API Migration Proxy의 제품 요구사항, 기능별 처리 계약, 적용 절차와 판단 기준을 정의한다. 문서에 정의된 요구사항과 현재 구현의 대응 관계는 [구현 구성](implementation/README.md)에서 확인한다.

프록시는 backend 요청을 실행하기 전에 사용자 응답을 제공할 serving을 선택한다. Shadow 적격성, 표본 선택과 자원 상한을 모두 충족한 요청에 대해서만 반대편 backend도 실행한다. 마이그레이션 담당자는 비교·수집 결과와 운영 지표를 확인한 뒤 v2의 serving 비율 변경 여부를 판단한다.

계측·비교·데이터 보호는 프록시 내부에서 수행해야 한다. 내부 snapshot과 상태 조회는 유지하며, 메트릭·상세 상태를 내보내는 HTTP endpoint와 활성화 설정은 제공하지 않는다. 외부 수집기나 SaaS는 내부 처리를 위한 필수 구성 요소가 아니다.

상태 확인은 별도 loopback listener의 `GET /healthcheck` 하나만 제공한다. 실제 접속 peer도 loopback인지 확인해야 한다. 요청 수락 준비 상태이면 200, 준비되지 않았으면 503과 최소 본문을 반환한다. 이전 health 경로의 alias나 외부 접속을 허용하는 token 예외는 제공하지 않는다. 사용자 API 전달 포트는 별도로 유지하고 인터넷에 직접 공개하지 않는 배포 구성을 사용해야 한다.

## 문서의 적용 기준

- 기능 문서의 `해야 한다`는 요구사항을 뜻한다. 해당 문장을 실제 환경에서 검증했다는 뜻으로 해석해서는 안 된다.
- Python/FastAPI는 현재 구현 스택이다. 이벤트 저장은 로컬 SQLite를 기본으로 하며, 운영 조건에 따라 사설 PostgreSQL을 선택할 수 있다. 실행 인프라와 외부 관측 플랫폼은 아직 선정하지 않았다. 특정 운영 환경의 채택·검증 여부는 별도로 확인해야 한다.
- 현재 메트릭은 프로세스 메모리에 있으므로 재시작하면 초기화된다. SQLite의 선택된 shadow 비교 이벤트는 전체 메트릭 집계가 아니며, 저장 이벤트만으로 전체 요청의 분모를 복원해서는 안 된다.
- 운영 임계값과 예시 수치를 구분한다. 대상 API별로 값을 정하도록 명시한 항목은 설명용 예시를 사용하여 충족 여부를 판단해서는 안 된다.
- 문장의 의무 수준, 미확인의 처리와 절차 표기는 [공통 작성 기준](_rules/README.md#문장의-의미와-작성-기준)을 따른다. 기능 문서에 정의한 조건을 다른 기능의 완료 조건으로 대신 사용해서는 안 된다.

## 전체 처리 관계

```mermaid
flowchart LR
    A["API 요청"] --> B["경로·serving 선택"]
    B --> C["serving 실행"] --> D["사용자 응답"]
    B -. "적격성·표본·상한 충족" .-> E["반대편 shadow 실행"]
    C --> F["선택된 요청의 종료 후<br/>비동기 비교·수집"]
    D --> F
    E --> F
    F --> G["관측·수동 전환 판단"]
    C --> H["프록시 내부 실행 계측"]
    E --> H
    H --> G
    G -. "후속 요청에 적용" .-> B
```
