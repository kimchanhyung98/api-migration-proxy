# 응답 정규화와 의미 비교

정규화는 route에 등록된 규칙으로 의도된 차이를 처리하는 과정이다. 의미 비교는 그 규칙을 적용한 두 응답의 status, 계약 class, 필수 header 및 JSON 값을 비교하는 과정이다. 규칙은 비교용 데이터에만 적용하며 사용자 응답 원문을 수정하지 않는다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | [비교 가능 조건](context-and-outcomes.md)을 충족한 완전 응답, route별 비교 정책 revision, 명시된 제외·허용 오차·매핑 규칙을 사용한다. |
| 결과·출력 | 정책 적용 후 `matched` 또는 `different`를 판정하고, 허용 범위의 차이 경로와 정책 적용 결과를 반환한다. |
| 실패·제한 | 정규화로 중요한 회귀를 숨겨서는 안 된다. 캡처 불완전, 파싱 실패 또는 정책 한계 때문에 의미를 확정할 수 없으면 `not_comparable`로 판정한다. |

## 기본 비교 규칙

| 대상 | 기본 동작과 route별 결정 사항 |
| --- | --- |
| status | 같은 코드를 기대한다. 서로 다른 코드를 호환 가능한 것으로 취급하려면 해당 v1·v2 코드 쌍을 정책에 명시해야 한다. |
| 응답 class | 성공과 예상 거절을 구분한다. 예상 밖 오류는 의미 일치 비교에 포함하지 않고 실행 오류로 분류한다. |
| 헤더 | 정책에 명시한 필수 header를 비교한다. 콘텐츠 유형, 캐시 또는 업무상 의미가 있는 header 중 무엇을 선택할지는 route 계약에서 결정해야 한다. |
| JSON 객체 | 키 순서는 무시한다. 필드의 존재 여부, 타입 및 값은 비교한다. |
| JSON 배열 | 순서와 중복을 보존한다. 집합 또는 ID 기준 비교가 필요한 API는 해당 경로의 별도 규칙과 계약 테스트를 정의해야 한다. 별도 규칙이 기본 동작에 자동 적용된다고 가정해서는 안 된다. |
| 숫자 | 숫자의 의미를 보존해 비교한다. float 변환으로 큰 정수나 금액의 정밀도를 잃어서는 안 된다. 허용 오차는 명시한 경로에만 적용한다. |
| 문자열 | 기본적으로 정확히 같은 문자열인지 비교한다. 시간대, 대소문자 또는 Unicode 정규화가 필요하면 그 경로에 적용할 별도 규칙을 정의해야 한다. |
| null·누락 | 필드가 존재하고 값이 null인 경우와 필드 자체가 없는 경우를 다르게 처리한다. |
| 빈 body | HEAD, 204, 304 등이라는 이유만으로 허용하지 않는다. 비교 정책에서 빈 body를 명시적으로 허용한 경우에만 빈 body 비교를 진행한다. |
| 파싱 오류 | 전체 JSON을 해석할 수 없으면 비교 불가로 기록한다. 파싱 가능한 앞부분만으로 판정해서는 안 된다. |
| 비결정적 필드 | 정책에서 지정한 경로만 제외한다. 제외 목록과 comparison policy revision을 유지해야 한다. |

필수 header 이름은 대소문자를 구분하지 않지만, 선택된 header의 값은 비교 대상이다. 필수 header가 한쪽 또는 양쪽에 없으면 필수 header 조건을 충족한 것으로 처리하지 않는다.

## 정규화·비교 순서

비교기는 미실행·실행 오류와 문맥·캡처의 비교 불가 조건을 먼저 제외한다. 나머지 쌍에 다음 자동 처리 순서를 적용한다.

1. 캡처 본문을 정책의 크기 상한 안에서 해석한다.

   압축된 본문이면 지원하는 인코딩을 확인한 뒤 압축을 해제한다.
   인코딩이 지원되지 않거나 유효하지 않으면 `not_comparable`로 종료한다.
   해제 후 크기가 상한을 초과해도 `not_comparable`로 종료한다.

2. 설정된 파싱 상한을 적용하여 JSON을 파싱한다.

   상한은 깊이, 노드 수, 숫자의 자릿수 및 지수를 제한한다.
   중복 키 또는 파싱 한계가 있으면 `not_comparable`로 종료한다.
   임의 값을 선택하여 비교를 계속하지 않는다.
   정책이 허용한 양쪽 빈 body에는 JSON 파싱을 요구하지 않는다.

3. 제외·허용 오차·매핑 등의 정책을 적용하기 전 차이를 계산한다.

   이때의 raw 차이는 해석된 응답의 정책 적용 전 차이이다.
   압축된 전송 바이트 자체의 차이가 아니다.

4. 등록된 필드 매핑을 비교용 데이터에 적용한다.

   매핑을 확정할 수 없으면 `not_comparable`로 종료한다.
   대상 경로에 기존 필드가 있어 충돌하는 경우가 여기에 해당한다.

5. 등록된 status 호환, 필드 제외 및 숫자 허용 오차를 적용해 정규화 후 차이를 계산한다.

   명시되지 않은 경로에는 해당 규칙을 확대 적용하지 않는다.

6. 정규화 후 차이에 따라 최종 결과를 판정한다.

   차이가 있으면 `different`, 없으면 `matched`로 판정한다.

7. 정책 revision, 적용된 규칙 및 제한된 차이 정보를 결과와 함께 반환한다.

필드 경로는 JSON Pointer 형식으로 지정한다. 예를 들어 `/price`는 최상위 `price` 필드를 나타낸다. 그 경로의 제외나 허용 오차가 `/nested/price`에도 적용된다고 해석해서는 안 된다. 객체 키 또는 경로에 민감 정보가 포함될 수 있으므로 차이 경로도 [저장 허용 정책](../collection/detail-sampling.md)을 통과해야 한다.

정책 적용 전(raw) 차이와 정책 적용 후 차이는 구분해야 한다. 최종 `result`는 정책 적용 후 차이로 결정하므로 `matched`여도 raw 차이가 있을 수 있다. 비교 결과에서 계산하는 정보와 저장 이벤트에 포함하는 필드는 같은 것으로 가정해서는 안 된다. 저장 필드는 [이벤트 모델](../collection/event-model.md)을 따른다.

차이 개수의 집계를 제한해 총개수를 확정하지 못한 경우에는 집계 제한 여부를 함께 표시해야 한다. 차이 경로 목록도 허용 경로와 목록 길이의 제한을 받는다. 목록이 비어 있다는 이유만으로 차이가 없다고 판단해서는 안 된다. 정책 적용 내역을 기록하는 것과 응답 원문 값을 저장하는 것은 별개의 동작이다.

## 예시: 상품 상세 API

다음은 양쪽 응답의 계약 class가 `success`이고 나머지 비교 가능 조건을 모두 충족한 가상 상품 데이터이다.

```json
{
  "v1": {"id": "item-101", "price": 12000, "available": true, "request_id": "a"},
  "v2": {"id": "item-101", "price": 12000, "available": true, "request_id": "b"}
}
```

정책에 `/request_id`만 제외하도록 명시하면 이 쌍은 `matched`이다. 같은 정책에서 v2의 `price`를 12500으로 바꾸면 `different`이다. `/price`가 저장 허용 경로이면 차이 경로로 기록할 수 있다. 가격에 무조건적인 오차를 허용하거나, 이름에 timestamp 또는 ID가 있다는 이유로 모든 필드를 일괄 제외해서는 안 된다.

| 변형 | 판정과 해석 |
| --- | --- |
| 객체 키 순서만 바뀐다. | 다른 조건이 같으면 `matched`이다. |
| 한쪽에 `available: null`이 있고 반대편에는 해당 필드가 없다. | `different`이다. |
| 배열 원소의 순서가 바뀐다. | 기본 비교에서는 `different`이다. 집합 의미를 적용하려면 해당 경로의 별도 규칙이 필요하다. |
| v2가 timeout으로 종료된다. | `execution_error`이며 v2의 timeout 결과를 보존한다. |
| 양쪽이 같은 예상 밖 500을 반환한다. | `execution_error`이며 양쪽 예상 밖 오류를 보존한다. |
| 양쪽이 같은 예상 거절 403을 반환한다. | 다른 비교 조건도 충족하면 `matched`, `comparison_class=expected_rejection`이다. |
| v2가 다른 테넌트의 데이터를 반환한 사실을 확인한다. | 권한 불변식 위반으로 조사해야 한다. 중지 여부는 일반 불일치율과 별도로 판단해야 한다. |
| 응답이 캡처 크기 상한을 초과한다. | 더 높은 우선순위의 실행 오류가 없으면 `not_comparable`, `capture_oversized`이다. |

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-18 | P0 | status·필수 header·JSON 의미를 비교해야 한다. | 객체 키 순서만 기본적으로 무시하며, 배열 순서·null·누락·타입 차이는 보존한다. |
| FR-19 | P0 | 제외 필드·허용 오차·좁은 매핑을 버전 관리해야 한다. | 제외 전후 차이와 정책 revision을 추적하고, 업무 핵심 필드가 정책에 명시되지 않은 채 제외되지 않도록 한다. |
| FR-26 | P1 | 업무별 비교 확장은 필요한 API에만 적용해야 한다. | 집합·순위·비결정적 결과 규칙을 추가할 때 해당 계약 테스트로 검증한다. |

## 검증 기준

검증 담당자는 [T-10, T-18, T-19, T-20, T-40](../validation/test-catalog.md)를 적용하십시오. 기본 의미 보존과 명시한 경로에 한정된 규칙 적용을 확인하십시오. 사용자 응답 원문 보존을 확인하십시오. 확장 규칙의 회귀 여부를 확인하십시오.
