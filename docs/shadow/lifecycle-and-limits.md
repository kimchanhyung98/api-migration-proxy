# 실행 수명·취소·자원 제한

프록시는 serving, shadow, 사용자 응답 전송과 내부 비교·저장 작업의 종료 상태를 각각 관리한다. 이 문서는 각 작업의 시간·자원 상한과, 정상 완료·timeout·호출자 취소·프로세스 종료에 따른 처리 차이를 정의한다.

여기서 timeout은 설정한 대기·실행 기한의 만료이고, 취소는 진행 중 작업을 중단하려는 요청이다. 어느 경우도 backend에서 이미 발생한 업무 효과를 되돌렸다는 뜻이 아니다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 역할별 timeout·동시 실행 한도, 요청 복제·응답 캡처 상한, 비교·저장 큐 예산과 client·프로세스 종료 신호를 사용한다. |
| 결과·출력 | 프록시는 완료·timeout·취소·미실행을 구분하고, 작업 종료와 자원 회수 상태를 관측한다. |
| 실패·제한 | 작업·대기열을 무한히 늘려서는 안 된다. 취소를 시도했다는 사실만으로 backend 효과 취소, 실제 CPU 작업 종료 또는 정확한 유실 개수를 보장해서는 안 된다. |

## timeout·취소·실패

### 시간 예산의 적용 범위

| 예산 | 시작·종료 범위와 주의사항 |
| --- | --- |
| HTTP connect·read·write·pool timeout | 각 연결·읽기·쓰기·연결 풀 대기를 제한한다. read timeout 이내로 chunk가 계속 도착해도 전체 실행이 무제한 지속되어서는 안 된다. |
| 역할별 총 실행 deadline | serving과 shadow 각각의 backend 실행을 제한한다. 연결 풀 대기도 이 예산에 포함한다. 두 역할은 각자의 기한을 사용한다. |
| 요청 body 확보 예산 | shadow에 복제할 body를 읽는 대기를 제한한다. body 확보가 끝나지 않았는데 요청 입력을 완전히 확보했다고 처리해서는 안 된다. |
| 사용자 응답 전송 예산 | 사용자 전달 작업의 대기와 headers·body 전송을 제한한다. backend 수신 종료와 사용자 전송 종료는 서로 다른 상태이다. |
| 응답·연결 정리 예산 | 실행 완료·실패·취소 후 streaming 응답과 연결 자원을 닫는 작업을 제한한다. 실행 deadline이 이미 끝났다는 이유로 정리 기회를 0으로 만들어서는 안 된다. |
| 비교·저장 작업 수명 | 큐 대기 age와 실제 처리·쓰기·재시도를 제한한다. 큐에서 기다린 시간도 최대 수명 판단에 포함해야 한다. |

현재 응답 정리는 요청 실행 deadline과 별도의 유한 예산으로 수행한다. 호출자 취소가 도착해도 연결 자원을 반환하는 정리 작업은 보호하되, 취소 사유를 정상 완료로 바꾸지 않는다. 역할별 실행, 사용자 전송과 자원 정리는 서로 다른 시간 예산을 사용한다. 개별 예산 준수를 전체 요청이나 프로세스 종료가 그중 하나의 시간 안에 끝난다는 보장으로 해석해서는 안 된다.

초기 운영안은 역할별 총 시간 예산과 검증된 HTTP 클라이언트 기본 설정을 사용하는 것이다. 실제 운영값은 대상 API의 지연·크기·부하와 종료 조건을 확인하여 정해야 한다. HTTP 구현의 범위는 [HTTPX·실행 환경 제약](../research/service-options-and-constraints.md)을 따른다.

### 상황별 처리

| 확인된 상황 | serving·사용자 응답 처리 | shadow·수집 처리 |
| --- | --- | --- |
| serving 실행과 사용자 응답 전송이 정상 완료됨 | 선택한 응답을 완료 상태로 기록한다. | 이미 시작한 shadow는 자신의 deadline까지 유지할 수 있다. 정상 응답 완료만을 이유로 일괄 취소하지 않는다. |
| shadow가 timeout 또는 전송 오류로 종료됨 | 진행 중인 serving을 계속 처리한다. | 실패 결과를 기록하고 재시도하지 않는다. serving이 끝나기 전에 양쪽 실행 종료를 확정해서는 안 된다. |
| serving이 timeout으로 종료됨 | 응답 headers 전송 전이면 504를 생성하고, 이미 보낸 뒤이면 불완전 전송으로 종료한다. | 이미 시작한 shadow는 제한 시간 안에서 결과를 수집할 수 있다. 그 응답을 사용자 응답으로 대체하지 않는다. |
| serving 연결이 실패함 | 응답 headers 전송 전이면 502를 생성한다. headers 전송 후 실패는 불완전 전송으로 처리한다. | 반대편 backend로 fallback하지 않는다. |
| 사용자 전송 완료 전에 client 연결 종료가 확인됨 | 진행 중 upstream 실행의 취소를 시도한다. 성공한 사용자 전송으로 기록하지 않는다. | 실행 중 shadow의 취소도 시도하고 종료 사유를 유지한다. |
| shadow 실행 슬롯이 없음 | serving 전달을 계속한다. | 신규 shadow를 생략한다. 슬롯이 날 때까지 무한 대기열에 쌓지 않는다. |
| 요청 복제 상한을 넘음 | 이미 읽은 prefix와 남은 입력을 이어서 전달한다. | shadow 실행을 생략하고 선택 사실·미실행 사유를 유지한다. |
| 응답 캡처 상한을 넘음 | 지원 범위 안의 serving 응답 전송을 계속한다. | 비교용 캡처를 중단한다. 일부 바이트를 완전한 JSON으로 판정해서는 안 된다. |
| 비교 큐 또는 저장소에 장애가 발생함 | serving 전달은 계속한다. | 감지한 드롭·실패를 계측한다. 운영자는 해당 관측 장애가 해소되고 승격 근거가 확보되기 전까지 단계 확대를 중지해야 한다. |
| 프로세스 정상 종료가 시작됨 | 신규 요청 수락을 중단하고 진행 중 요청에 배출 시간을 부여한다. | 잔여 작업을 제한된 예산 안에서 배출하고, 완료하지 못한 상태와 유실 가능성을 구분한다. |

응답 headers 전후의 정확한 전송 처리는 [HTTP 전달 계약](../routing/http-forwarding.md)을 따른다. 프록시가 502·504를 생성할 수 있어도 이미 끊어진 호출자 연결로 전송할 수 있다는 보장은 없다.

### 호출자 연결 종료의 판정

프록시는 연결 종료 신호를 받았을 때 사용자 응답 전송의 완료 여부를 함께 확인해야 한다. ASGI `http.disconnect`는 정상 응답 완료 뒤에도 발생할 수 있다. 따라서 이 신호만으로 정상 완료 요청을 client 취소로 바꾸거나 기존 shadow를 취소해서는 안 된다. [ASGI HTTP 규격](https://asgi.readthedocs.io/en/latest/specs/www.html#disconnect-receive-event)의 관측 경계를 따른다.

사용자 전송 완료는 서버가 확인한 전송 종료를 뜻한다. ASGI `send()`가 완료되었다고 해서 최종 client가 전체 body를 수신하고 업무 처리를 끝냈다고 판정해서는 안 된다. 적용 환경에서는 실제 서버·프레임워크의 연결 종료 동작을 검증해야 한다.

client 취소나 upstream 취소 시도가 있어도 backend가 이미 수행한 DB 변경·외부 호출을 취소했다고 가정해서는 안 된다. 취소된 요청도 선택·실행 분모와 종료 사유에 남겨야 한다. 초기 shadow 범위를 부작용 없는 API로 제한하는 이유와 적격성 검토는 [복제 조건](eligibility-and-sampling.md)을 따른다.

## 프로세스 종료와 자원 회수

아래 순서는 프록시 프로세스가 정상 종료를 시작했을 때의 처리 기준이다. 외부 진입점의 연결 배출·플랫폼 강제 종료와의 연결은 [배포·종료 계약](../infrastructure/deployment-and-stack.md)에서 별도로 확인한다.

1. 프록시는 신규 요청 수락을 중단한다. 그 뒤에 들어오는 요청을 기존 작업의 배출 대상으로 계속 추가해서는 안 된다.
2. 프록시는 진행 중 요청과 이미 등록한 양쪽 결과 취합 작업의 완료를 종료 배출 예산 안에서 기다린다. 이때 정상 완료한 사용자 요청의 shadow가 남아 있을 수 있다.
3. 배출 기한에 남아 있는 실행에는 취소를 요청한다. 취소 요청 시각을 자원 반환 완료 시각으로 기록해서는 안 된다.
4. 프록시는 취소한 실행의 응답·연결 정리를 수행한다.
5. 프록시는 비교·저장 큐를 남은 예산 안에서 처리한다. 완료하지 못한 작업의 드롭·미확인 상태는 유지한다.
6. 프록시는 연결 풀과 저장 자원을 닫는다.

종료 결과를 확인하는 담당자는 실제 잔여 작업과 회수 상태를 함께 확인해야 한다.

실행 중인 thread는 비동기 대기 취소만으로 강제 종료되지 않을 수 있다. 작업이 실제로 끝나기 전에는 해당 작업의 슬롯·캡처 메모리를 반환한 것으로 집계해서는 안 된다. 종료 이후에도 남는 작업이 있으면 그 자원과 수집 완전성의 한계를 표시해야 한다. 프로세스 강제 종료로 유실된 결과를 정확히 셀 수 없으면 정확한 유실 개수로 보고해서는 안 된다.

## 자원 예산

| 예산 | 제한할 대상 | 상한 도달·초과 시 처리 기준 |
| --- | --- | --- |
| serving 동시 실행 | 현재 처리 중인 사용자 요청과 연결 | 현재 애플리케이션은 상한에 도달하면 신규 요청을 503으로 거부한다. 운영자는 이 신규 요청 수락 제한과 기존 서비스 SLO의 적합성을 검증해야 한다. |
| shadow 동시 실행 | 반대편 요청·연결과 결과 취합까지 보유한 슬롯 | 신규 shadow를 생략하고 사유를 계측한다. |
| 요청 복제 bytes | 입력 body와 복사본을 제한한다. 압축 해제를 수행하면 해제 바이트도 제한한다. | 누적 bytes가 상한보다 커지면 추가 복제를 중단하고 shadow를 생략한다. 검증된 serving 전달은 유지한다. |
| 응답 캡처 bytes | 비교용 body를 제한한다. 압축 해제를 수행하면 해제 바이트도 제한한다. | 누적 bytes가 상한보다 커지면 캡처를 중단한다. 비교 조건에 따라 `not_comparable`로 처리하며 serving body를 자르지 않는다. |
| JSON 복잡도·CPU | 입력 bytes, 파싱 깊이·노드 수와 비교 작업 시간 | 진입 한도와 지원되는 중단 방식을 적용하고 제한에 도달한 원인을 기록한다. |
| 큐 개수·bytes·age | 비교 대기·저장 대기 작업 | 정해진 한도에서 드롭·만료시키고 이를 계측한다. |
| batch 크기·쓰기 시간 | 저장소 쓰기와 재시도 | 제한된 재시도 예산을 넘으면 드롭 또는 저장 확인 불가 상태를 수집 계약에 따라 구분한다. |
| 상세 보존량 | 상세 표본과 만료 처리 | 보존 예산을 유지하기 위한 표본 축소 또는 상세 수집 중지를 검토한다. 이 선택은 적용할 수 있는 운영 대응이며 자동 조절 기능을 전제하지 않는다. |

본문 캡처 상한은 프로세스 전체 메모리 상한과 다르다. 메모리를 산정할 때에는 진행 중 캡처, 요청 복사본, 큐 entry, parser와 HTTP 클라이언트 overhead를 함께 포함해야 한다. 양쪽 응답을 보관하는 큐는 entry 수와 총 bytes를 동시에 제한해야 한다. 압축된 body 크기만으로 해제 후 메모리를 계산해서는 안 된다.

현재 구현은 본문 바이트 수와 JSON 깊이를 파싱 전에 검사하고, 숫자의 자릿수·지수 한도는 파싱 중에 검사한다. JSON 노드 수는 파싱 후 검사하므로 노드 한도만으로 파서의 메모리 사용량을 제한할 수 없다.

비동기 timeout이 동기 CPU 연산을 즉시 선점 중단한다고 가정해서는 안 된다. 취소 뒤에도 실행 중인 작업은 실제 종료될 때까지 실행·메모리 예산에 포함한다. [AnyIO thread 취소 경계](https://anyio.readthedocs.io/en/stable/threads.html#reacting-to-cancellation-in-worker-threads)를 참고한다.

serving과 shadow의 실행·연결 예산은 shadow가 serving 자원을 모두 점유하지 못하도록 구분해야 한다. 현재 구현은 역할별 연결 풀과 실행 한도를 분리한다. 다른 공유 방식으로 변경한다면 같은 serving 여유와 최대 영향 범위를 입증해야 하며, 단순히 풀을 공유한다는 이유만으로 격리 조건을 충족했다고 판정해서는 안 된다.

한도 L이 적용되는 실행 단위가 N개이면 전체 동시 실행은 최대 N×L까지 늘어날 수 있다. 예를 들어 한도가 프로세스별이면 N에는 실제 실행 프로세스 수를 사용해야 한다. 자동 확장으로 N이 늘어날 때의 전체 shadow 예산을 용량 모델에 반영해야 한다. 분산 limiter를 도입하기 전에는 실행 단위별 예산과 최대 replica 수로 전체 상한을 관리할 수 있는지 검토한다.

## 검증 기준

[T-14, T-16, T-17, T-18, T-23, T-36, T-38, T-42, T-44](../validation/test-catalog.md)에 따라 느린 shadow·client, body·큐 상한, timeout·취소와 프로세스 종료를 각각 검증한다. timeout 뒤에는 종료 지표만 확인하지 말고 연결 풀의 재사용 가능 여부, 실제 잔여 작업과 캡처 메모리까지 확인해야 한다.
