# 복제 적격성 판단과 표본 선택

복제 적격성은 동일 논리 요청을 반대편 backend에도 실행할 수 있는지에 대한 판단이다. 표본 선택은 적격 요청 중 실제 shadow 실행을 시도할 요청을 고르는 별도 판단이다. 두 판단을 통과해도 실행 슬롯·입력 상한·취소 조건에 따라 shadow가 실행되지 않을 수 있다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | API 소유자가 확인한 실제 효과·권한·데이터 계약, route의 전환 활성 상태, cohort 배정 결과, shadow 표본율과 중지 상태를 사용한다. |
| 결과·출력 | 프록시는 `ineligible`, `sampled_out`, `selected` 중 하나로 선택 결과를 구분한다. 선택 후 실제 실행 여부는 별도로 기록한다. |
| 실패·제한 | 부작용·권한·데이터 계약이 확인되지 않은 경로를 복제해서는 안 된다. `selected`를 backend 실행 시작이나 정상 완료와 동일하게 해석해서는 안 된다. |

## 세 가지 비율

| 이름 | 적용 대상 | 의미 |
| --- | --- | --- |
| `v2_serve_ratio` | 전환이 활성화된 route의 배정 단위 | serving을 v2에 배정할 bucket 비율이다. |
| `shadow_sample_ratio` | 복제 적격 요청 각각 | 반대편 backend 실행 대상으로 선택할 확률이다. |
| `detail_sample_ratio` | 상세 수집이 허용된 비교 이벤트 | 마스킹된 상세 표본을 저장할 확률이다. |

세 비율의 허용 범위는 모두 `0 <= 비율 <= 1`이다. 초기 제안값은 모두 0이며, 이 제안을 모든 운영 환경의 확정값으로 해석해서는 안 된다. 실제 변경은 해당 전환 단계와 자원 예산에 따라 결정한다.

shadow 선택에는 serving cohort와 독립적인 난수 또는 별도 salt를 사용해야 한다. 특정 serving 집단의 bucket을 그대로 재사용하여 그 집단만 비교 대상으로 선택해서는 안 된다. 현재 구현은 요청별 독립 난수를 shadow 선택에 사용한다.

상세 표본 선택은 backend 실행 여부나 비교 여부를 바꾸지 않는다. MVP에는 비교 CPU용 표본율을 별도로 두지 않는다. 확보한 양쪽 결과는 비교 조건과 CPU 예산 안에서 처리하고, 처리하지 못하면 누락과 원인을 구분해야 한다. 전체 shadow 실행과 별도의 비교 표본율을 운영하는 방안은 추가 제어와 분모 정의가 필요한 별도 검토 항목이다.

## 적격성 판정 순서

### route 활성화 전에 수행할 검토

API 소유자는 eligibility를 활성화하기 전에 다음 절차를 수행하십시오. 이 절차는 route 정책을 정할 때 적용한다. 요청마다 API 소유자가 개입하는 절차가 아니다.

1. 대상 route가 지원 프로토콜·콘텐츠·본문 크기 범위에 속하는지 확인하십시오. 지원 범위 밖이면 shadow를 활성화하지 마십시오.
2. 같은 요청을 양쪽에 실행했을 때의 DB 변경, 외부 호출, cache 변경과 사용 한도(quota) 소비를 확인하십시오. GET이라는 이유만으로 부작용이 없다고 판정하지 마십시오.
3. 양쪽의 인증·권한·tenant 문맥과 입력 의미를 대조하십시오. 복제 허용 여부를 확인하지 못하면 eligibility를 활성화하지 마십시오.
4. 실제 효과·권한·데이터 검토 근거를 route에 연결하십시오.
5. eligibility를 활성화하는 설정에 해당 검토 참조를 포함하십시오.

검토 참조가 설정에 존재한다는 사실만으로 실제 업무 효과가 안전하다고 입증되지는 않는다. 검토한 API 계약이 바뀌면 변경된 조건을 다시 확인해야 한다.

### 각 요청에 적용할 판정

프록시는 serving을 선택한 뒤 아래 순서로 shadow 선택을 판단한다. E는 적격 요청 수, S는 E 중 shadow 표본으로 선택한 요청 수이다. 전체 분모 관계는 [비교 커버리지](../observability/coverage-and-analysis.md)를 따른다.

1. 등록된 지원 route가 있고, `rollout_enabled=true`이며, route의 shadow eligibility가 활성이고, serving 배정 사유가 `missing_cohort_key`가 아닌지 확인한다. 네 조건을 모두 충족해야 한다.
2. 조건 중 하나라도 충족하지 않으면 `ineligible`로 정하고 선택 절차를 종료한다. 이 요청은 E와 S에 포함하지 않으며 shadow를 실행하지 않는다.
3. 모든 조건을 충족하면 E를 증가시킨다. 이 시점에는 표본 선택이나 실제 실행이 완료된 것이 아니다.
4. shadow 중지 상태이면 선택 결과를 `sampled_out`으로 정하고 선택 절차를 종료한다. 이 경우 S는 증가하지 않는다. 중지 상태가 아니면 5단계로 진행한다.
5. 독립적인 표본값과 shadow 비율을 비교한다. `표본값 < shadow_sample_ratio`이면 `selected`로 정하고 S를 증가시킨다. 그 밖의 경우에는 `sampled_out`으로 정하고 선택 절차를 종료한다.
6. `selected` 요청만 [실행 슬롯·입력 상한 확인](parallel-execution.md)으로 넘긴다. 이후 실행하지 못하더라도 S에서 빼지 않는다.

현재 선택 결과에서 `sampled_out`은 난수 표본에서 제외된 경우뿐 아니라 shadow 중지 상태도 포함한다. 중지로 인한 S=0을 관측 장애나 적격 요청 부재로 해석해서는 안 된다. 중지 여부는 해당 요청의 설정 revision과 함께 확인해야 한다.

## 경계 사례

| 조건 | 선택·실행 결과 |
| --- | --- |
| serving이 v2임 | shadow를 선택하고 실행할 수 있으면 반대편 v1에 요청한다. |
| 적격 요청이고 shadow 비율이 0임 | E에는 포함하지만 S에는 포함하지 않는다. shadow를 실행하지 않는다. |
| 적격 요청이고 shadow 중지 상태가 아니며 비율이 1임 | 모든 적격 요청을 S에 포함한다. 실행 슬롯·입력 상한·취소에 따라 실제 실행 수는 S보다 작을 수 있다. |
| 표본 선택 후 슬롯이 부족하거나 요청 복제 상한을 넘음 | `selected` 상태와 S를 유지한다. 미실행 결과를 실제 시작한 요청과 구분한다. |
| shadow eligibility 또는 관련 계약이 변경됨 | 변경 이후 요청의 E·S를 설정 revision과 함께 구분한다. 과거 조건과 같은 실험으로 합산해서는 안 된다. |

양쪽 실행은 공통 DB·cache·외부 quota를 사용할 수 있다. shadow 자체의 동시 실행 한도를 지켰더라도 공유 의존 시스템의 부하가 허용 범위인지 별도로 확인해야 한다. 이 영향은 [용량·비용 검증](../infrastructure/capacity-and-cost.md)에 포함한다.

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-09 | P0 | 실제 업무 효과에 따라 shadow eligibility를 정의해야 한다. | route 등록만으로 복제하지 않으며, 부작용·권한·데이터 계약을 확인하지 않은 경로는 shadow를 허용하지 않는다. |
| FR-10 | P0 | shadow 표본율과 serving 비율을 독립적으로 설정해야 한다. | v2 serving에서는 v1을 shadow로 사용한다. 중지되지 않은 비율 1의 적격 요청은 실행 제한·취소가 없을 때 양쪽에 각각 한 번 실행하고, 미실행이 생겨도 선택 분모와 사유를 유지한다. |

## 검증 기준

[T-11, T-12, T-16](../validation/test-catalog.md)에 따라 부적격, 비율 0·1, 중지 상태와 선택 후 미실행을 각각 검증한다. E·S가 바뀌는 지점과 실제 backend 실행이 시작되는 지점은 서로 구분하여 확인해야 한다.
