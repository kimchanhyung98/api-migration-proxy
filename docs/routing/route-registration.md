# API 경로 등록과 지원 범위

이 문서는 API 소유자와 설정 변경 담당자가 마이그레이션 대상 route를 등록할 때 확인할 입력, 검증 순서와 실패 처리 기준을 정의한다. route는 같은 HTTP method, 경로 의미와 공개 API 계약을 공유하는 등록 단위이다. path template은 고정 구간과 동적 parameter로 요청 경로를 표현한 패턴이다. 개별 호출자의 raw URL을 route ID로 사용하지 않는다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 등록 대상의 method·path template, route ID, v1/v2 목적지, 전환 활성 여부, API 계약과 소유자가 식별되어 있어야 한다. |
| 결과·출력 | 요청은 하나의 등록 route에만 일치하거나, 미등록 요청으로 판정되어 기본 v1으로 전달된다. 미지원 프로토콜의 진입 경로는 운영 구성에서 별도로 유지해야 한다. |
| 실패·제한 | 중복 route, 모호한 경로 일치와 허용하지 않은 목적지가 있으면 설정을 거부한다. 미지원 프로토콜을 프록시가 투명하게 전달하거나 자동 우회한다고 가정해서는 안 된다. |

## 등록할 정보

| 정보 | 작성·확인 기준 |
| --- | --- |
| route ID | raw URL이나 호출자 입력과 독립된 안정적인 식별자를 정해야 한다. 같은 설정 안에서 중복되어서는 안 된다. |
| method·path template | method와 고정 경로 구간, 동적 경로 구간을 각각 명시해야 한다. 동적 구간은 `/catalog/{id}`처럼 경로 segment 전체를 차지해야 한다. |
| v1/v2 목적지 | 운영자가 허용한 고정 HTTP 또는 HTTPS origin을 지정해야 한다. origin은 scheme·host·port로 이루어진 목적지 기준 주소이다. 호출자의 헤더·query·body로 목적지 호스트를 선택하게 해서는 안 된다. |
| API 계약 | 정상 응답, 예상 거절, 업무 오류, 필수 헤더·body, 인증·권한 의미, 지원 콘텐츠 형식과 본문 크기 범위를 기록해야 한다. |
| 실행 적격성 | 동일 요청을 양쪽에 실행했을 때 발생하는 업무 효과와 권한·데이터 검토 결과를 연결해야 한다. route 등록만으로 shadow를 허용해서는 안 된다. |
| 소유자 | 대상 API의 계약과 전환 조건을 확인할 담당 역할을 명시해야 한다. |

경로 매칭은 method와 path template을 함께 사용한다. 같은 method에서 두 template이 같은 요청에 일치할 가능성이 있으면 설정을 거부한다. 예를 들어 `GET /catalog/{id}`와 `GET /catalog/search`를 함께 등록한 뒤 정적 경로가 우선한다고 추정해서는 안 된다. 서로 다른 method는 별개로 판단한다. wildcard와 명시되지 않은 우선순위 규칙은 사용하지 않는다.

목적지 origin에는 credential, 별도 path, query 또는 fragment를 넣지 않는다. backend별 경로가 원래 요청 경로와 다를 때에는 명시적인 path 매핑을 사용한다. 매핑은 등록된 동적 parameter를 모두 보존해야 하며 새 parameter를 만들어서는 안 된다. 인코딩 보존과 매핑의 문자 제한은 [HTTP 전달 계약](http-forwarding.md)을 따른다.

## 등록과 검증 흐름

다음 절차는 route를 추가하거나 method·template·목적지·공개 계약을 변경할 때 적용한다. API 소유자는 계약 확인 절차를 수행한다. 설정 변경 담당자는 확인된 계약으로 등록값 검증·반영 절차를 수행한다.

### API 계약 확인

API 소유자는 다음 순서로 등록 입력을 준비하십시오.

1. 대상 method, 경로와 입력·응답 예시를 정리하십시오.
2. 호출자와 지원 프로토콜·콘텐츠 형식·본문 크기 범위를 식별하십시오.
3. 입력·응답·인증·권한 계약을 확인하십시오.
4. 양쪽 실행의 업무 효과를 확인하십시오. shadow 활성화에는 [복제 적격성 검토](../shadow/eligibility-and-sampling.md)가 필요하다.
5. 확인한 계약과 검토 근거를 등록 입력에 연결하십시오. 확인하지 못한 항목이 있으면 그 항목을 미확인으로 표시하십시오.

### 등록값 검증·반영

설정 변경 담당자는 위 등록 입력이 준비되면 다음 절차를 수행하십시오.

1. route ID와 v1/v2 목적지를 정하십시오.
2. backend별 경로가 원래 요청 경로와 다르면 path 매핑을 명시하십시오. 경로가 같으면 매핑을 추가할 필요가 없다.
3. 같은 설정의 route 전체에서 ID 중복과 template 충돌을 검사하십시오. 충돌이 있으면 등록값을 수정한 뒤 3단계를 다시 수행하십시오. 목록 순서로 충돌을 해결하지 마십시오.
4. 목적지 허용 목록, cohort group, 정책 revision과 자원 상한을 포함하여 [설정 검증](configuration.md)을 수행하십시오. 실패하면 반영 절차를 중단하십시오. 마지막 유효 설정은 유지된다.
5. 검증된 route를 해당 전환 단계의 설정에 반영하십시오. route 등록만을 이유로 v2 비율이나 shadow 비율을 올리지 마십시오.
6. [설정 적용 절차](configuration.md)에 따라 실제 반영 결과를 확인하십시오.

등록 검증의 완료 조건은 route가 하나로 식별되고, 고정 목적지와 공개 계약이 정해져 있으며, 선택한 전환 상태에 필요한 값이 모두 유효한 것이다. 이 조건을 충족하지 않은 route를 활성화해서는 안 된다.

## 미등록·미지원 요청

| 요청 또는 변경 | 처리 기준 |
| --- | --- |
| 지원이 검증된 일반 HTTP 요청이 어떤 route에도 일치하지 않음 | 프록시는 설정의 기본 v1으로 전달한다. 이 요청에 v2 배정이나 shadow 실행을 추가하지 않는다. |
| 등록 route의 전환을 비활성화함 | 프록시는 해당 route에 등록된 v1으로 전달한다. 설정의 기본 v1과 route의 v1이 같은 주소라고 가정해서는 안 된다. |
| route를 설정에서 제거함 | 이후 같은 요청은 다른 route에 일치하는지 다시 판단하고, 일치하지 않으면 기본 v1으로 전달한다. 변경 담당자는 이 결과가 기존 호출 계약을 보존하는지 확인해야 한다. |
| SSE·WebSocket·gRPC·대용량 전송 등 지원이 검증되지 않은 경로 | 운영 구성에서 기존 진입점을 유지해야 한다. 프록시가 이 경로를 감지하여 자동으로 기존 진입점에 우회시키는 기능을 전제로 해서는 안 된다. |

등록 route 일부가 v2 serving에 도달해도 서비스 전체의 전환이 끝난 것은 아니다. 전환 종료를 판단하는 담당자는 미등록 경로와 미지원 경로가 여전히 v1을 사용하는지 [종료 조건](../rollout/retirement.md)에 따라 확인해야 한다.

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-01 | P0 | method·path template으로 route와 고정된 v1/v2 목적지를 등록해야 한다. | 중복 route, 모호한 경로 일치 또는 잘못된 목적지가 있으면 활성화 전에 설정을 거부한다. |
| FR-08 | P0 | 미등록·미지원 경로의 처리 방식과 책임을 명시해야 한다. | 검증된 일반 HTTP의 미등록 요청은 기본 v1으로 전달하고, 미지원 프로토콜은 운영 구성에서 기존 진입점을 유지한다. |

## 검증 기준

[T-01, T-03, T-11, T-39, T-48](../validation/test-catalog.md)에 따라 등록·미등록·비활성·충돌 사례를 구분하여 검증한다. route를 제거하거나 비활성화하는 검증에서는 실제 목적지가 원래 계약과 일치하는지도 확인해야 한다.
