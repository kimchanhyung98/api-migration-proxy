# 설정 스냅샷 검증과 적용

설정 스냅샷은 특정 revision에서 사용할 route·목적지·배정·실행 정책을 고정한 값이다. 프록시는 요청을 수락할 때 스냅샷 하나를 선택하고, 그 요청이 끝날 때까지 같은 값을 사용한다. 설정 변경 담당자는 새 설정의 유효성과 실제 적용 상태를 구분하여 확인해야 한다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 변경 담당자는 현재 revision, 새 revision, 등록 경로·목적지·정책·운영 상한과 변경 사유를 준비한다. 반영 시 변경 주체도 식별해야 한다. |
| 결과·출력 | 설정 반영에 성공하면 신규 요청에 새 불변 스냅샷을 사용한다. 적용한 worker의 revision과 변경 이력도 제공한다. |
| 실패·제한 | 유효하지 않거나 현재 revision과 충돌하는 갱신은 거부한다. 기존 유효 설정이 있으면 유지하고, 최초 유효 설정이 없으면 요청 처리 준비가 된 것으로 표시하지 않는다. |

## 설정 모델

설정 변경 담당자는 어떤 공급원의 정책 묶음을 적용 기준으로 삼는지 정해야 한다. 서로 다른 revision의 목적지·배정·비교 정책이 부분 덮어쓰기로 섞이게 해서는 안 된다. 아래 표는 정책을 설명하기 위한 논리 모델이며, 하나의 설정 파일이 모든 정책을 직접 포함한다는 의미는 아니다.

| 설정 묶음 | 명시할 값 |
| --- | --- |
| 식별 | schema version, 새 revision, 이전 revision과 변경 사유를 명시해야 한다. |
| 목적지 | 기본 v1과 route별 v1/v2를 지정해야 한다. backend별 경로가 다를 때에는 명시적인 path 매핑을 추가해야 한다. |
| 범위 | route ID, method·path template, 전환 활성 여부와 shadow eligibility를 지정해야 한다. |
| 배정 | v2 비율, cohort 방식·그룹·키 출처와 salt를 식별해야 한다. |
| 복제 | shadow 표본율, shadow 중지 상태와 실행 한도를 지정해야 한다. |
| 비교·수집 | 활성 기능에 필요한 comparison policy revision, 캡처 상한, 상세 표본율·허용 필드와 보존 정책을 지정해야 한다. |
| 자원 | 역할별 timeout·동시 실행 한도, 큐 개수·bytes·age, 비교 작업 수명, batch·저장 재시도 예산을 지정해야 한다. |

명시적인 전환 전에는 v1 전달과 shadow 비활성 상태를 유지해야 한다. 시간·동시 실행·캡처·큐 예산에는 유한한 상한을 사용해야 한다. 필수값을 결정하지 못한 route를 활성화해서는 안 된다.

| 전환 설정 | 의미 |
| --- | --- |
| `rollout_enabled=false` | route의 v1으로만 전달하며 shadow를 실행하지 않는다. |
| S2에서 `rollout_enabled=true`, `v2_serve_ratio=0`, `shadow_sample_ratio>0` | serving은 v1이다. shadow 적격성·표본·실행 한도를 충족한 요청은 v2에도 실행한다. |
| shadow 중지 상태만 활성화 | 신규 shadow 선택을 중지한다. `v2_serve_ratio`에 따른 serving 배정은 유지한다. |

전체 전환 비활성화와 shadow 중지는 결과가 다른 조작이다. shadow를 중지하려는 목적으로 `rollout_enabled=false`를 적용하면 serving도 v1으로 돌아간다. 변경 담당자는 원하는 결과에 해당하는 값을 선택해야 한다.

다음은 비활성 route의 논리 설정 예시이며, 실행 가능한 완전한 설정 파일이 아니다. 예시의 `null`은 검증 전 미정 값이다. `null`을 무제한 또는 자동 기본값으로 해석해서는 안 된다.

```yaml
schema_version: 1
revision: example-draft-001
default_backend: v1
routes:
  - route_id: catalog_detail
    method: GET
    path_template: /catalog/{id}
    rollout_enabled: false
    backends:
      v1: https://v1.example.invalid
      v2: https://v2.example.invalid
    v2_serve_ratio: 0
    cohort:
      mode: user
      group: catalog
      key_source: trusted_identity
      salt_ref: null
    shadow:
      eligible: false
      sample_ratio: 0
      timeout_ms: null
      max_inflight: null
    comparison:
      policy_revision: null
      capture_limit_bytes: null
    collection:
      detail_sample_ratio: 0
      retention_days: null
```

credential 원문을 설정 예시나 변경 이력에 저장해서는 안 된다. credential이 필요한 실제 구성에서는 기존 비밀 관리 방식의 참조를 사용해야 한다.

## 활성화 전 검증

변경 담당자는 새 revision을 적용하기 전에 아래 항목을 검사해야 한다. 애플리케이션의 형식 검증이 성공해도 API의 업무 효과·권한·데이터 계약 검토가 완료된 것으로 간주해서는 안 된다.

| 검증 대상 | 거부 조건 또는 확인할 근거 |
| --- | --- |
| 비율 | 0보다 작거나 1보다 큰 값, 숫자가 아닌 값, 비유한 값은 거부한다. 0과 1은 허용한다. |
| 시간·동시 실행·캡처·큐 상한 | 필요한 값이 없거나 유효한 양의 유한 값이 아니면 거부한다. 개수·bytes 한도에는 정수를 사용한다. |
| route·목적지 | route ID 중복, 같은 method에서의 template 충돌 또는 운영자 허용 목록 밖의 backend를 거부한다. 목적지 origin의 제한은 [경로 등록](route-registration.md)을 따른다. |
| 목적지 path 매핑 | 등록 parameter를 없애거나 추가하는 매핑을 거부한다. 정적 segment의 raw 비ASCII 문자와 DEL도 거부하며, 자동 Unicode 변환으로 수용하지 않는다. |
| cohort group | 그룹 내부의 전환 활성 상태·배정 단위·키 출처·해시·직렬화·salt·v2 비율 중 하나라도 다르면 거부한다. |
| shadow | eligibility를 활성화하려면 실제 효과·권한·데이터 계약의 검토 근거가 있어야 한다. 애플리케이션은 검토 참조가 없는 활성화를 거부하지만, 참조 문자열만으로 검토 내용의 타당성을 입증하지는 않는다. |
| 비교 정책 | 전환 활성, shadow eligibility 활성, shadow 비율이 0보다 큼이라는 세 조건이 모두 성립하면 comparison policy revision이 필요하다. 참조한 revision의 정책도 실행 구성에 존재해야 한다. |
| 상세 수집 | 상세 수집을 활성화하려면 허용 필드, 마스킹·표본 정책, 캡처 상한과 보존 정책을 확인해야 한다. 요약 수집만 사용하는 상태와 구분한다. |

현재 애플리케이션은 프로세스 자원 예산을 실행 중 변경하는 것을 거부한다. 자원 예산을 바꾸려면 시작 구성을 갱신하고 재시작해야 한다. 새 route를 추가할 때에도 해당 route의 계측 등록을 포함한 시작 구성을 확인해야 한다. 설정 변경 기능이 있다는 이유로 모든 시작 구성을 실행 중 바꿀 수 있다고 가정해서는 안 된다.

## 설정 변경과 충돌

초기 반영은 버전 있는 설정과 기존 배포·재적용 절차를 사용한다. 동적 설정 서버나 DB polling은 필수 구성에 포함하지 않는다. 애플리케이션이 스냅샷 검증·교체 기능을 제공한다는 사실과 여러 worker에 설정을 자동 전파하는 제어기가 연결되어 있다는 사실을 구분해야 한다.

설정 변경 담당자는 새 설정의 적용부터 완료 판정까지 다음 절차를 수행하십시오. worker는 자체 설정 스냅샷으로 요청을 처리하는 실행 프로세스이다.

1. 적용 대상 worker 목록을 확인하십시오.
2. 각 대상 worker의 현재 revision을 확인하십시오. 기대한 이전 revision과 다르면 차이를 해소할 때까지 해당 변경을 반영하지 마십시오.
3. 새 revision과 변경 사유를 정하십시오. 같은 revision을 다른 내용으로 재사용하지 마십시오.
4. 새 revision에 필요한 정책 묶음을 준비하십시오.
5. 새 스냅샷에 대해 위의 활성화 전 검증을 수행하십시오. 실패한 항목이 있으면 반영 절차를 중단하십시오. 마지막 유효 설정은 유지된다.
6. 기대한 이전 revision을 함께 제시하여 검증된 설정을 반영하십시오. 애플리케이션은 반영 시점의 revision을 다시 확인한다. 다른 변경이 먼저 반영되었으면 오래된 변경을 거부한다.
7. 각 대상 worker가 신규 요청에 사용하는 revision을 확인하십시오. 변경 요청이나 한 worker의 성공만으로 전체 적용 완료를 선언하지 마십시오.
8. 대상 worker별 실제 적용 결과를 기록하십시오.
9. 모든 대상 worker의 신규 요청용 revision이 의도한 값과 일치하면 해당 대상 범위의 적용을 완료로 판정하십시오. 불일치하거나 확인하지 못한 worker가 있으면 완료로 판정하지 마십시오.

애플리케이션의 설정 이력에는 반영에 성공한 revision, 변경 주체·사유와 요청·반영 시각이 남는다. 운영 적용 기록에서는 요청한 revision과 실제 적용 시작·완료·실패 worker를 구분해야 한다. 하나의 프로세스가 제공하는 적용 상태만으로 다른 프로세스의 상태를 추정해서는 안 된다.

| 확인 결과 | 다음 처리 |
| --- | --- |
| 새 설정이 유효하지 않거나 revision 충돌이 발생함 | 해당 갱신을 거부하고 마지막 유효 설정을 유지한다. 변경 담당자는 현재 revision과 거부 원인을 확인한 뒤 새 변경을 준비한다. |
| 최초 기동에 유효한 설정이 없음 | 요청 처리 준비 상태를 실패로 유지한다. 임의의 backend·비율을 추정하여 요청을 수락해서는 안 된다. |
| worker 사이에 적용 revision이 다름 | 부분 적용 상태로 기록한다. 서로 다른 revision의 결과를 같은 실험 조건으로 합산해서는 안 된다. |
| 변경 전에 시작한 요청이 이전 revision을 사용함 | 해당 요청은 기존 스냅샷으로 끝까지 처리한다. 신규 요청의 적용 실패와 구분해야 한다. |

shadow 중지나 v1 롤백을 검증할 때에는 실제 배포 방식으로 측정한 전파 시간을 목표 복귀 시간과 대조해야 한다. 설정 값 하나가 바뀐 시각만으로 모든 요청 경로가 복귀했다고 판정해서는 안 된다.

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-06 | P0 | 요청당 하나의 설정 스냅샷을 사용해야 한다. | 처리 중 설정이 변경되어도 해당 요청의 목적지·비율·비교 정책에 서로 다른 revision이 섞이지 않는다. |
| FR-29 | P0 | 설정 검증·적용 현황·변경 이력을 제공해야 한다. | 유효하지 않은 설정을 거부하고, 인스턴스별 적용 revision과 변경 주체를 추적할 수 있다. |

## 검증 기준

[T-01, T-07, T-08, T-31, T-46, T-48](../validation/test-catalog.md)에 따라 유효한 적용, 유효하지 않은 갱신, revision 충돌, 진행 중 요청과 신규 요청의 스냅샷을 각각 확인한다. 여러 worker를 사용하는 구성에서는 각 worker의 실제 적용 결과를 확인해야 한다.
