# 사용자 응답 선택과 cohort 배정

프록시는 요청마다 사용자 응답을 제공할 serving backend를 한 번 선택한다. cohort는 같은 배정 기준을 적용받는 사용자·세션·테넌트 등의 집합이고, cohort group은 배정 일관성을 공유해야 하는 연관 route의 집합이다. bucket은 배정 입력을 0 이상 1 미만의 수로 변환한 값이다. salt는 같은 입력을 재현하는 데 사용하는 고정 해시 입력값이다. 이 문서는 배정 조건, 키 누락 처리와 비율 경계값을 정의한다.

## 기능 계약

| 항목 | 정의 |
| --- | --- |
| 시작 조건·입력 | 요청에 고정된 설정 스냅샷, 등록 route와 cohort group, 배정 방식에 맞는 신뢰할 수 있는 키, v2 비율과 고정 salt를 사용한다. |
| 결과·출력 | 프록시는 serving을 v1 또는 v2로 정하고 배정 사유를 구분한다. cohort 계산을 수행한 경우에는 해당 bucket도 배정 결과에 포함한다. |
| 실패·제한 | 필수 cohort 키가 없으면 v1으로 배정한다. shadow의 속도·실패·비교 결과를 근거로 이미 선택한 serving을 바꾸어서는 안 된다. |

## route와 배정 기준

route는 method·path template과 안정적인 `route_id`로 식별한다. `GET /items/{id}`와 `POST /items/search`는 별개 route이다. method가 POST라는 이유만으로 복제 가능성을 배제하거나, GET이라는 이유만으로 복제를 허용해서는 안 된다. 복제 적격성은 [업무 효과 검토](../shadow/eligibility-and-sampling.md)로 판단한다.

목록·상세 API처럼 같은 버전 배정이 필요한 route에는 동일한 `cohort_group`과 같은 출처의 배정 키를 사용해야 한다. 같은 그룹의 모든 route는 아래 값을 모두 일치시켜야 한다. 하나라도 다르면 설정 검증에 실패한다.

- 전환 활성 상태인 `rollout_enabled`와 `v2_serve_ratio`
- 배정 단위인 사용자·세션·테넌트·요청 모드와 키 출처
- 해시 알고리즘, 직렬화 규칙과 salt

서로 독립적으로 전환해야 하는 route에는 자체 group을 사용한다. MVP는 무상태 API를 우선 대상으로 하며, 특정 backend에서만 해석할 수 있는 cursor·transaction 또는 backend 종속 세션을 요구하는 그룹은 제외한다.

| 배정 방식 | 사용 조건 | 키가 없을 때의 처리 |
| --- | --- | --- |
| 사용자 단위 | 인증된 사용자 식별을 신뢰할 수 있고 사용자별 일관성이 필요할 때 사용한다. | v1으로 배정하고 배정 사유를 `missing_cohort_key`로 정한다. |
| 세션 단위 | 같은 설정·배정 조건에서 세션 단위 일관성이 필요할 때 사용한다. backend 종속 세션은 MVP 대상이 아니다. | v1으로 배정하고 배정 사유를 `missing_cohort_key`로 정한다. |
| 테넌트 단위 | 테넌트 전체를 같은 기준으로 전환해야 할 때 사용한다. 운영자는 큰 테넌트의 요청량 편중을 별도로 확인해야 한다. | v1으로 배정하고 배정 사유를 `missing_cohort_key`로 정한다. |
| 요청 단위 | 사용자·세션·테넌트 키가 없는 완전 무상태 API에 사용한다. 프록시가 각 논리 요청에 독립적인 내부 키를 생성한다. | 프록시가 생성한 내부 요청 키를 사용한다. 배정 함수에 키가 제공되지 않으면 v1으로 배정한다. |

호출자가 임의로 보낸 헤더 값을 검증된 사용자·세션·테넌트 키로 간주해서는 안 된다. 키의 신뢰 경계는 [인증과 데이터 책임](../_rules/identity-and-data-boundaries.md)을 따른다. 요청 단위 배정은 같은 사용자의 연속 요청이나 서로 다른 연관 API 호출을 같은 버전에 고정하지 않는다.

## 요청별 배정 순서

아래 절차는 [경로 등록](route-registration.md)에 따라 route를 찾은 뒤 수행한다. 미등록 요청은 이 절차에 들어가지 않고 기본 v1으로 전달한다.

1. 프록시는 route의 `rollout_enabled`를 확인한다. 값이 `false`이면 route의 v1으로 배정하고 배정 절차를 종료한다. 이 경우 사유는 `rollout_disabled`이다.
2. 전환이 활성 상태이면 cohort 모드에 맞는 키를 가져온다. 요청 모드에서는 내부 요청 키를 사용하고, 나머지 모드에서는 지정된 신뢰 출처의 키를 사용한다.
3. 키가 제공되지 않았거나, 문자열이 아니거나, 빈 문자열이면 v1으로 배정한다. 이 분기에서는 배정 절차를 종료한다. 사유는 `missing_cohort_key`이며, 이 요청은 shadow 적격 요청에도 포함하지 않는다.
4. 키가 유효하면 group·키·salt와 고정된 해시·직렬화 규칙으로 bucket을 계산한다. bucket 범위는 `0 <= bucket < 1`이다.
5. `bucket < v2_serve_ratio`이면 v2를 선택한다. 그 밖의 경우에는 v1을 선택한다. 이 경우의 배정 사유는 `cohort`이다.

절차가 끝나면 선택 결과를 요청 전체에 고정한다. 전송 실패가 나더라도 반대편 응답을 선택하기 위해 이 절차를 반복해서는 안 된다.

## bucket과 배정 일관성

bucket은 `cohort_group + 검증된 key + salt`로 표현한 논리 입력에 대해 결정적으로 계산한다. 여기서 `+`는 문자열을 구분자 없이 붙이라는 뜻이 아니다. 현재 해시 버전은 `sha256-v1`, 직렬화 버전은 `length-prefix-v1`이며, 필드 길이를 포함하여 경계가 모호해지지 않게 직렬화한다. 프로세스마다 seed가 달라지는 언어 기본 hash를 사용해서는 안 된다.

동일한 group·키·salt·알고리즘·직렬화 규칙에서는 같은 bucket이 나온다. 이 값들을 유지하면서 v2 비율만 올리면 기존 v2 집합은 유지된다. 예를 들어 기존 조건을 만족한 bucket은 더 큰 v2 비율에서도 계속 `bucket < v2_serve_ratio`를 만족한다. salt 또는 배정 단위가 바뀌면 같은 집단으로 비교하지 말고 별도 실험 epoch로 구분해야 한다.

같은 그룹의 배정 일관성은 동일한 설정 revision, 동일한 배정 조건과 동일한 키를 사용한 요청 사이에서만 보장한다. 설정이 worker별로 혼재하거나 비율 변경 전후에 요청이 걸쳐 있으면 서로 다른 backend에 배정될 수 있다. 요청당 스냅샷을 사용한다는 사실만으로 세션 전체의 고정 배정을 보장해서는 안 된다.

운영자는 연관 API의 버전 혼용 허용 여부, 세션 수명, 설정 전파 시간과 복귀 목표를 확인하여 전파 기간의 운영 방식을 결정해야 한다. 이러한 값은 대상 서비스 계약에 따라 정하며, cohort 해시만으로 해결된 것으로 처리하지 않는다.

## v1 통과와 배정 경계

| 조건 | serving 결과 | shadow와의 관계 |
| --- | --- | --- |
| 전환 비활성 | route의 v1으로 배정한다. | shadow를 실행하지 않는다. |
| 전환 활성, 필수 키 존재, `v2_serve_ratio=0` | 모든 bucket을 v1으로 배정한다. | [shadow 정책](../shadow/eligibility-and-sampling.md)에 따라 v2 실행을 별도로 선택할 수 있다. |
| 전환 활성, 필수 키 존재, `v2_serve_ratio=1` | 모든 bucket을 v2로 배정한다. | shadow를 선택하고 실행 조건도 충족하면 반대편 v1을 실행한다. |
| 전환 활성, 필수 키 누락 | 비율이 1이어도 v1으로 배정한다. | 이 요청은 shadow 적격 요청에서 제외한다. |
| 미등록 또는 지원 범위에서 제외된 경로 | [미등록·미지원 경로 계약](route-registration.md)을 따른다. | 등록·적격 요청의 분모와 구분해야 한다. |

운영자는 설정 비율과 실제 사용자 응답 분포를 함께 확인해야 한다. cohort 비율은 배정 단위의 비율이며 요청량 비율이 아니다. 사용자별 활동량이 다르므로 사용자 10%를 v2에 배정했다고 해서 초당 요청 수(QPS)의 10%가 v2로 간다고 해석해서는 안 된다. 필수 키 누락, 미등록과 제외 경로도 배정 조건을 충족한 집단과 구분하여 분석해야 한다.

진입 gateway와 프록시 양쪽에서 전환 비율을 적용하려면 운영자는 각 계층의 배정 책임을 명시하고 실제 노출·cohort·복귀 결과를 검증해야 한다. 기존 weighted routing이나 cookie stickiness로 이 배정을 대체하려는 경우에도 같은 배정·관측·복귀 계약을 충족한다는 근거가 필요하다.

## 요구사항과 수용 조건

| ID | 우선순위 | 요구사항 | 수용 조건 |
| --- | --- | --- | --- |
| FR-02 | P0 | v1 통과 모드를 제공해야 한다. | shadow 비율과 v2 비율이 모두 0이면 v2 요청이 발생하지 않고 기존 전달 계약을 보존한다. |
| FR-03 | P0 | 요청마다 serving backend를 한 번만 선택해야 한다. | 응답 속도나 shadow 결과가 이미 선택한 serving을 바꾸지 않는다. |
| FR-04 | P0 | route 또는 연관 route 그룹별로 v2 응답 비율을 제어해야 한다. | 비율 0과 1에서 표에 정의한 결과가 나오고, 같은 revision·조건·키에서 같은 배정이 나온다. |
| FR-05 | P0 | 일관성이 필요한 API에 안정적인 cohort를 적용해야 한다. | 고정 해시·직렬화에서 동일 입력의 bucket을 재현하고, 그룹 정책 불일치를 거부하며, 비율 상승 시 기존 v2 cohort를 유지한다. |

## 검증 기준

[T-02, T-04, T-05, T-06, T-07](../validation/test-catalog.md)에 따라 키 존재·누락, 전환 활성·비활성, 비율 0·1과 그룹 정책 불일치를 각각 검증한다. 비율 변경 검증에서는 group·키·salt·알고리즘·직렬화 규칙을 유지했는지 함께 확인해야 한다.
